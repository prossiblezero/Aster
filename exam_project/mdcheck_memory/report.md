# mdcheck 真实开发与 Memory 对照报告

日期：2026-09-18（Asia/Shanghai）。机器可读结果见 [results.json](results.json)，需求见 [requirements.md](requirements.md)。

**两组各三个阶段均由 Aster 完成，六次运行全部通过独立验收，没有操作员返修提示或代写实现。持久 Memory 在自然开发中没有被使用；明确要求保存记忆时，模型可以自行发现工具并保存。** 这证明 Aster 能在当前支持的 Python 环境中，从需求文件起步开发、测试和迭代一个实用 CLI；不等于已证明任意需求、联网调研、依赖安装和长任务恢复的通用自主交付能力。

## 交付与实验条件

- [memory_off 项目](workspaces/memory_off/README.md)：包含模块、可安装包、MIT LICENSE、示例与测试，可作为本次小工具的使用入口。
- [memory_on 项目](workspaces/memory_on/README.md)：独立实现，作为对照保留。元数据声明 MIT，但未生成独立 LICENSE 文件，正式单独发布前应补齐。
- 实现包括本地 Markdown 链接、图片、编码路径、代码围栏、标题锚点、重复标题、JSON 输出、稳定排序和退出码。第三阶段默认检查 `manual`，显式路径仍有效。支持的是需求约定的 Markdown 子集，不是完整 CommonMark。
- 两组均从只有 `PROJECT.md` 与阶段需求的目录开始，**没有实现代码，但不是字面意义的全空目录**。操作员提供需求、三阶段调度、约定文件变更、独立验收和 Git 保存；项目代码、项目测试和 README 由 Aster 编写。
- 固定 `gpt-5.6-sol`、Responses、128,000 总上下文、32,768 单次输出上限、80 工具步、50 模型轮、300 秒请求超时。required 沙箱，工具禁网，Worker 关闭，未配置 Skill。Python 均为 `/home/dzh/.conda/envs/aster/bin/python`，没有在 base 执行或安装项目依赖。
- `memory_on` 开启持久 Memory、演化与自动 Dream；`memory_off` 关闭这三项。两组任务内 working memory 均保留。每阶段是同一项目上的新 Runtime 任务，不是已实现自然续聊的证明。
- 核心实现冻结于 `30acbae`，协议提交为 `058fc4e`；六次运行的源码 manifest 全部一致。两条任务链交错执行，有并发、无随机化和重复采样，只能作个案观察，不能将延迟或 token 差异解释为因果收益。

104 份记录到的模型回复都返回了输入、输出、缓存和推理字段，逐指标覆盖率为 104/104；59 份缓存读取大于 0，45 份明确为 0。表中是按 token 加权的缓存比例，不是请求命中率，也不是省钱比例。已报告总量为 **1,877,680 tokens**；20,969 reasoning tokens 已包含在输出统计中，不能再相加。供应商账单、网关内部处理及未暴露的重试成本不能由这些字段完整推断。

本轮未改变 prompt 布局。结合此前动态状态放在第二条消息的审计，**稳定早部前缀仍值得做下一轮独立对照**，但不能承诺某个命中率，也不能用 on/off 差异证明 prompt 优化效果。应固定任务与模型，比较缓存、总输入、质量及耗时后再决定保留改动。

32,768 是每次响应的上限，不是每次实际消耗；本轮最大已报告单次输出为 **5,024 tokens**，没有记录到输出额度耗尽或 Provider 终止错误，也没有上下文压缩。提高上限提供了余量，本实验未做输出预算消融，不能宣称它造成了成功或某个效率提升。预检另报告 4,400 tokens；显式记忆诊断另报告 18,629 tokens，均未混入上表。

## Memory 到底发生了什么

自然任务的 on 组全程没有调用 `memory_store`、`memory_update` 或 `memory_retrieve`，存储始终为空，自动召回也无条目。每个阶段末尾 Dream 的 `deactivated=0` 只表示维护了空存储。**启用开关不等于自动从任务中学习；这次没有产生可用于比较收益的持久记忆。** 任务约定一直可从磁盘重新读取，提示也要求读取，因此本实验并非必须依赖记忆才能解决的任务。

为区分未触发与机制故障，另外完成两项不计入 A/B 成绩的诊断：

| 诊断 | 实测结果 | 证明边界 |
| --- | --- | --- |
| 操作员指定动作，5 次 Runtime，0 次模型调用 | 经真实 `read_file → memory_store` 保存有来源的原文；新 Runtime 原句查询命中且进入实际请求；中文改写“默认目录”和阶段 2 原提示均未命中；来源变化后立即过滤，Dream 随后标记 `stale_source` | 保存、持久化、精确匹配、来源失效链路可用；9 项诊断预期符合不等于 9 项用户能力都成功 |
| 单次真实模型显式记忆请求，不提示工具名 | 14.459 秒、3 轮、4 步；模型自行 `list_files → read_file → tool_load(memory_store) → memory_store`，成功保存 1 条原文，无拒绝、无追加提示 | 明确要求记忆时能发现并使用工具；不能冒充自然主动写入 |

证据：[离线机制诊断](probes/memory-mechanism/result.json)、[显式模型诊断](probes/memory-explicit/summary.json)。摘要也保存于可提交的 `results.json`。

源码与轨迹解释了剩余边界：默认核心工具只通过加载目录展示 Memory 名称，未引导何时值得保存；自动检索使用初始任务提示，按词面子串匹配，中文改写容易漏召回。保存限定为**本次运行成功读取文件的原文摘录**，不能直接保存失败命令、用户偏好或自主概括的经验；Dream 也不从轨迹提炼新经验。它目前更接近“有来源的项目摘录记忆”。

一个具体例子是：on 组阶段 2 已遇到 `apply_patch: not found`，新任务阶段 3 仍尝试该命令。当前保存契约无法直接接收前一轮工具失败作为记忆来源，会话又在任务边界重启。不能把这种重复单纯归咎于检索算法。

建议先明确 Memory 产品目标：若保留摘录定位，改善工具发现、保存时机、中文查询与目录标签即可；若要保存环境约束、用户偏好、纠错教训，则需单独设计这些来源的准入、失效和验证。保留现有 provenance 和过期过滤，不以无约束自动总结替代它们，不急于引入向量库或重写整个 Runtime。

## 暴露的问题与下一步

| 实际发现 | 当前处置 / 后续建议 |
| --- | --- |
| pip 在沙箱中读取 `/etc/debian_version` 被拒，尚未进入项目构建 | 已保留失败并由宿主确认产物可安装。后续最小候选修复是只读放行该文件并补离线打包回归；不是开放整个 `/etc`，也不代表依赖复用问题已解决 |
| 合法 heredoc 因正文中的 `directory's` 被 `shlex.split()` 当成未闭合引号，误判 `invalid_shell` | `/bin/sh -n` 对原命令返回 0，控制组验证了词法误拒；只检查语法，没有执行命令。后续修 Shell 预检与审批分类，保留沙箱与权限约束。证据：[诊断](probes/shell-heredoc/result.json) |
| 模型假定 Shell 中有 `apply_patch`，实际没有；一次精确补丁匹配到 3 处被拒 | Aster 都自行回到可用的 `patch_file` 完成修改。改善可用命令说明和补丁契约，训练数据应保留失败—反馈—改用正确工具的过程；无需为了迎合假设添加同名万能工具 |
| 两次自测失败分别涉及错误的转义测试数据和行号期望 | Aster 自行修复；独立验收仍全过。后训练不能仅以模型自写测试或自报完成给奖励 |
| 普通任务没有持久记忆，中文改写漏召回，工具失败不能直接保存 | 按上节区分触发、检索与记忆来源，不把开关对照当作收益结论 |
| 旧 `scripts/benchmark_support.py::metrics()` 仍把缺失 usage 当 0，未带逐指标覆盖率 | 本实验直接记录 Runtime usage，未经过该函数，结果不受它影响；其他旧 benchmark 的消费端仍需适配，不能把部分用量当成完整费用 |
| 启动目录若本身被父 Git 忽略，工作区清单可能报 `git_ignore_unavailable` | 在忽略的 CLI 诊断目录复现，独立 Git 初始化后 CLI smoke 通过。正式两组放在非忽略 workspaces 中；应明确该启动边界或改善错误诊断 |

自然 160 次工具动作中有 6 次非成功结果：两次自测失败、pip 环境失败、缺失 `apply_patch`、非唯一补丁与合法 heredoc 误拒；其余 154 次成功。没有操作员修改候选实现来消除这些记录。

高频工具仍是读文件 54 次、补丁 33 次、Shell 20 次和写文件 16 次；唯一一次 `tool_load` 加载的是计划工具，随后未调用。没有证据支持按工具数量大删核心；先减少无用加载与反复交互、改善输出和命令契约。Skills 本轮没有配置，因此仍需单独的真实技能试点，不能把此次成功算成 Skills 的收益。

本轮按已批准顺序完成基础小修与现有 Memory 实验，没有修改实验中的 Memory、Shell 策略或文件白名单。新发现留在此处作为下一批可复现修复，不将边评测边改算法后的结果合并成一次成功。自然续聊、失败后继续、任务执行环境复用、授权联网、Node/Web 正式验收、Skill 实际试点仍是待办；本轮也没有 pi 同条件对照。

## 后训练结论

**可以开始数据集构建、SFT、GRPO 的方案设计，无须先照 pi 重构核心；尚不能把当前项目直接当作完整训练系统开训。** Aster 已具备真实工具闭环、隔离 episode、实际请求归档及独立奖励入口，本轮又提供了成功、失败和自修正轨迹。详细依据与阶段门槛见 [后训练准备度审计](../../docs/post-training-readiness.md)。

下一步先冻结新的 train/dev/test 任务家族与可信验证器，打通按实际请求导出的 SFT 数据、assistant-only mask 和工具协议校验；随后接入可训练模型，补 token/logprob、权重版本、同题采样组和独立奖励，再做小规模 GRPO。现有网关只是推理服务，不会因为运行 GRPO rollout 而更新其模型。

本案例和教学网站已用于工程调试，只能作为开发/诊断案例，不能再同时用来训练和宣称未见任务泛化。Memory 也不是开始训练设计的前置条件；首版可关闭 Memory/Worker，先保证单 Agent 的观察、动作、奖励契约可靠。
