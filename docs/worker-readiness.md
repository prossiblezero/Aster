# Worker 适用范围与剩余边界

更新于 2026-09-30，对应 `src/aster/core/workers.py`。9 月 18 日只读工具并行实验始终关闭 Worker，其读取重叠不能作为多 Agent 收益。历史实验见 [交付修复](../evaluations/worker-handoff-20260925/REPORT.md)、[调查委派迭代](../evaluations/worker-value-20260925/REPORT.md)与[重设计前代码任务基线](../evaluations/worker-code-20260928/REPORT.md)。[三臂真实模型评测](../evaluations/worker-redesign-20260928/REPORT.md)和最新的[四题三次聚焦复验](../evaluations/worker-focused-20260929/REPORT.md)都证明 partial handoff 可以保留并对账，但没有证明 Worker 稳定提高通过率或降低全队 token。

最新复验的 24 个 episode 中，Solo 通过 2/12、Worker 5/12；正确正常交付为 1/12 对 3/12，但 Worker token 多 21.6%、时间多 30.2%。CDF repeat-01 是明确的 scoped 正例：子任务实际写入六个 CDF 方法，公开内部样例 12/12 通过；三轮合计仅 Worker 31/36、Solo 30/36，后续仍有精度错误和超时。这个结果支持“可选协作能力在特定任务可能有用”，不支持默认开启或效率收益的简历表述。

## 已有能力

Worker 使用独立 Runtime 与历史；`max_workers` 限制同时活跃数，默认关闭。Explore 强制只读，不因任务中的“修复、测试”等关键词产生无法履行的编辑门槛。写 Worker 必须声明非空范围，且同一时间只允许一个写 Worker；父任务在此期间也不能写入或启动进程，可继续只读调查。子任务不能继续派生。

父子共享根 `TaskSpec.max_steps` / `max_turns` 总额度，以及可选的 `max_tokens` 上限。子任务按剩余额度分配，最多 24 个工具步骤、12 次模型调用；为父任务保留总步骤与调用额度的约 20%（至少各 2 次），token 至少保留约 20%，父任务已有请求估计时取它与两次父请求估计的较大值。余额连该保留量加一次最大输出都无法容纳时，不再启动子任务。直接 API 尚未构造父请求时退回 20%；切换运行清除旧估计。请求发出前预留估算输入与最大输出，返回后按供应商报告结算；缺失 usage 时保留估算记账。计数持久化在 `RunState.team_usage`，失败、取消及在途请求不会被视为免费；这是请求预算控制，不是供应商美元账单的精确上限。

首轮能力提示说明分工与交付；子任务自动收到初始 `TaskSpec.prompt` 及当前分支最近的用户请求（最新要求优先），父任务补充局部目标、已知事实、输出形式和测试责任，并用可选 `parent_work` 声明自己负责的独立工作。双方收到分工，记录随父检查点保存；这仍是协调提示，不是无重复工作的保证。局部预算耗尽时会尝试一次无工具交付轮；团队额度不足、服务错误或取消时保存包含已读路径、实际改动、验证状态与停止原因的确定性部分结果。`handoff.json` 的 `delivery` 区分 `complete` / `partial`，不会将额度耗尽标成完成。

已结束子任务的交付在父任务下一次模型请求前自动送达一次。`worker_status` 仍可等待单个 ID 或最多四个 ID，共享 0–300 秒期限；返回工具结果后，不再重复自动通知。界面轮询不算模型已收到结果。外层 `finished` 仅表示选中的子任务都已终止，必须检查每项结果；超时和取消查询均不取消孩子。父检查点保存待交付编号，恢复后补发已落盘结果；没有交付文件时报告中断，不会重启子协程。

已结束子任务可用 `worker_message(..., resume=True)` 在原上下文中补问一次，新增额度最多 8 步/4 轮，仍从团队余额扣除。父权限变化、并发名额用尽或预算不足会拒绝续跑。普通未绑定子任务在父任务结束时清理；绑定了需求的活跃子任务会让过早的 Final 返回等待反馈，显式取消和总预算耗尽仍会清理全部孩子。不会隐式无限等待。

父任务具有严格测试要求时，子任务按实现交付、父任务验证最终工作区。调查结论应保留来源和未核查项；父任务针对具体缺口查证、通过真实接口检查可执行结论。提示不是事实担保：引用路径不等于自动验证了来源，`completed` 不等于独立验收通过。

多个独立结果的请求可用现有 `todo_add.acceptance` 记录验收条件，Solo 也支持。`worker_start.todo_id` 绑定其中一项，启动后记录子运行与负责人；启动被拒绝不改变待办。完整或部分交付都会把事项返回父任务待验收，只有父任务 `todo_update` 附上 `resolution` 才能关闭。绑定运行期间不能直接关闭或抢占这项待办；需要先等待或停止子任务。旧版不带这些可选字段的工具调用仍兼容。

带验收条件的未处理事项阻止严格完成；本次请求取消的事项会出现在最终答复中，最多标为 `completed_with_warning`，不能成为独立的通过证据。同一任务恢复继续保留该警告，新用户请求不继承历史取消警告。状态、交付关联和验收说明随原检查点保存，旧交付不能覆盖后一次重新分派；续聊将无法复活的运行归属退回待处理。`resolution` 和 `done` 仍是父模型的判断，运行时不能保证其语义正确，也不能发现模型从未列出的需求，必须结合独立评分。

## 仍未提供的能力

- **独立文件工作区与自动合并**：父子共享真实工作区，写入范围检查不隔离用户编辑器或另一个 Aster 进程。执行依赖按 Runner 隔离，不共享可写依赖根。
- **恢复后台执行与任意往返消息**：进程恢复只补发交付；不复活子任务，补问仅支持当前进程内保存的子 Runtime，且最多一次。
- **自动保证结论正确或交付完整**：无工具收尾和确定性 fallback 保住已有证据，但不会修正模型遗漏、错误引用或未完成的实现。父任务仍须看终态与证据并补救。

会话内模型切换仍要求所有 Worker 空闲。后训练首版继续关闭 Worker；子轨迹信用分配未实现，不宣称支持完整多 Agent GRPO。

保持轻量实现：优先用于能独立调查、交付短结论的任务；单文件小修改可能付出更多交接成本。收益必须结合具体场景、独立正确性与全部父子消耗解释，不把主上下文下降等同总成本下降。
