# 2026-10-11 上下文计量与调用成本优化

第二版完整二十题使用 8,369,416 已报告 tokens、405 次请求，独立通过 15/20。pi 和 Codex 的固定历史用量分别约 653 万 tokens。Aster 未缓存输入为 3,648,020，缓存输入占比 55.8%；差距不能用输出篇幅或后台记忆独自解释。

## 诊断证据

检查第二版的 393 次前台请求，373 对相邻请求中有 138 对改写此前已发送的历史前缀；工具定义没有变化。保持历史前缀的请求缓存输入占比 77.9%，改写前缀的请求为 25.5%。这是观察关联，不是独立的缓存因果实验。后台记忆已报告 69,051 tokens，占总量约 0.83%，另外两次后台请求缺少用量。

Requests 5414 第十二次请求的本地序列化计量约 54,682 tokens，而服务端输入回执为 22,665；其中加密推理字符串被本地 tokenizer 算成约 29,610 tokens。下一轮开始裁剪旧历史，缓存输入由 20,992 降为 5,632。加密载荷的文本长度与其重放时占用的模型上下文不是同一个量。

参考已安装的 pi 1.1.0 的 `estimateContextTokens`：使用最近有效 usage 加后续消息估算，压缩或编辑旧历史后使旧基准失效。Aster 采用更局部的校准：只替换有对应回执的加密字段估算，保留其余请求结构的原有计量。尝试访问 OpenAI reasoning / prompt caching 官方页面均遇到 HTTP 403；本轮没有把未读取的官方网页作为实现证据。

## 实现

- `context/budget.py`：仅在成功、无诊断异常且用量完整的单次回执中提取推理 token；使用密文摘要关联原生推理项。若缺少单独 reasoning 计数，保守采用该回复全部输出 token。密文原样保留在实际请求、历史和检查点中。
- 同一运行与模型内保留观察到的最大正向输入开销，涵盖兼容服务在请求之外添加的内容。无回执、重试累计用量、失败回执或模型不符时不进行校准。切换运行或模型后清除校准；未知或恢复后的旧推理项继续用原有保守估算。没有改变 checkpoint 格式。
- 只有达到原输入上限才触发裁剪，并为下一轮预留最多输入额度的 1/8、且不超过输出预留额度的空间。保留工具交换配对、用户约束和最新交换，不增加 LLM 摘要调用。策略版本为 `deterministic-v8`。
- `core/runtime.py`：用成功请求的实际 payload 和该次回执更新计量；账单累计、未知用量、请求重试和团队预算结算维持原有统计方式。
- `context/prompt.py`：精简原验收指引，先执行聚焦回归，代码与环境未变时复用通过证据；环境问题须检查未改动基线，避免扩展到无关产品修复。没有削弱正式验收、旧失败保留或工作区变化失效规则。

没有新增依赖、服务、模型、配置项或额外模型调用。自动记忆保持开启。已校准的密文计量是基于供应商回执的估算，不是解密或声称精确知道服务端内部上下文。

## 验证与评测口径

新增回归覆盖大密文原样重放、证据保留、缺失/失败/累计用量拒绝校准、成功重试回执的独立归属、模型切换清理、裁剪后下一轮前缀稳定。旧二十题日志中有 372 次可校准的后续请求；离线计量均不低于其服务端输入回执，但这不保证未来所有服务都不会低估。

工程测试与费用评测分开。先执行 Requests 5414、C++ heap crash、Sphinx 11510 三题两版各一次的新对照，两组都包含路径隔离修复；达到预先规定的质量和费用条件后，才执行新版完整二十题。使用同模型、题面、镜像和预算，记录全部失败、超时与未知用量，不以三题最好结果替换全组。见[事先登记协议](../evaluations/general-coding-cost-20261011/PROTOCOL.md)。

费用比较报告未缓存输入 U、缓存输入 C、输出 O 和请求数；`U + r*C + q*O` 只作明确权重的敏感性分析，不能当作实际账单。压缩减少也可能使总输入增加，最终判断必须同时观察独立通过率与这些计价分量。

## 2026-10-12 完整结果

二十题全部独立评分，通过 **15/20**，正常交付且通过也是 **15/20**，与上一版及 pi 的固定历史成绩持平。解释器新增通过，Requests 2931 新增字节参数回归；内部完成 19 题中有 4 题独立失败，另有一次超时。

请求 **405→349（−13.8%）**，未缓存输入 **3,648,020→3,342,426（−8.4%）**；总 token **8,369,416→9,148,018（+9.3%）**，累计耗时 **+27.4%**。历史前缀改写 **138/373→11/319**，缓存输入占比 **55.8%→63.0%**，但仍低于 pi/Codex 的历史占比。

六组费用权重的已知用量估算仅下降 **0.7%–4.7%**，缺失回执 **3→6 次**，实际账单下降没有得到证明。共同通过的 14 题中，未缓存输入反而 **+6.4%**、总 token **+20.4%**，六组费用权重均增加 **6.5%–12.8%**。因此保留计量正确性修复，但不把本轮描述成普遍降本、全面提速或成本优于 pi/Codex。

三题两版对照与完整复测共 **26 次尝试、13,395,171 已报告 tokens、537 次请求、10 次用量缺失**，各阶段分列。工程测试合计 1220 个不同测试通过、4 项跳过；首次完整运行的三个旧版本断言失败及修正后复验记录均保留。完整比较、失败分析、研发消耗和冻结证据见[评测报告](../evaluations/general-coding-cost-20261011/REPORT.md)。

后续[2026-10-12 源码与耗时诊断](../evaluations/cost-diagnosis-20261012/REPORT.md)确认了重复处理大仓库基线的检查点开销，并发现 pi/Codex 请求携带而 Aster 缺少的会话缓存键；建议先局部重构持久化、独立验证缓存路由，再采用离线检查与四题门禁。该诊断没有调用模型或产生新的 benchmark 成绩。
