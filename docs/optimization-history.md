# Aster 的优化历程

本文整理 2026-09-11 至 2026-10-09 的主要实现与取舍，回答三个问题：遇到了什么问题，怎样解决，为什么选择这种办法。依据是开发提交、设计记录、工程回归和本地实验归档。它不是对当前版本重新进行的模型能力评测。

首次公开仓库采用干净源码快照，原始轨迹、逐轮结果、模型请求、产物压缩包及个人材料不上传。文中的短提交号是维护者本地历史索引，不是公开仓库可 checkout 的版本；验证当前实现应使用本仓库的测试与评测入口。下列历史观察保留失败、条件和未解决边界，不把开发集成绩写成公开榜单成绩。

## 1. 从工具循环到可检查的 Runtime

**问题。** “模型说完成”无法证明文件真的变了，命令退出成功无法证明测试真的执行了；如果交互模式与评测模式各实现一套循环，研究结果也可能脱离产品行为。

**解决。** 将任务状态、模型回复、工具动作、观察、证据与完成检查放在同一个 Runtime。CLI、TUI、直接执行和外部策略环境复用它；工作区文件操作与子进程执行通过统一权限和沙箱边界。事件、检查点和工作区指纹让运行过程可以检查。

**原因。** 先建立可以验证的执行契约，比增加更多工具或另一套 Agent 框架更有价值。证据是结构化状态，不依赖模型在最终答案里自我声明。

早期评测逐步区分工程回归、参考动作回放、机制开关和真实模型任务。后续又把任务、初始仓库和独立评分器移到 `datasets/`，避免评分规则与模型观察混在一起。

当前入口：[Runtime](../src/aster/core/runtime.py)、[执行协调](../src/aster/core/execution.py)、[证据存储](../src/aster/storage/evidence.py)、[评测教程](learning/14-evaluation.md)。本地历史：`ee4dca0`、`6a47853`、`60220c1`、`8f55b97`、`3127ad1`。

## 2. 修复状态、权限和验证的共同根因

09-14—09-15 的集中修复来自真实调用链中的不一致。

| 问题 | 解决办法 | 为什么放在这里 |
| --- | --- | --- |
| 连续成功编辑因输出相似被误判停滞 | 同时比较动作、结果和实际文件变化；保留有界恢复窗口 | 停滞判断必须依据进展，不能只比较模型文本 |
| 工具定义可见但执行必然拒绝 | 目录、按需加载和直接执行共用可用性判断 | 修一个共享入口，避免多个列表各自漂移 |
| diff 把哈希当成原文 | 指纹判断漂移，文本快照生成 diff；恢复沿用原基线 | 哈希与内容有不同职责 |
| TUI 默认批准或取消后仍有迟到操作 | 明确审批回调、单个在途操作、先取消再回收子任务 | 交互状态不能替代真实授权与生命周期 |
| 成功路径漏 Stop hook，失败路径重复收尾 | 所有终态统一、幂等地收尾 | 保持 CLI、自主循环和外部步进的一致性 |
| 打印 passed、全部 skip 或提前退出被算通过 | 读取结构化测试报告，核对执行与错误状态 | stdout 文字不构成有效测试证据 |
| 导入失败被归因于记忆有害 | 区分环境错误与实际测试失败，反馈只作用于明确应用的记忆 | 未执行的验证不能提供负面因果证据 |
| 子进程隔离阻断 asyncio 自唤醒 | 允许必要的本地 IPC，继续拒绝建立网络连接 | 文件、网络和进程机制需要分别理解 |
| 特殊文件、路径重定向、回写冲突 | 拒绝链接和特殊文件，读取有上限，写回前核对版本 | 防止阻塞、越界和覆盖用户的新修改 |

Memory 快照的存取改为深拷贝，避免回滚后的操作继续修改旧快照。RL episode 也增加终态与并发保护，奖励来自独立验证器，防止反复调用工具刷奖励或结束后再次 step。

这些修复选择了现有状态模型、标准库、统一权限函数和结构化报告，没有另建执行引擎。保留的边界包括：批量文件回写不是整个工作区的事务，候选 Python 与测试共用解释器不能防范任意恶意策略，测试反馈也不能证明某条记忆造成成功。

当前证据：[生命周期测试](../tests/test_runtime_lifecycle.py)、[工具契约](../tests/test_tool_contracts.py)、[沙箱测试](../tests/test_sandbox_async.py)、[RL 契约](../tests/test_rl_contract.py)、[评分边界](grader-boundary.md)。本地历史：`d405773`、`1377204`、`02636f3`、`9e34f54`、`fd2fe66`、`a7a1e1d`。

## 3. 上下文：先归档，再按真实请求压力压缩

**问题。** 对工具结果统一截成固定长度，可能在窗口仍充裕时删掉关键错误；只计算消息正文又会漏算工具 schema 和协议包装。按固定条数裁剪历史还可能切开工具调用与结果、丢失模型原生推理状态。

**解决。** Context 与 Provider 使用同一请求构造逻辑，估算完整请求并预留输出预算。观察先保存原文归档，再根据全局压力移出旧内容；工具交互成组处理，近期请求和必要状态优先保留。模型可以按引用、页码或行段回读归档，分页游标与实际展示范围一致。正常运行与外部策略共用输入构造。

**原因。** 确定性管理容易解释与复现；额外的模型总结器会带来费用、延迟和语义丢失，因此当时没有引入。归档保留了重新取证的通道，但不能保证模型主动使用它。

实验也修正了一个容易夸大的结论：历史记录中的 57.8% 是某组开发题首请求的本地估算压缩率，不是整个任务的供应商费用节省。同输入预算的新版完成情况并未全面改善；随后选定更宽预算得到更好结果，不能把预算调整归因成代码优化。一次性信息在压缩后未被主动回读，仍是边界。

检查点随后单独修复了对加密推理字段的误脱敏：可展示文本需要脱敏，协议不透明状态不能随意改写字节。该修复与前一轮模型评测的源码版本分别记录。

当前入口：[预算构造](../src/aster/context/builder.py)、[预算教程](learning/06-context-budget.md)、[归档教程](learning/07-context-archives.md)、[协议配对测试](../tests/test_protocol_pairing.py)。本地历史：`3ddf848`、`54e1900`、`67e4415`、`9f0cbfb`、`4bb221b`。

## 4. 从一次调用走向连续开发

09-17—09-19 的实际产品任务暴露了环境、输出和交互问题。

- **修改太碎、输出看不全。** 增加批量补丁、分页文件与命令观察，以及可读归档；写入仍要求当前版本的读取，不能为了便利跳过冲突检查。
- **模型切换只能改 URL。** 增加具名 profile，统一服务、协议、凭据引用和预算；历史转换只承诺可移植部分，不伪装成能无损迁移所有供应商状态。
- **长请求没有反馈，取消不及时。** 接入 Responses 流式与异步终端展示；完整回复确认后才执行工具，失败和取消不提交半截工具调用。
- **凭据轮换后旧 Key 仍可能出现在错误中。** 将历史与当前凭据纳入脱敏，同时保护必须原样保存的协议状态；Skill 元数据和正文也经过相同展示边界。
- **依赖安装后下一次命令找不到。** 保留默认的一次性隔离，增加显式环境复用；失败时解释依赖目录是否已回收。复用要求严格沙箱，并保护包缓存与清理路径。
- **普通命令成功被当作已验证。** 明确 `run_tests` 的职责，增加 Node 内置测试的结构化支持；其他命令仍可执行，但不自动获得正式测试证据。
- **工具很多但大多数用不到。** 保持核心目录短小，Skills 支持包元数据与安全分页；加载正文后固定快照，刷新才更新。
- **每轮动态记忆破坏稳定前缀。** 固定规则、原始请求和已确认历史在前，动态状态在后；缓存命中仍由服务端决定。

只读工具批次可以并行，写操作继续保留顺序与版本检查。选择这种局部并发，是因为“多个独立读取”比“多个写入者共享工作区”更容易定义一致性。

这阶段的网页与数据处理产品也经历了返修、环境错误和人工验收，不能用首次运行结束代替最终产品可用性。产物本身不是 Aster 的运行依赖，所以公开仓库只保留提炼后的方法与核心实现。

当前入口：[模型配置](configuration.md)、[执行环境](execution-environment.md)、[Skills](skills.md)、[Provider](../src/aster/providers/)、[工具](../src/aster/tools/)。本地历史：`30acbae`、`ead9f26`、`c02a587`、`15269d6`、`59ca274`、`95178d9`、`168906a`、`ad67657`、`fbdc680`、`7252d50`、`c74e445`。

## 5. 拆分职责，并验证真正安装后的路径

**问题。** Runtime、工具路由、协议传输和 UI 逐渐集中在大文件里；恢复和模型切换在检查完成之前就修改状态，失败时会留下半更新。只在源码根目录运行测试，也可能掩盖包缺文件或错误导入。

**解决。** 工具 schema、业务与正式测试拆开；Provider 区分 codec、streaming、usage 与 errors；会话操作先准备候选，再提交上下文和生命周期状态。随后采用 `src/aster/` 布局，将 core、storage、knowledge、training、sessions、ui 分组，删除迁移期间的旧模块 shim。

**原因。** 模块边界围绕真实职责，仍保留一个 Runtime、一套执行契约，避免“拆文件”演变成多套框架。验证同时覆盖源码回归、wheel 内容和离开源码目录后的 CLI/TUI 导入。

测试也分为 smoke、core、完整回归，用原生 pytest 标记选择；分层不删除断言、不把不同条件合并成一个看似更少的用例。

当前入口：[模块地图](module-layout.md)、[测试指南](../tests/README.md)、[开发指南](development.md)。本地历史：`3fa6170`、`f4e7a81`、`da23241`、`c7a837d`、`b49c113`、`9d8b70f`、`a3f338b`、`edec1aa`。

## 6. 会话树：把对话位置与运行快照分开

**问题。** 连续探索后想回到第 i 轮重新尝试，单个“最近 checkpoint”不够；把后续总结塞回旧历史又可能泄露未来信息。多个会话还需要独立状态和明确的切换、命名与恢复入口。

**解决。** 引入类型化会话条目与历史树，支持从选定位置分支、查看记录来源、显式摘录交接，以及多个独立终端会话。运行快照与历史位置分别保存，选择历史不重复累计模型用量；后台流式预览和共享记忆刷新也随生命周期处理。

**原因。** 历史导航是交互能力，不应等同于复制整个工作区。文件仍是当前磁盘状态，采用外部变更要显式确认并重新读取/验证。历史隔离、操作便利性和真实代码质量分别检查，不能把点击次数减少解释为模型更聪明。

当前入口：[会话指南](sessions.md)、[树结构](../src/aster/sessions/tree.py)、[导航](../src/aster/sessions/navigation.py)、[会话树测试](../tests/test_session_tree.py)。本地历史：`6fdb8de`、`69a6438`、`a9f63c7`、`4daaa13`、`1fee848`、`e2f14f7`。

## 7. Worker 第一轮教训：能派工不等于能交付

09-22 起的多轮任务发现，子任务可能已经启动，但父任务频繁查询、提前结束，或者双方重复调查与测试。早期固定代码对照还观察到委派组交付不稳定，整体正确性与费用没有稳定优势。

**先修等待。** `worker_status` 加入有界等待，后续支持一组任务集中等待，避免只拿到“仍在运行”就继续消耗模型轮次。

**再修责任。** 父任务的严格测试要求不能原样压给受限子任务。调查型子任务提交调查结论，实现型子任务提交实现与说明；父任务保留最终验证责任。只读 Explore 的完成条件也必须与其权限匹配。

**补齐原始要求。** 子任务收到初始请求和当前分支最新用户请求，父方再提供局部分工与已知证据，减少复现步骤、验收条件在转述中丢失。`parent_work` 明确父方仍承担的工作。

**保留真实成本。** 统计整个任务树的模型调用、工具动作、token 和端到端时间，不能只看父上下文缩短或一个子任务耗时。服务失败与缺失 usage 不记成零费用。

**为什么仍默认 Solo。** 小任务的协调和重复验证成本可能超过并发收益。某次少量任务多通过一题，只能作为进一步调查的线索；并不构成默认开启委派的依据。

本地历史：`9edb23b`、`c2d1cd5`、`7a3c06a`、`d6d586b`、`cd626c4`、`f163b50`、`20236d5`、`f812df8`、`856345e`。当前机制见[交互与子任务教程](learning/13-interaction-and-workers.md)。

## 8. 共享预算与部分交付

**问题。** 子任务临近预算时还在探索，额度耗尽后父方只收到失败；给每个子任务一个独立大预算又会让总成本失控。父子同时写同一工作区，也使来源和最终测试难以解释。

**解决。** 父子共享根任务的模型轮次、工具步骤与可选 token 额度，并为父方保留收尾预算。子任务按剩余团队预算分配局部额度，接近边界时进入无工具交付轮；失败、取消也保存明确标注的部分结果。交付在父方下一轮自动送达，已消费结果不重复投递。写 Worker 活跃时，父任务只读，同一工作区同一时刻只有一个写入者。

早期方案曾有固定的子任务步数/轮数上限，后来改成从团队余额分配，避免同样的固定截断对不同任务产生过强限制。不能用历史参数说明当前行为。

**为什么接受部分交付。** 已完成调查也有价值，保留“确认了什么、尚未完成什么”比把全部过程变成空结果更有用；部分结果仍不能伪装成完整验收。

随后把需求责任接到已有 todo：`acceptance` 记录验收，`worker_start.todo_id` 关联分工，子任务交付后需求返回待验收，父方以 `resolution` 记录检查。启动失败不丢需求，未处理项阻止严格完成。这复用了既有状态，不引入第二套项目管理系统。

当前入口：[Worker 管理](../src/aster/core/workers.py)、[任务与状态模型](../src/aster/schema.py)、[交互回归](../tests/test_interaction_workers.py)。本地历史：`376db32`、`8377327`、`8c2afa2`、`a3d3364`。

## 9. 从一次性 Worker 到可继续的子会话

**问题。** 一次性结果不能回答后续问题；重启后子任务上下文难以找到；恢复旧父分支时，如果只加载子任务最新状态，还可能看到未来消息。

**解决。** 子任务拥有独立持久会话，可以查看、取消和沿原上下文补问。TUI 增加 `/agents` 面板，让用户无需修改配置即可显式启动只读调查或审查。父检查点引用固定的子历史位置，恢复到过去不会自动读到未来，也不会自动重放中断工具。

**原因。** 会话复用可以减少无谓的重复交代，但它需要历史隔离与权限重新校验。文件变化通过 `stale_paths` 提醒；有缓存结论不代表结论对当前代码仍然成立。

当时的三组小样本对照中，所有子任务正常交付没有转化成普遍质量提升；并行组即使减少了父方输入，全队 token 与时间仍明显高于 Solo。因此持久子会话作为显式能力保留，自主委派继续默认关闭。

本地历史：`9320db0`、`c12092c`。当前入口：[子任务面板](../src/aster/ui/agent_widgets.py)、[会话检查点](../src/aster/sessions/checkpoint.py)。

## 10. 证据交付、短引用与 any/all 等待

10-01—10-03 的主要问题从“是否有答案”转为“父方能否直接采用答案”。

**证据不足导致重读。** `worker_finish` 让子任务一次提交结论和最多四段已授权读取的源码。Runtime 根据来源 ID、行段和版本取出真实原文，拒绝未读来源、越界行段和过长正文；父方可以据此满足调查观察要求，但编辑前仍要读取目标，最终测试仍由父方执行。

**引用太难使用。** `read_file.source_ref` 提供短引用，在当前子分支授权来源中唯一解析；完整 ID 与哈希仍保存。交付显示真实行号，对不同错误给出可修正反馈。缩短消息本身不构成端到端降本证明。

**第一份结果已到，父方却还在等。** 默认 `any` 在首个新交付就绪时返回。随后观察到父方无独立工作时会反复等待与催促，于是增加显式 `all`：只剩整合就等齐，提前结果能解锁其他工作时继续用 `any`。

**评分器也会错。** 旧评分遗漏合法嵌套函数，附加审计与原评分分开保留。非法最终 JSON、服务认证失败、未知用量和计时缺失都不能删除后重算“成功率”。

**没有默认强制多 Agent。** 十题开发迭代中，最终按需委派方案只在少数回合真正启动子任务。严格整题通过、事实正确数、可解析答案、费用和耗时并未全部同向改善；因此不能把某一指标上涨概括成普遍优势。

当前可复用资产：[十题任务](../datasets/subagent-ten-20261003/README.md)、[子任务执行器](../evaluations/subagents/evaluate.py)、[评分回归](../tests/test_subagent_evaluation.py)。生产变化集中在既有 Worker、Runtime、工具 schema、状态和提示词模块，没有引入多 Agent 服务。

## 11. Token 边界：先证明新机制真的触发

**问题。** 10-04 的候选尝试在子任务 token 耗尽前主动交付。自然委派的一轮对照中，分数有所变化，但全部 team 回合都没有派工，新路径根本没运行。

**决定。** 当轮不采用候选，也不把分数变化归因于它。随后冻结强制派工、受控压力及充足预算条件，分别确认子路径触发与正常路径是否退化。

**后续结果与取舍。** 10-05 的受控续测中，压力组提前交付路径全部触发，严格完成从 0/6 到 4/6，已报告 token 增加约 10.2%。结果支持在这些预算条件下改善交付可靠性，于是采用；它没有证明通用降本，仍有空答案、父预算耗尽与内容错误。

**原因。** “机制触发 → 交付可用 → 任务正确 → 成本可接受”是四个不同层次。先确认代码路径执行，再讨论效果，避免把随机波动、零委派或不同预算混成因果结论。

当前检查集中在 [Worker 回归](../tests/test_interaction_workers.py) 与[用量预算回归](../tests/test_usage_budget.py)。依赖旧运行轨迹生成前缀的历史脚本没有作为公开入口发布。

## 12. 项目记忆：从摘录发展为有来源的知识

**问题。** 只存文件原文难以表达“为什么这样修”“哪些约定以后还有效”。模型也可能把本轮临时要求存成长期规则，或在答案里声称“记住了”却没有真正持久化。

**解决。** 保留摘录，并允许提炼带出处、适用范围和纠正关系的事实与操作经验。来源包括实际读取、真实用户要求和执行结果；保存通过 Runtime 验证。真实失败后测试通过，可以提示一次修复经验提炼，允许无操作；保存回执在实际提交后才展示。

记忆新鲜度与文件版本关联；反馈只作用于本次明确应用的条目。更新、替换、停用和快照保留可检查状态。会话工作记忆与长期项目记忆分开，关闭长期记忆不会顺带删除本轮上下文。

**原因。** 本地 JSON、来源校验和简单检索足够支撑目前规模，暂不引入向量库、知识图谱或自动 Skill 生成。来源真实不保证提炼正确，因此保留范围错误、暂态内容和无关反馈的回归。

当前入口：[Memory](../src/aster/knowledge/memory.py)、[记忆知识回归](../tests/test_memory_knowledge.py)、[记忆教程](learning/10-layered-memory.md)。

## 13. 自动学习与异步整理

**问题。** 完全依赖主 Agent 主动写入会漏掉真实纠正和约定；每次结束都阻塞等待长复盘，又会损害交互延迟，并增加无效调用。

**解决。** 将已结束经历作为待处理材料，后台沿用当前模型进行有界提炼和整理，一批最多三个任务、三项变更。后台只生成候选；提交时在工作区锁内重新核对并原子保存，避免过期候选覆盖新纠正。前台可以继续；一次性 CLI 先输出答案，再给后台最多 15 秒，剩余材料以后继续。

用量包含前台与后台，不能把“回答已经出来”当作总费用结束。自动规则负责停用失效记录，模型整理负责有依据的提炼、合并与替换；更新的是外部记忆，未训练权重。

**原因。** 将耗时工作移出交互关键路径，同时保留候选验证，能复用现有 Runtime、模型和存储。不需要额外的常驻服务或第二个学习系统。

当前入口：[维护队列](../src/aster/knowledge/maintenance.py)、[维护测试](../tests/test_memory_maintenance.py)、[记忆演化教程](learning/11-memory-evolution.md)。

## 14. 降耗：减少无效往返和重复材料

**问题。** 实际费用来自整个工作流的请求次数、输入、输出和后台整理，不能仅看单条消息长度。已经稳定的前缀反复改写还可能丢掉服务端缓存机会。

**解决。** 收敛常见工具使用指引和纠错反馈，减少无效往返；确定重复的记忆材料不重复交给模型整理，保留有变化的新约定。固定规则、任务和确认历史继续排在动态内容之前，没有加入新的分类调用、模型路由或复杂成本调度器。

**为什么这样做。** Aster 已按需加载工具且保留可回读归档，再增加一套裁剪管理工具也会消耗决策轮次。先修可观察的重复工作，比移植依赖隐藏状态、训练决策头或未知供应商价格的方案更合适。

十题历史对照记录的总 token 下降约 39.9%，包含学习、后台整理和后续任务；双方正常完成且通过均为 9/10。新版仍出现一条 CSV 约定遗漏，修复范围处理后单题补查通过，原失败保留。缺失用量、部分请求未完整归档、未知单价意味着不能把该比例称为实际账单降幅，也不能据此保证所有项目同样受益。

当前复用入口：[记忆评测](../evaluations/memory/README.md)、[反馈契约](../tests/test_memory_feedback_contract.py)。本地主要集成提交：`13a4a27`。

## 15. 后训练接口与公开评测的边界

Aster 提供外部策略环境、可追溯 SFT 导出和 GRPO 数据契约：任务来源、许可、划分、请求/回复匹配、assistant mask、版本与预算必须能校验。这样可以在研究策略时继续使用真实运行与评分链。

但这些接口不等于已经实现训练器、tokenizer 对齐、优化器或模型权重更新。项目没有以“接口就绪”代替训练效果，也没有把参与开发的题目重新标成未见测试集。

10-08 的 SWE-bench Verified 十题属于固定子集；原本机原生评分流程与官方 Docker harness 不是同一个环境。公开整理保留任务清单，提供官方数据下载和评分说明；没有上传本机预测与成绩，也不把本地子集实验称为官方榜单成绩。

入口：[后训练设计](post-training-design.md)、[数据来源](../datasets/SOURCES.md)、[SWE-bench 入口](../evaluations/swebench/README.md)。

## 16. 首次公开发布：把本机可用变成 clone 后可验证

**发现的问题。** 根目录 README 堆积逐轮实验结果；Git 历史已包含大量轨迹与压缩包；两个比较器测试直接读取旧报告；教学站点提交了生成页面和源码副本；部分评测驱动绑定个人解释器或私有缓存。

**本次整理。**

1. 首页聚焦安装、配置、常用操作和入口，把本篇作为统一演进文档。
2. 用干净公开分支发布源码，原开发历史与实验留在本地，避免结果通过 Git 父提交上传。
3. 保留运行代码、工程测试、固定评测数据与核心评分代码；比较器用合成输入验证失败、配对和缺失尝试。
4. 子任务评测抽取实际使用的共享代码；跨会话记忆评测使用可配置输出；SWE 采用公开数据与官方评分路径。
5. 教程网站保留源码与构建器，测试时生成页面；凭据、缓存、预测和生成站点由 Git 忽略。
6. 修复评测恢复覆盖失败、未知用量误报降本与跨重启计时的问题，保留最小回归。
7. 在隔离目录安装依赖、运行回归、构建 wheel，并从源码目录之外验证 CLI 和 Runtime。
8. 首次 GitHub CI 暴露 Node/Go 的宿主 PATH 与沙箱 PATH 不一致：宿主能找到缓存里的工具链，实际执行却报找不到命令或无权限。CI 改为显式安装系统工具链；测试使用 Aster 的真实命令环境检测和运行，不再单独注入 Go 路径与环境变量。

工具链修复保留固定 PATH 和原有文件访问边界，并把安装位置写入文档。这样验证的是用户实际运行路径，也避免把缺少语言工具链的跳过结果当作完整验证。

**为什么不直接删文件再 push。** 删除工作树文件不会删除 Git 父提交中的大产物；只改 README 也不能修复隐藏的本地依赖。首次公开应明确区分源码、数据、生成结果和历史证据。

## 仍然沿用的原则

- 一个 Runtime，交互、工具与研究接口共享契约。
- 证据与工作区版本绑定，真实执行和模型自述分开。
- 默认简单：先 Solo，额外能力按需启用。
- 来源、预算、生命周期和失败路径先于更多功能。
- 分开讨论机制触发、任务正确、交互体验与成本。
- 保留不支持预期的结果；未知用量不计零，开发集不冒充独立测试。

本文引用的其他 Agent 思路仅用于设计解释。Aster 是独立实现；外部项目的当前功能或内部机制不能仅凭历史源码推断，设计参考见 [NOTICE.md](../NOTICE.md)。
