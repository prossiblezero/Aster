# Aster 一日优化：自动学习、异步整理与成本核算

方案始于 2026-10-05；2026-10-06 按用户要求将交付窗口缩短为一天。2026-10-07 收尾：代码、机制检查、十题对照与材料同步已完成。以下保留设计目标，实测结果单列。

目标是在一天内完成一轮有实质能力增量的记忆与自进化改造：任务中及时记录，任务后自动提炼，后台批量整理，后续任务按需使用，并由真实执行结果修正经验。先展示研究支持的方案，随后实施；约十道针对性任务做一次对比，最后同步教学文档、网站和简历。一天是交付范围的上限，不是必须等待的时长。

## 结论

本轮交付轻量的自动学习与异步 Dream。现有最多 64 条的项目记忆足以使用本地 JSON；这个规模限制不构成放弃自动提炼和语义整理的理由。LightMem 的批量更新、Codex 的旧会话后台处理，以及 Aster 已有的事件证据和记忆准入，提供了直接可用的设计基础。

采用进程内的有界异步任务，沿用现有模型接口和本地存储。保留默认开启的 Memory、Evolution、Dream，不增加独立服务、模型训练、向量数据库或用户配置步骤。前台执行期间可以处理已经结束的旧经验，写入由拥有工作区锁的 Runtime 在安全边界完成。

最小选项是只修交付、保存反馈和召回三个缺陷；本轮选择更完整的闭环，因为独立于主 Agent 最终回复的经验提取可以直接补救漏存，批量整理也能减少逐条反思和重复记录。新机制是否降低端到端成本，由一次固定对比判断，不把异步本身当作节省 token。

## 找到的睡眠记忆论文

### 最吻合的候选：LightMem

[LightMem: Lightweight and Efficient Memory-Augmented Generation](https://arxiv.org/abs/2510.18866) 已由 [ICLR 2026 官方页面](https://iclr.cc/virtual/2026/poster/10008366)确认收录。预印本首发于 2025-10-21，当前 v4 修订于 2026-02-28；不能因为会议是 2026 年，就称其为 2026 年首次提出。这里标注实际会议与 arXiv 来源，不以“顶会”代替 CCF 分级核验。

阅读范围：v4 的 §3 方法、§5.6 睡眠更新分析与附录流程；另核对版本信息和会议官网。它高度符合用户描述，但没有足够线索确认就是用户当时读过的那篇。

- 感觉记忆先过滤、压缩并按主题分组；短期记忆积累一批相关内容，再提炼成长期条目。批处理减少逐轮提取和更新的调用。
- §3.3 的在线阶段直接插入新条目（soft update），不要求每次写入都先完成复杂的冲突处理。
- 所有条目插入后，或收到更新触发信号后，为旧条目建立候选更新队列。用相似度选择相关内容，并限制较新的内容更新较旧的内容。
- 原文明确说候选队列的相似度检索可以与在线推理并行；不同目标条目的更新队列也可以并行处理。它没有把“睡眠”固定为夜间、整机空闲或必须停止接收用户输入。
- §5.6 指出逐条即时判断可能把相关但不矛盾的信息误判成冲突，误删旧记忆。批量观察的价值包括掌握更多上下文，不只是把工作挪到后台。

可借鉴的是分离记录与整理、聚合相关变化、控制处理范围。LightMem 使用的压缩模型、embedding 与完整存储流程不直接移植到 Aster；论文报告的 token 降幅也不能作为 Aster 的预期结果。并行主要改变延迟，token 成本下降仍须来自少处理重复内容、少调用模型和后续任务少做重复工作。

### 补充阅读：更新操作与时间条件

[TrustMem](https://arxiv.org/abs/2606.25161)（2026 年 arXiv 预印本）的 §3.1–3.2 将记忆维护拆成 Write、Revise、Prune，由冻结模型检查覆盖、保留和忠实程度，再将结果用于训练奖励。Aster 借鉴有限的局部操作和提交前核对，但没有实现其语义裁判或强化学习，不能将“来源存在”写成“知识一定正确”。

[Memory Consolidation Flattens the Temporal Shape of User Facts](https://arxiv.org/abs/2609.36457)（2026 年 arXiv 预印本）指出，有时间戳仍可能丢失“暂时”“当前”等时间条件；要求保留这些条件的提示在不同条件下并不一致有效。Aster 因而保留正文条件、`when`、来源时间和旧条目关系，不把摘要更短当作质量更好。它仍会依赖模型理解这些条件，未实现通用时间推理器。

另直接阅读 [LightMem 源码 8449d574](https://github.com/zjunlp/LightMem/blob/8449d574df6bae1bdf3314a1564da65e2f37e046/src/lightmem/memory/lightmem.py) 中 `construct_update_queue_all_entries`、`update_entry` 和批量更新路径，以及 memory manager 的结构化操作：按时间筛选候选，线程池生成，写锁提交。Aster 吸收批量提议与提交分离，使用现有词面检索，不复制 embedding 或线程池数据库层。此次重新核对的网页和源码哈希见[来源记录](../evaluations/memory-sleep-20261005/research-sources.json)。

## 改造前的能力与缺口

本轮基线的 `config.py` 中 `memory_enabled`、`memory_evolution`、`auto_dream` 都是 `True`。已有文件摘录、事实/方法提炼、来源认证、适用条件、用户纠正、使用反馈、快照及回滚。相同内容的记录已有去重，不能把这些重新包装为本轮新增。

`Memory.dream()` 在完成或停止时执行，检查来源变化、反证、重复失败等并停用条目，不调用模型，不会重新归纳多次任务。`Runtime._operation()` 在工作区锁内重载 JSON 记忆；当前存储通过整份状态原子写入。直接加入第二个后台写入者，即使每次写文件是原子的，也可能用旧状态覆盖新记忆。

现有证据支持的缺陷修复：

1. **主任务交付。** 受控预算任务中，父任务收到子任务报告后继续读取，下一次请求超过预算，最终没有回复。目前提前交接只覆盖子任务。见[原始报告](../evaluations/subagent-budget-controlled-20261004/REPORT.md)。
2. **真实保存。** 十题轨迹中的金额规则、重试规则学习会话出现“已记住/已记录”而没有记忆写入。修复经验题还出现多次写入拒绝和预算消耗；其中来源准入和错误提示已经修正，本轮不能重复算作新功能。见[原始报告](../evaluations/memory-knowledge-20261005/REPORT.md)。
3. **检索输入。** `_memory_text()` 会将最后一条 `role=user` 的内容加入查询，但内部恢复、反思提示也使用该角色。应只用任务请求和真实用户继续消息，避免内部提示改变记忆排序。这是基线源码确认的问题；本轮已修正，未单独消融其效果。

这里的“自进化”指经验改变后续任务的行为，并能根据使用结果修订或停用；不声称模型权重更新，也不把已有事实/方法类型和来源认证当作新增功能。

主任务预算收尾沿用现有请求估算和团队账本，给最终回答留出一次调用。满足完成条件才标为完成，否则交付已做工作与剩余事项，保留部分完成/停止状态。保存反馈使用真实工具或维护提交事件，不能在后台尚未完成时声称“已沉淀”。

其他研究也支持这个取舍：[BAGEN](https://arxiv.org/abs/2606.00198)显示预算预测会有成功率代价，且其回放实验未计在线预测成本；[An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804)中可回读归档并未自动带来收益，支持先处理已观察到的交付问题；[ERRAND](https://arxiv.org/abs/2609.29545)强调维护也占任务预算，其脚本化环境结果不直接代表真实编码收益。以上按 arXiv 预印本引用。

## 自动学习与异步 Dream 的设计

### 输入与处理方式

从真实用户消息、记忆操作以及执行失败/通过事件构造小型经历快照，记录任务 ID 和证据 ID。只处理已经结束、未处理过的片段；修复方法必须能引用相关失败和后续验证，不能把不相关的通过当作修复证明。来源始终可从现有 trace 核对，不把整段对话追加进每次模型请求。

及时记录仍使用现有记忆工具，用户明确纠正不等后台。后台提取与整理合并为一次调用：提供新增经历及相关旧条目，让模型输出至多三项结构化操作（新增、合并/替换、停用或无操作）。同批处理重复内容和冲突，避免先提取一遍、再让另一个 Agent 重新读完整历史。后台模型没有代码编辑、Shell 或任意文件写入工具。

不建立完整知识图。沿用 `fact/procedure/excerpt`、`when` 和来源引用；合并时保留原条目关系与各来源任务 ID。替换显式用户约定必须引用时间更晚的真实用户消息；提示要求其中确有纠正含义。程序认证来源与先后顺序，不能证明任何晚来的消息都构成语义上的纠正。保留日期、版本、适用范围和失败条件，不把“在条件 A 下有效”压缩成无条件规则。

### “睡眠期”与并发

“睡眠”是低优先级记忆维护，而不是整个 Agent 的互斥运行状态。任务结束时登记新增材料并尝试调度；应用再次启动或进入新的任务边界时处理遗留材料。已有后台任务时只积累输入，不再启动第二个。

```text
真实交互/执行证据 ──> 固定经历快照 ──> 一次后台提炼与整理
                            │                    │
前台 Runtime ──> 正常执行下一任务       结构化修改候选
     │                                           │
     └──── 工具批次/任务边界：核对、提交 <─────────┘
                         │
                 项目记忆与真实保存回执
```

后台读取快照并生成候选。提交时，Runtime 在现有工作区锁内重载记忆，检查整份记忆的内容版本，再检查证据和替换关系；检索和使用计数增加不算内容冲突。最多 64 条时采用整批作废，未实现逐条变更重放：即使无关条目的正文发生变化，这批旧候选也会被丢弃。这牺牲部分提炼机会，换取更简单的并发更新逻辑。期间被用户纠正、丢弃或来源变化的条目不接受旧候选覆盖。一个专用文件锁防止多个会话重复启动同一工作区的维护调用，前台不等待这个计算锁。

变更通过准入后一次原子提交：先保留快照，再增加新条目并停用被替换条目；全部失败则保持原记忆。停用表示不再自动召回，原始证据继续存在。原有规则 Dream 保留为无需模型的检查步骤。

### 开箱即用与退出行为

三个现有记忆开关继续默认开启；显式关闭依然生效。交互界面先交付任务答案，后台整理完成再显示学习结果，例如“已记录：金额计算使用 Decimal；适用于支付与退款”。没有实际提交时，只能显示正在整理、已跳过或未保存。

交互程序退出时取消未完成调用，保留待处理材料和已生成候选；下一次启动可以继续。单次 CLI 命令不在退出后留下进程：先输出任务答案，再给维护最多 15 秒的收尾时间，超时材料留待下一次使用。这个时间计入命令总耗时，不能隐藏在“后台”一词里。CLI、TUI 和测试共用同一维护接口。

### 成本和规模

初始实现每批最多处理三个已结束片段；完整请求的本地输入估算上限 4,096 tokens、输出上限 768 tokens，每批一次模型调用，维护调用不自动重试。沿用当前配置的模型与账户，不要求另配便宜模型。启动前在现有任务预算中预留额度；余额不足则延期，主任务交付优先。

通过来源事件引用和处理状态跳过已完成的同一片段；拒绝的同一批候选不立即重复请求。相关条目的筛选沿用现有词面检索，默认最多注入三条有效记忆。固定上限是本轮初始策略，不作参数搜索，也不宣称已经找到最优值。

后台使用独立的请求记录和 usage 项，与前台用量一起计入总成本；重试、失败和取消的已知消耗也计入，供应商未返回 usage 时明确标记缺失。维护 API 失败只影响这批整理，不改变任务交付结果。存储变为十倍规模时仍按固定批次处理，不全量回读会话。

关键假设是这一次有界整理能减少漏存与重复经验，并让后续任务少走弯路。如果收益不足以抵消维护成本，固定对照会显示出来；届时报告真实取舍，不靠增加评测轮次挑出好看数字。

## 文件、兼容性与回退

本轮改动十一个生产文件：`knowledge/memory.py`、新增的 `knowledge/maintenance.py`、`core/runtime.py`、`context/prompt.py`、`schema.py`、`providers/client.py`、`sessions/lifecycle.py`、`sessions/navigation.py`、`cli.py`、`ui/app.py`、`ui/commands.py`，另有对应测试与教学文档。模型客户端只补充内部调用的重试上限控制；仅增加一个承担提炼、调度和候选校验的内部模块，不增加服务或第三方依赖。

保留 `state.json` 和现有工具接口。给跨会话引用补充可选任务 ID，旧条目按已有来源读取；待处理位置、候选与维护锁放在现有 `.aster/memory` 目录，沿用脱敏和文件边界检查。新增字段不要求重写旧记忆。仍通过已有 `/memory` 查看记忆，在同一入口补充生效/停用状态、来源与最近一次整理结果，不另造配置向导。

回退时停止维护任务并撤销调度接入，旧条目仍可由原代码读取；已提交整理可通过已有快照回滚。自动生成 skills、模型微调、自主修改 Aster 源码、多项目共享记忆和重型图检索不在本轮范围。

## 十题验证与目标指标

十道模型任务预先固定，覆盖报表时区、金额、两次补充 CSV 约定、用户更正、三文档归纳、来源过期、支付修复迁移、测试命令迁移、不同适用范围和预算受限交付。每题包含明确的临时材料，学习提示不要求“记住”，后续使用采用新会话。并发整理、整理途中纠正、退出恢复与原子提交使用真实 Runtime 加确定性模型输出的机制检查；它们不混入模型成功率。具体条件见[运行前协议](../evaluations/memory-sleep-20261005/PROTOCOL.md)。

每题每版本一次，同模型、相同任务预算和初始仓库，两组现有记忆开关均开启。另用小型机制测试覆盖 API 失败、坏格式、无新材料零调用、写入失败和取消；不再为每个边界启动一批模型评测。

预设优化目标为任务完成至少 8/10 且不低于本轮当前版、后续任务 token 比本轮当前版降低至少 10%、包含后台维护的总 token 不增加。它们是目标，不是承诺或已有成绩；不以部分交付冒充任务完成。

结果同时列出任务完成率、学习/后续任务/总 token、工具调用、前台响应与维护耗时。自定义指标为“经验迁移成功率”“每条有效经验的写入成本”“实际保存回执准确率”，注明任务范围和分母；后台覆盖较新的用户纠正、无新材料仍发模型请求属于机制缺陷，必须修复。

保留旧十题的冻结结果，新版本另记。文档和网站讲解实际实现与一条完整运行案例；简历写实测改进和可解释的技术贡献，技术栈继续使用用户能理解的名称，不用“严格”“复用”等措辞。

## 交付结果

自动提炼、异步候选生成与边界提交、来源和版本检查、实际保存回执、取消恢复、父任务预算收尾以及后台用量入账已实现。三个现有开关继续默认开启，新增一个维护模块，没有新增运行依赖。完整工程检查为 1,170 项通过、4 项因缺少 Go 跳过；末轮历史账本修正另通过 36 项相关回归，网站 25 项检查通过。

[一次固定十题对照](../evaluations/memory-sleep-20261005/REPORT.md)中，正常完成且通过验收为 4/10 → 7/10，功能通过为 4/10 → 9/10，约束满足为 13/30 → 27/30；14/14 保存回执可对应真实条目。新版后续任务均有最终答复，两个仅部分完成，不算成功。

预设的 8/10 完成率和降耗目标未达到：已报告总 token +12.6%、后续 +20.0%，两组有缺失用量，基线有更多服务失败，不能将差异全部归因于记忆。金额题漏填适用范围导致的保存失败保留，最终只补查该修复一次，成功保存；不把补查改写为新的十题成绩。

本轮值得保留的是无需用户提醒的自动补存、可核查的修复经验和可靠交付状态；整体降耗尚未得到这组数据支持。简历中的早期 11.7% 降耗仍归属前期知识版本，新增后台机制单独描述。
