# 脚本动作（script）设计说明

状态：待用户确认后实现。目标是一个与具体模型无关的 harness 设计：任何模型都可以选择使用，也可以继续只用原有的结构化工具。

## 1. 为什么做

做完“证据与模型视图分离”以后，fresh30b 上（去掉供应商报错题和离群题，按题比较）和 pi 的差距结构如下：

| | Aster v15 | pi |
| --- | ---: | ---: |
| 请求次数 | 207.5 | 194 |
| 每请求输入 | 16.0k | 13.7k |
| 成本 | 1.50 | 1.33 |

剩下的差距来自两处：回合数和每回合携带的上下文。脚本动作可以同时作用于这两处：

- **一次请求做完一串操作**：例如读三个文件、搜索、修改、跑测试，原来要跨好几个回合，现在可以在一个回合里完成，循环和条件判断都写在脚本里。
- **中间结果不进上下文**：工具返回的内容先留在脚本内存里，只有脚本主动打印的部分才会进入模型上下文。例如跑完测试只打印失败的用例，搜索全仓只打印命中计数。

依据：

- CodeAct（Wang 等，ICML 2024）在 17 个模型上比较了“用代码组织动作”和“JSON 工具调用”，代码动作的成功率最高提升 20%，交互轮数也更少，开源模型大多同样受益。
- Codex 的执行工具也是这种思路：在 fresh30b 的数据里，它平均每个请求执行 2.9 条命令，pi 是 1.9 条，Aster 只有 1.0 条。

## 2. 接口

新增一个工具 `script`，只有一个参数 `code`（Python 源码）。脚本里可以调用以下函数，每个函数对应一个现有工具：

| 函数 | 对应工具 | 返回 |
| --- | --- | --- |
| `read(path, start=1, end=200)` | read_file | 文件原文（不带行号） |
| `search(pattern, path=".", regex=False, context=0, limit=100)` | search | 与 search 工具相同的分组文本 |
| `ls(path=".", limit=200)` | list_files | 路径列表文本 |
| `write(path, content)` | write_file | None |
| `patch(path, old, new)` 或 `patch(path, edits=[(old, new), ...])` | patch_file | 修改后的片段预览 |
| `sh(command, timeout=30)` | run_shell | 结果对象，含 `.ok`、`.exit_code`、`.output`；非零退出码不抛异常 |
| `test(command="pytest -q", code="", timeout=120)` | run_tests | 结果对象，含 `.ok`、`.output`、`.failed`（失败用例列表） |
| `diff()` | git_diff | 改动文本 |

- 工具被拒绝或出错时，函数抛出 `ToolError`。消息里写明工具、原因和简短内容，脚本可以捕获后换个做法。
- `print()` 的输出就是脚本返回给模型的内容。

工具描述大约 150 个 token。系统提示里只加一句：需要连续调用多个工具或根据结果做判断时，用 `script`，并且只打印需要看的内容。

## 3. 执行与安全边界

脚本的设计原则是：**脚本只负责控制流程，所有副作用都必须经过工具。**

1. **脚本本身在一个更严的沙箱里运行**：沿用现有的 Landlock/seccomp 启动器，但根目录是一个空的临时目录，看不到工作区，也没有网络。Python 标准库照常可用（解释器目录只读）。另有 CPU 时间、内存和总时长上限。
2. **工具调用通过管道回到 harness**：脚本进程和 harness 之间用两根继承下来的管道通信（seccomp 禁用了 socket，所以只能用管道）。每次函数调用发出一条请求，然后阻塞等待结果。
3. **每次调用都走现有的同一个入口 `Runtime._step`**，所有已有的规则因此原样生效：
   - 先读后改；
   - 权限和审批（ask 模式下逐个征求同意）；
   - 只读和计划模式的限制；
   - 预算计数（每次内部调用都计一个工具步骤）；
   - 证据记录；
   - 正式验证及其状态更新；
   - 不确定副作用防重放的在途标记，每次内部调用单独标记。
4. **脚本层面的上限**：每个脚本最多 40 次内部调用，总时长最多 300 秒。超出时脚本中止，已经完成的调用照常保留。
5. **暂不开放给脚本的工具**：worker 相关工具、`tool_load`、记忆工具、`service_start`。脚本里也不能再调用 `script`。

## 4. 模型看到什么，系统记录什么

- **历史里只有一次 `script` 调用和它的输出**：打印内容，加一行页脚，例如 `[script: 5 calls — read_file×3, patch_file×1, run_tests×1 passed]`。抛出未捕获的异常时，附上回溯的最后几行，并注明已执行的调用。
- **打印内容的大小限制和归档**：沿用 `run_shell` 的规则。
- **证据记录里每个内部调用单独成条**：调用编号为 `<脚本调用编号>#<序号>`，审计和回放都能看到完整过程。
- **对训练的影响**：
  - 一个动作对应一段代码，SFT 和 RL 的样本仍然是“一次决策、一段输出”；
  - 在 Qwen 的 XML 参数格式里，代码是按原文传递的，不经过 JSON 转义，这是 Qwen3.5 原生格式的优势。

## 5. 评测与判定标准（事先写死）

在 old20 和 fresh30b 上，用两个模型（gpt-5.6-luna 走 Responses 接口，deepseek-v4-1-flash 走 Chat Completions 接口），分别对比 v15 和加入脚本动作的版本。

判定为有效，需要两个模型上同时满足：

- 请求次数降低 15% 以上；
- 成本降低 10% 以上；
- 通过数下降不超过“每 30 题平均 1 道”。

另外统计两项诊断指标：

- **采用率**：含脚本的回合占总回合的比例。如果模型几乎不用，说明接口或描述有问题，而不是思路本身有问题。
- **脚本失败率**：抛出未捕获异常的脚本所占比例。

有任意一个模型明显变差，就不默认开启，改为通过配置项手动开启。

## 6. 分阶段实施（每阶段一个提交加一个标签，回滚方式为 `git switch -c rollback-sN <上一阶段标签>`）

| 阶段 | 内容 | 必须通过的测试 |
| --- | --- | --- |
| S1 | 脚本沙箱和管道通信，只开放只读函数（read、search、ls） | 脚本直接打开工作区文件会失败；不能联网；不能在临时目录之外写文件；CPU 和时间限制生效；打印输出原样返回 |
| S2 | 开放有副作用的函数（write、patch、sh、test、diff），全部经过 `_step` | 先读后改仍然生效；审批被拒时抛出 `ToolError`；内部测试会更新验证状态；预算按内部调用计数；内部调用进行中崩溃时，恢复后不会重放 |
| S3 | 工具描述、系统提示一句话、模型视图页脚；两个模型各跑几道题做冒烟 | 全量回归通过；小窗口预算测试通过 |
| S4 | 按第 5 节评测，决定默认开启、需配置开启还是撤回 | — |

## 7. 风险

1. **模型不用或用不好**：工具描述太长会增加每个请求的成本，太短模型又不会用。所以 S3 先冒烟，看采用率。
2. **脚本出错浪费回合**：通过清楚的报错信息（`ToolError` 带原因）和回溯末尾来减轻。
3. **崩溃恢复的粒度变细**：一个脚本里有多个副作用。每个内部调用单独打在途标记，恢复时按现有规则拒绝重放不确定的调用。
4. **安全**：脚本沙箱比 `run_shell` 更严（看不到工作区，也没有网络），副作用只能通过工具产生，所以不会扩大攻击面。S1 的测试专门验证这一点。
