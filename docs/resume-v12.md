本文是给作者本人准备的面试材料，所有数字都能追溯到 [评测报告](../evaluations/harness-v12-20261017/REPORT.md)、[v12 设计说明](harness-v12.md) 和 [v13 设计说明](harness-v13.md)。

## 简历条目（可直接使用）

> **Agent Harness 性能、可靠性与评测方法。** 通过分阶段计时和容器内复现，发现 63% 的任务耗时花在 harness 自身的检查点和日志写入上。容器 overlayfs 上单次 fsync 需要 88–225 ms，另外还有全仓重哈希、全量重写和 O(n²) 的日志追加。为此实现了：增量工作区快照（仿 git index 的 stat 缓存加 racy 窗口）、按内容寻址的任务基线、O(1) 追加的 trace、checkpoint 组提交（断电最多丢失 5 秒进度）和 SQLite WAL 调优。单步 harness 开销降低 6.7–13 倍，真实评测中模型之外的耗时下降 81%。修复沙箱绝对路径、断网测试误判、Jest 无法正式验证等执行环境问题。由运行时在原始代码上复跑测试并比对失败签名，以此判断既有失败，追逐这类失败的轮次减少 47%。通过精简系统提示词做消融，请求数降到历史最低。构建留出评测集和隔离判分网络，排除了判分环境漂移（24/24 历史结果复现）。在 30 道留出题上，独立通过与正常交付均与 pi 持平（23/30），高于 Codex（21/30），成本较优化前降低 57%。

加上 v13 后推荐的版本（突出评测方法，数字更经得起追问）：

> **Coding Agent harness 优化与防过拟合评测。**
> - **定位瓶颈**：用分阶段计时发现 63% 的任务时间花在 harness 自身上，根因是容器 overlayfs 上每次 fsync 88–225 ms、每步全仓重哈希、O(n²) 日志追加。
> - **降开销**：实现增量快照（仿 git index 的 stat 缓存加 racy 窗口）、按内容寻址的基线、checkpoint 组提交，单步开销降低 6.7–13 倍，模型之外的耗时下降 81%。在 CI 中加入按计数（而非计时）的开销预算测试，防止回退。
> - **补执行能力**：跨工具调用存活的沙箱服务，按退出码判定的构建加测试命令。
> - **评测可信度**：搭建隔离判分网络，修复了判分环境漂移，24/24 份历史结果复现。在任何候选版本评测之前，先冻结一套新抽的 30 题留出集；同日把自研 Agent 两个版本（各两次）与 pi、Codex 按题配对，用 bootstrap 给出置信区间。
> - **结论**：v12 与 pi 通过率持平（配对差 0，95% CI [−2, +2.5]）。v13 在开发集上从 14/20 提升到 16/20，但在留出集上没有显著提升（−1 [−3, +1]）。据此没有夸大结论，并从留出轨迹中定位到一个新引入的门禁缺陷。

更短的版本：

> 优化自研 Coding Agent 的 harness：用分阶段计时定位 63% 的非模型耗时，通过增量快照、内容寻址基线和 checkpoint 组提交，把单步开销降低 6.7–13 倍；建立留出集和隔离判分网络保证评测可信；在 30 道留出题上通过率与 pi 持平、高于 Codex，成本较优化前降低 57%。

## 面试官可能问的问题

**1. 为什么花在模型之外的时间这么多，你是怎么发现的？**

网关会记录每次模型请求的耗时，用任务总耗时减掉它，就得到 harness 自身的时间：v11 为 3,663 秒，pi 只有 174 秒。接着在运行时里加了分阶段计时，写到 `timings.json`，结果显示 checkpoint 平均每次 1,078 ms、每个请求调用 4 次，比所有工具执行加起来还多。最后在任务容器里用脚本化模型复现，cProfile 显示每次 fsync 要 125 ms，而宿主机上只要 1.4 ms。

**2. 增量快照怎么保证不漏检文件变化？**

用 `(mode, size, mtime_ns, ctime_ns, inode, dev)` 作为文件身份，身份没变就复用上一次的哈希。ctime 无法被用户态伪造，同尺寸重写、恢复 mtime 都会被发现。修改时间落在 3 秒内的文件不进缓存，每次重新哈希，这是 git 处理 racy 问题的同一个思路。对应的测试覆盖了同尺寸改写加恢复 mtime、权限变化等情况。

**3. 组提交会不会丢数据？**

进程崩溃不会丢：原子 rename 保证文件要么是旧版本要么是新版本，SQLite WAL 在 NORMAL 模式下进程崩溃也不丢事务。只有断电时可能丢失最近 5 秒的 checkpoint。工具执行前写入的 in-flight 标记、操作账本和记忆仍然每次 fsync，因为它们用来防止不确定的副作用被重放，必须持久化。

**4. 留出集是怎么保证没被污染的？**

new30 在开发中从未使用。第一天只跑了一次 rc1；它暴露出 Jest 的问题，修复后不回头重跑来冲分。所有调整都在 old20 上完成，最终版只在 new30 上确认一次，确认后没有再改任何东西。

**5. 判分环境漂移是什么，怎么证明你的修复没有偏向自己？**

requests 的超时测试依赖 `10.255.255.1` 是一个黑洞地址，而当天主机网络会应答它，导致连官方参考补丁也过不了。修复办法是把判分容器放到子网 `10.255.255.0/24` 的网桥上，容器地址取自 `.128/25`，于是 `.1` 是链路内没有主机的地址，连接必然超时。用这个环境复判 pi、Codex 和优化前 Aster 的 24 个历史补丁，结果与历史判分完全一致。

**6. 既有失败为什么不直接豁免？**

第一版就是“在原始代码上同样失败就放行”，结果被现有测试否决：如果某个已有测试本来就失败、恰恰是任务要修的 bug，它会不经修复就被放过。最终方案分两步：先把证据告诉模型（“改动没有影响它；如果它就是要修的行为，说明还没修好”），到最终交付时，只有在 Agent 改过代码、被门禁提示过至少一次、并且在当前代码上仍然完全相同地失败时，才不再阻塞。

**7. 精简提示词为什么能减少轮次，会不会伤质量？**

提示词是针对开发集失败一条条累积起来的“多检查一点”规则，在开发集上属于过拟合。同一个模型，在所有 Agent 都能通过的 10 道题上，Aster 用 155–169 个请求，而 pi 只用 113 个。消融后请求数降到 Aster 历史最低，低于此前 6 次运行范围两个标准差以上；通过题集合与上一版完全相同；留出集上质量仍与 pi 持平。

**8. 还有什么没做好？**

- 成本仍是 pi 的 1.43 倍、Codex 的 1.23 倍（new30）。在 fresh30 上去掉离群题后，约为 pi 的 1.6 倍、Codex 的 1.4 倍，差距来自请求数（多 30%–50%，按题配对显著）。
- v13 在 BigCodeBench 上连续低于 v12（new30 和 fresh30 方向一致，但单看任一数据集都不显著），还没有找到 harness 层面的原因。
- 单次 20 题运行的单题波动可达 ±30 轮，±10% 的效果需要多次重复运行才能确认。
- 工具反馈类改动（编辑回显、搜索上下文）没有测出收益。

## v13 相关的追问

**9. 开发集上提升了，留出集上没有，说明什么？**

说明开发集上的提升有一部分是噪声，或者只对开发集有效。old20 从 14 到 16，单次 20 题运行的波动本来就有 ±2。正因为预料到这种情况，才在评测任何 v13 版本之前先冻结了 fresh30，并规定在留出集上只看、不改。结果 v13 相对 v12 是 −1 [−3, +1]，于是如实写成“没有显著提升”。v13 真正的收益是新能力（常驻服务、构建类项目的正式验证）和工程化，没有拿通过率来包装。

**10. 置信区间怎么算的？为什么要配对？**

以题为单位：同一题上两个 Agent 的结果相减（重复运行先取平均），对 30 道题的差值做 10,000 次有放回重抽样，取 2.5% 和 97.5% 分位。题目难度差异远大于 Agent 之间的差异，配对能把难度这个因素消掉，区间比分别估计再相减窄得多。

**11. 为什么 pi 的成本区间那么宽？**

pi 在一道数据库恢复题上输出了 13 万 token，单题花了 1.65 美元，其余 29 题合计只有 1.69 美元。均值对这样的离群值很敏感，所以报告里同时给出去掉这道题之后的成本。面试中可以借这个例子说明：报告 Agent 成本时，只看均值是不够的。

**12. 留出集上发现的缺陷为什么不修完再跑一次？**

修是修了（v13.1），但这样做等于看了答案再改卷子。修复后的版本只在开发集上验证，fresh30 上的数字保留 v13-rc3 的。如果要再声明留出成绩，需要重新抽一套题。

**13. 这个缺陷具体是什么？**

v13 让 `make test`、g++ 编译加运行这类命令按退出码进入正式验证。失败原来按命令字符串记录，要求同一条命令重新通过才能消除。但退出码证据没有“用例”这个身份：命令因为调用方式出错而失败（例如把链接输出写到不可写的 `/tmp`），和测试真的失败，看起来一模一样，而且这条命令再跑多少次都会失败，任务就卡在完成门禁上。修法是：退出码失败只把验证状态置为失败，不记成必须消除的义务；逐用例失败仍然必须让同一个用例重新通过。

**14. 你否决过自己的什么方案？**

“最新结果覆盖”：让后一次内联测试或命令的结果覆盖之前的失败。它被 3 个已有测试否决，因为模型可以写一个必然通过的检查，把真实的失败清掉。这条原则（同一个检查重新通过才能消除失败）与问题 13 的修法不冲突，前提是失败有明确的身份。

## v14 补充（2026-10-18）

**可以加进简历的一句：**

> 用逐轮对比定位到与 pi、Codex 相比多出的请求主要来自收尾阶段：门禁驳回、测试环境与 shell 不一致、重复验证。修复了沙箱副本中可编辑安装项目的导入失败（Landlock 只读暴露原工作区，并由运行时守护 chmod 这类 Landlock 不拦截的元数据修改），并在新抽的第二套留出集上验证：质量与 pi 持平（25/30），仓库题请求减少 16%。同时为 Qwen3.5 的 SFT/RL 实现了 token 级 rollout：原生 chat template、hermes 与 XML 两种工具调用解析、逐回合 token id、logprob 和 loss mask、按上下文改写切段，基础设施失败不进梯度。

**新的追问：**

**15. 为什么又抽了一套留出集？**

v14 的问题是从 fresh30 的轨迹里分析出来的。再用 fresh30 证明提升，等于看了答案再改卷子。所以动手之前先冻结了 fresh30b。之后发现的 S3 缺陷修了，但不再用 fresh30b 的成绩去声明它的效果。

**16. 沙箱为什么要只读暴露原工作区？安全吗？**

SWE-bench 的仓库都以可编辑模式安装，`.pth` 文件指向工作区的绝对路径。测试在副本中运行，读不到原路径，导致 matplotlib 的命名空间包加载失败，进而触发 DeprecationWarning，又被项目配置提升为错误。安全上有两点：

- 只有当整个工作区（包括被忽略的文件和 .git）中没有敏感文件名、`.git/config` 里也没有带凭据的 URL 时才暴露；
- Landlock 不拦截 chmod 和 utime，所以运行时在每条命令前后对比原工作区的文件权限，有变化就恢复并报告。

**17. token-in-token-out 为什么重要？你怎么保证？**

重新分词会让训练用的 token 与采样时不一致，重要性采样会因此失真。保证方式：

- 用策略自己的 chat template 渲染 prompt，以 token id 送去 vLLM，生成结果按 `token_id:N` 读回；
- 每个回合单独作为样本时一定准确；
- 下一个 prompt 不是“上一个 prompt 加 completion”的严格延长时（模板删掉 `<think>`、上下文被压缩等），自动开始新的一段。

**18. v14 有什么没做好？**

- 总请求数在留出集上没有显著下降，去掉一道离群题后约少 8%；
- 单次运行不做记忆整理的修复第一版没生效，是在留出数据里查出来的；
- 训练部分还没有在 GPU 上跑过。

## v15 补充（2026-10-19）

**简历可以加的一条：**

> 将 harness 内部的证据记录与模型看到的视图分离：完整的结构化记录仍用于审计、恢复和训练，模型只看渲染后的纯文本（状态行、原文、必要的游标），搜索结果按文件分组，并精简了工具定义。在 GPT 与 DeepSeek 两个模型家族、两套题上按题配对验证：每请求输入降低 9.8%（95% 置信区间 [−14.2%, −5.1%]），通过率不变；用消融实验排除了“新视图伤害 BigCodeBench”的假象。补齐了输出截断恢复、Chat 协议工具名解析、失败签名临时路径归一化等鲁棒性问题。

**新的追问：**

**19. 为什么要把“证据”和“模型视图”分开？**

harness 需要完整记录（状态、证据编号、归档引用、字节数）来做审计、崩溃恢复、上下文预算和训练数据导出；模型做决策只需要内容本身和少数要引用的游标。原来把内部记录原样塞给模型，每条结果外面套着约 111 个 token 的 JSON 外壳（pi 只有 2 个），代码和测试输出还要逐行转义，而且之后的每个请求都要重复携带。分离后，历史里照样存完整记录，只在组装请求时渲染；渲染是确定性的，供应商的前缀缓存不受影响。

**20. 你怎么证明改动对任何模型都有效，而不是在迎合 GPT？**

接入了第二个模型家族：DeepSeek，走 Chat Completions 接口，和本地开源模型同一条路。每项改动都在两个模型、两套题上同时间段成对运行，按题配对后合并做 bootstrap。只看一个模型时，我曾两次被假象误导：一次是第三方 DeepSeek 端点的报错，一次是单次运行的波动。

**21. BigCodeBench 一度变差，你是怎么排查的？**

做消融：在 20 道 BigCodeBench 题上，对比 v14.2、v15、“v15 但工具结果改回 JSON”、“v15 但状态提示改回 JSON”四个变体，DeepSeek 每题跑 3 次，GPT 每题跑 2 次。结果四个变体之间没有显著差异，说明下降来自供应商报错和单次波动。排查过程中还找到并修了两个真实缺陷：空结果被渲染成 `[done]`；Chat 历史里工具名解析不到。

**22. 每请求输入显著下降，总成本却不显著，怎么解释？**

成本等于请求数乘以每请求成本。每请求输入是 harness 能直接控制的，下降 9.8% 且区间不跨 0。请求数则由少数长任务和模型的解题路线决定，波动远大于这个节省。有一个反直觉的现象：v14.2 在 DeepSeek 上因为输出截断直接崩溃，请求数反而“少”，因为它失败得早。所以评测时要区分“便宜的失败”和“真实的节省”，也要优先使用离线可计算、波动小的指标。

**23. 输出截断恢复为什么要设上限？**

DeepSeek 思考模式有时会把 8,192 个输出 token 全用在推理上，什么动作都没给出。被截断的内容不能执行，也不进入历史；系统追加一句提示后再请求一次。每次截断都是一整份输出预算的钱，模型如果陷进去会一直烧钱，所以每次运行最多恢复 2 次。数据上：v14.2 有 4 道题因此直接终止；v15 恢复成功了 1 道，另外 2 道在任务末尾连续截断 3 次，用满上限。
