# 上下文改进调研：先采用确定性管理

2026-09-16。本文是调研与建议，尚未修改生产代码。对应现状为 v5 专项评测；原始成绩保留，不能把建议中的能力写成已经实现。

## 结论

先优化规则裁剪、工具结果归档回读和结构化状态，不增加额外 LLM 总结器。保留 Runtime、权限边界、单一 RunState、工作记忆、调用与结果配对、现有 token 计量和 checkpoint；重构范围集中在上下文构建与观察存取，不推倒整个 Harness。

单纯调大预算最省事，也能缓解部分失败，但无法解决一次性证据被删除或长输出无法回读。因此本次建议改善信息组织，同时保留正常默认预算；3,584 tokens 是压力条件，不能承诺所有工具协议、用户要求和模型行动都能被塞进去。

## 已确认的问题与边界

- 原策略会修改活动历史并删除旧交互，缺少供模型回读历史观察的入口。执行记录存在不等于模型能够查回它。
- 每条工具正文限制为 1,600 tokens，不代表一个并行批次能放进全局剩余空间；最新完整批次又不能被整组删除，因此可能停止。
- 工作记忆主要取工具正文前 500 个字符，不是语义摘要；测试是否通过等已有结构化状态，没有作为紧凑的核心任务状态统一呈现。
- “代码通过隐藏测试但未正常收尾”不能一概归因于裁剪。部分失败的实际请求仍保留公开测试成功证据；新设计也不能保证模型看到状态后就一定正确结束。
- `AsterEnv._observation()` 返回结构化状态，正常模型路径在 `Runtime._turn()` 构建 prompt。目前二者不是同一个最终模型输入，需要在后训练接入时统一。

## 推荐的最小设计

```text
成功工具结果、文件变化、验证结果
                ↓
   现有 RunState + 有来源的观察归档
                ↓
      共用的确定性上下文构建
      ├─ 当前请求、用户约束、权限
      ├─ 任务／修改／验证状态
      ├─ 最近完整工具交互
      └─ 旧观察预览与回读引用
                ↓
       正常模型调用 / RL 策略输入
```

### 1. 用已有状态生成短记录

从 RunState 渲染当前目标、未完成待办、实际修改路径、验证状态、测试命令、对应工作区指纹、未解决错误和剩余额度。不新增第二套 working memory，也不从模型声称的“我修改了”推导真实修改。

例如展示“公开测试通过；命令为 X；对应工作区版本为 H；之后无修改”，比只保留测试日志开头更准确。文件又被修改时复用现有失效规则。公开测试通过仍不等于隐藏任务条件满足，不能自动据此给成功奖励。

### 2. 给大正文可回读的引用

复用 EvidenceStore 的执行证据和编号，归档已采集、已脱敏的工具正文；prompt 只带状态、来源、有限首尾预览与引用。文件读取继续按路径／范围重读；Shell 等不可安全重跑的观察从归档读取。

最多增加一个受限历史观察读取工具，限制当前运行及白名单事件类型，支持分页和简单字面检索。普通 read_file 不开放整个 `.aster`；不暴露配置、密钥或其他运行数据。新工具延续按需加载，但有归档引用时必须确保模型能发现并加载它。

归档也需要明确容量与来源：当前执行器只采集有限输出，不能把已丢弃的数据说成可恢复。超过采集范围的部分明确标注，磁盘归档失败时不先删除唯一可用正文。先不引入向量数据库或新的检索模型。

### 3. 按剩余空间分配正文

先计量系统规则、当前请求、用户追加约束、工具定义、任务状态和最近交互元数据，再把剩余空间分给工具正文。即使是一轮四个搜索结果，也必须共享一个正文总额度，不能让四条各自拿满单条上限后一起超限。

保留原生调用、结果和不透明推理元数据的合法关系；只缩短允许处理的正文，不篡改调用参数或伪造结果。原文已经可靠归档时，长正文可缩成状态、预览和引用。对用户要求和权限不做启发式“自动改写”。必需输入本身超过窗口时仍明确停止。

**调用与结果配对是硬约束，不能为满足预算而破坏。** `call_id` 是一次工具调用的唯一标识，结果通过它关联原调用；同一个工具连续或并行调用多次，也必须分别对应，不能按工具名或结果到达顺序配对。

- 在发起下一次模型请求、写入可续跑的回合检查点前，每个保留的调用必须恰有一个对应结果。禁止孤立结果、缺失结果、重复结果和重复调用 ID。执行过程中暂未返回的调用属于待完成状态，不能把这样的半批历史直接交给下一次模型请求。
- 缩短工具正文时，保留调用 ID、原生消息结构、真实执行状态及关联关系；归档引用放在对应结果内部。需要删除旧历史时，以完整交互组为单位，同时移出调用及其结果；并行调用批次与协议要求关联的推理元数据也保持完整，不独立切掉某个结果。
- 失败、拒绝执行和中断也要有真实结果。中断结果必须说明执行状态；若副作用是否完成尚不确定，要明确不确定性。不能为了配对而补造成功结果，也不能把未知的执行情况写成“未执行”。
- 复用现有 `history_groups()` 的分组与校验逻辑；重构时在压缩完成后及转换为供应商请求格式后检查配对与协议顺序。遇到不合法历史，在发送请求前明确报错，不通过静默丢弃结果掩盖错误。

例如模型同时发出 `read_file(call_id=A)` 和 `read_file(call_id=B)`，即使 B 先返回，两条结果仍分别关联 B、A。可以分别把正文缩成预览与归档引用；不能只留下 B 的结果却删除 B 的调用，也不能把两次结果合成一条冒充其中一次的返回。

现有实现已经有这部分基础：`src/aster/context.py` 的 `history_groups()` 按完整交互分组并检查缺失／孤立结果等错误；`src/aster/runtime.py` 在工具批次中断时记录取消结果后保存检查点。以上是新压缩方案必须保留并补充验收的合同，不代表所有新增边界检查已经实现。

### 4. 逐步减少旧观察占用

近期完整交互优先；较旧的大正文降为引用，重复且来源版本相同的文件观察无需反复展开；必要时移出更旧的完整组。压缩索引本身也要有界，更多历史通过分页／字面检索查回。索引不无限追加到 prompt。

用户约束保持明确来源和先后次序，不仅靠关键字判断哪条要求已失效。纯规则无法保证从任意长自然语言对话中无损提炼语义；当前阶段主要解决代码任务中大量工具输出和已知运行状态的膨胀。用户约束本身超长时仍需要扩大已知安全窗口、拆分任务，或在将来单独评估语义总结。

### 5. 正常运行与后训练共用同一输入构建

上下文策略固定并记录版本、预算、裁剪边界、归档哈希和实际发送的 observation。`observation` 指策略模型本次真正看到的输入；原始 trace 另外保留，不能训练时塞入完整历史、实际使用时才裁剪。

LLM 总结器并非不能用于 RL：冻结的总结器可以视为环境的一部分。但它增加额外调用、失败路径和采样波动；若还共同训练总结策略，才会进一步扩大优化范围。现阶段保持确定性上下文转换，便于固定环境后做 SFT／GRPO。运行环境和策略采样仍可能随机，不能称整个 Agent 因此完全确定。

## 验收与收益边界

先做机制检查：最新并行工具批次缩短后仍合法、归档回读逐字一致、一次性证据可寻回、测试状态修改后失效、超长用户约束明确停止、恢复前后同状态构建相同输入、正常模型路径和 RL 路径输入一致。归档失败、越权读取、敏感文本、损坏引用等也应有确定性检查。

调用配对的验收覆盖单次调用、并行批次、同工具不同 ID 与乱序返回、失败／拒绝／中断，以及连续多次压缩后恢复。反例覆盖缺失结果、孤立结果、重复结果和重复 ID；分别检查内部历史及 Responses、Chat Completions、Anthropic 请求转换后的关联与顺序。合法样本要求配对保持率 100%，非法样本要求请求前拦截率 100%，按实际用例数报告分母；这些是验收目标，当前不作为已测成绩。

随后保留 v5 原题和三档预算作对照，报告完整任务的 Pass@1／Pass@3、隐藏功能通过率、预算停止数、证据回读次数、共同成功配对的工具与 token 成本。信息丢失控制继续单列。v5 已用于发现设计问题，属于开发回归证据；另建未参与调参的留出题，检验改善是否泛化。

不预先承诺完成率 100%，不以 Pass@3 相同掩盖 Pass@1 下降，不将更早停止导致的低 token 算收益。若同预算下完成率下降，不能仅凭压缩率更高启用新策略。

新增的公开能力控制在一个观察回读工具；不新增服务、摘要模型、向量库、框架或一套记忆系统。改动主要涉及现有 context/runtime/evidence/tools/rl 及对应测试，若需要改采集上限再涉及 runner；实际实现前按这条主链确定接口，不先创建通用 ContextEngine 或插件体系。
