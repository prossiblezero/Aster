## 3. 优先级与最小修改范围

以下 P0 指阻碍目标开发流程的能力缺口，不代表已发现新的紧急安全事故。P1 是长程效率与日常可用性；P2 是有收益证据后再投入的扩展。严重程度与实现顺序可以不同，例如缓存统计和搜索截断应先作为小改动落地。

### P0：补齐连续开发、调研和交付的基本流程

| 问题与证据 | 最小修改建议 | 验收方式 |
|---|---|---|
| **执行环境不能可靠跨命令保留依赖。** 每次命令新建临时目录，`.venv`、`node_modules` 等不属于复制/回写清单。探针创建的 `node_modules` 在下一条命令消失，普通 `vendor/` 文件保留。实际 pip 安装成功与否尚未建立证据 | 区分“受管理源码”和“任务执行环境”。先为同一任务提供可复用、可清理的受控执行目录或依赖位置，明确哪些输出可回写源码。保留写范围、外部修改检测及隔离约束；不要仅把 `node_modules` 加进每轮全仓库复制 | 从空目录安装一个真实 Python 依赖及一个 Node 项目依赖，后续独立命令能导入/构建/测试；重启后的保留策略明确；取消和越界写不破坏主工作区 |
| **打开 network 还不能在本机完成普通域名访问。** 默认关闭网络是配置选择；开启后本地 HTTP 成功，但 required 沙箱访问 Python 官方文档 DNS 失败。宿主同一 Python 返回 200；沙箱不能读 `/etc/resolv.conf`，也不继承代理配置 | 修通授权联网场景所需的解析、证书与显式代理配置；启动时给出实际环境摘要和失败原因。先让已有 Shell 能完成有来源的网页检索/读取，再按真实任务需要增加小型 fetch/search 适配；不预设要建浏览器平台 | 同环境、同 URL 在授权沙箱中成功，禁网模式仍按配置工作；记录 URL、抓取时间和引用。再让模型自主寻找资料并引用，单个 GET 通过不能代替调研评测 |
| **正式验收偏向 Python。** `run_tests` 只支持 pytest/unittest 路径；`npm test` 和构建加测试的复合命令被拒绝。最终建站轮自行适应为先 Shell 构建，再独立 `run_tests`。Shell 返回成功不直接成为 formal verification | 保留一个统一验收入口，让任务明确声明验收命令和必需产物；先支持实际需要的 Python、npm/Node 命令。校验命令执行结果与测试是否有效运行；继续把验证证据绑定到当前工作区版本。网站再加入可选浏览器 smoke 检查 | Python/Node 各通过真实用例；零测试、测试失败、改代码后沿用旧通过状态都不能误报交付。验收深层页面、异常存储和可重建性；不能仅靠关键词推断或进程 exit 0 |
| **日常返修缺少自然会话入口。** `run(TaskSpec)` 会启动新任务并清空历史；`resume()` 校验身份和工作区，但只恢复原状态，失败/取消等终态不会因此继续。TUI 普通后续提交仍是新任务。CLI 不暴露任务步数/轮数和恢复入口 | 明确“继续未完成任务”“对已交付成果提出修改”“启动新任务”三种操作。复用现有 checkpoint/history，保留原需求和新反馈，重新判定修改后的验收；先开放已有预算与验收配置。恢复时显式处理工作区漂移和模型变化，不能跳过校验 | 不用专用 Python 驱动，CLI/TUI 就能完成需求澄清→开发→中断→继续→反馈修改。验证新反馈保留、旧验收失效、已成功工具不被无意义重放，外部编辑不被覆盖 |

源码入口：[执行器](../src/aster/safety/runner.py)、[工作区](../src/aster/workspace.py)、[沙箱](../src/aster/safety/linux.py)、[测试工具](../src/aster/tools.py)、[验收器](../src/aster/verifier.py)、[Runtime](../src/aster/runtime.py)、[CLI](../src/aster/cli.py)。

补充两个判断边界：Aster 没有内建 `web_search` / `web_fetch`，`search` 是仓库内字面搜索；这不代表只能靠专用工具才能调研。默认 required 沙箱中的 `git init` 探针被 `.git` 保护规则阻止，也不等于无法生成可以开源的代码。Git 初始化/发布应作为后续明确的操作能力，不需要为它取消全部元数据保护或关闭沙箱。

缓存审计还发现：对紧凑输入 JSON 做本地 `cl100k_base` 计数，精确 token 公共前缀为 209–571，中位数 252。**这只是本地布局代理值**，不含服务端工具排列、隐藏内容及真实 tokenizer，不能据此断言缓存为零。应调整 prompt 结构，但先补观测，再验证收益。仅添加 `cache_key` 不能修复不断变化的早部前缀；也不应为追求缓存把网页、记忆或技能正文升为系统权限。

建议的请求组织是：稳定约束与任务起点 → 已确认的交互记录 → 本轮新增状态/反馈；压缩时记录一个新的明确边界。它是语义与布局原则，并不要求每个供应商采用完全相同的消息角色或缓存参数。供应商缓存策略和缓存写入价格可能不同，最终比较应包括质量、总成本与等待时间。

### 单次输出上限的补充核查

4,096/8,192 是每次模型响应的最大输出，不是整个任务或整个网站的总量，也不是读取文件或 Shell 返回内容的上限。工具调用参数中的代码也属于模型输出。按 [OpenAI 官方定义](https://developers.openai.com/api/docs/guides/token-counting#understand-output-token-counts)，输出预算包含非可见 token；[推理指南](https://developers.openai.com/api/docs/guides/reasoning#allocating-space-for-reasoning)建议初次实验为推理和输出预留至少 25,000 tokens，再按实际用量调整。这是起始建议，不是所有模型必须使用同一预算。

当时采用较小上限是操作员对单请求用量和等待时间的保守控制，没有建立足以证明 4k/8k 合适的对照。降低上限不能保证更快或更便宜：如果造成截断或额外交互，反而会重复输入和工作。提高上限也不等于每轮一定用完额度。16 次运行的可见记录中没有明确的 `responses:max_output_tokens` 等额度耗尽终止；已报告的成功响应最大输出为 4,809。缺失的失败请求详情与用量不能补推，不能断言上限完全无影响。

截至本次查阅，三个参照项目的策略如下：

| 项目 | 已确认行为 |
|---|---|
| pi，`5a3a03a7f5db43692915d6ae45e6d96497ea248d` | 常规 `streamSimple` 默认从 `model.maxTokens` 出发，按剩余上下文裁剪；4,096 是窗口安全余量，不是默认输出上限。普通 Responses 分支通常发送 `max_output_tokens`；专用 Codex Responses 分支不发送该字段；Anthropic 分支发送 `max_tokens`，并按 thinking 模式处理预算。不存在统一的 4k/8k 默认 |
| Codex，公开客户端 `7abf2a3b5cbe08ca875d677dcd027528f9556152` | 普通 Coding 的 Responses 请求结构与构造路径不主动设置 `max_output_tokens`；仍受模型/服务端限制。配置中的 `tool_output_token_limit` 是工具结果进入历史的限制，不能当作模型生成上限 |
| Claude Code，当前官方环境变量文档 | `CLAUDE_CODE_MAX_OUTPUT_TOKENS` 控制多数请求的最大输出；默认和 cap 随模型而异。未知模型 ID 默认 32,000，超过已知模型 cap 会钳制；不能把旧版统一默认/最大值当作当前所有模型行为 |

| observation archive | 保留已有协议配对与来源保障；用真实回读任务检验交互设计，暂不新增检索平台 |
| plan/todo | 功能有重叠，可保留一份简洁计划/待办状态并兼容已有记录；不用再加工作流引擎。完成待办也不能代替验收 |
| 工具调用中的全工作区复制 | 每条修改/命令的复制成本随仓库增长，应单独 profile。环境生命周期需要改，但当前数据不支持为了本次耗时立即重写所有文件 I/O |

## 5. Skills：已经有机制，尚未形成实际使用闭环

**“本次没用到”成立，“完全没有实现”不成立，“已经能像成熟 Agent 那样使用技能包”也不成立。** Aster 没有配置任何技能，自然无法从技能获益。操作员 Codex 使用的 Skills 不会自动传给 Aster。

| 现状（源码与离线探针确认） | 问题与最小建议 |
|---|---|
| 只扫描 `.aster/skills/*.md` 和 `.skills/*.md`；前者同名优先；不识别 `<name>/SKILL.md`，不扫描用户全局技能目录 | 若目标是复用现有技能包，兼容目录式 `SKILL.md`，保留现有平铺格式。用户级来源可以显式配置，不应隐式把操作员全部技能复制进项目 |
| 目录只展示文件名，没有 `name/description` 等元数据 | 增加简短用途、触发条件和来源路径，使模型能选择适合当前任务的技能；先不做 embedding 路由、市场和自动安装 |
| `skill_load` 分页返回正文，首次成功即激活；下一次及之后每次请求重新读活动技能全文，在早部 context 注入；历史仍有工具返回的页面 | 分页只限制工具返回，不限制最终注入。离线读取 30 字符后，下一请求已含完整正文。选择按内容版本稳定加载的策略；需要压缩或文件变更时显式更新，避免重复正文和不必要的早部变化 |
| 没有资源基准目录；不自动处理引用/脚本。`.aster/skills` 中脚本受保护，普通读工具和沙箱不可访问；`.skills` 普通资源可读且可作为输入 | 返回明确 `base_dir`，允许按需读取授权资源，脚本仍经原有执行权限。不能为了技能脚本而整体开放保存轨迹等元数据的 `.aster` |
| `skill_load` 在空目录时也出现在可加载目录中；调用前还可能要先 `tool_load` | 启动时明确“无可用技能”；有技能时给可理解目录与直接加载路径，避免无意义探索。它与工具 schema 稳定策略应一起设计 |
| 技能正文被标注为不可信观察材料 | 明确技能可以提供用户授权范围内的方法，但不能修改权限、联网配置或用户要求；无需把整个技能提升成系统指令 |

**下一步只需要一个有真实用途的技能试点。** 例如静态教学站的构建与验收技能：规定先理解来源材料、选择已有构建方式、检查深层相对路径/图示信息/移动端阅读，资源脚本按需使用。不要把本次每个页面的修补过程写死成通用 Runtime 规则。

对照任务应保持模型、网关、预算和需求一致，比较有/无技能时的漏项、返修次数、输入量和独立验收结果。至少验证模型能够发现、选择、读正文、使用一份引用资源并完成验收；`skill_load` 调用次数增加本身不是收益。

源码入口：[Skills](../src/aster/skills.py)、[Runtime](../src/aster/runtime.py)、[Context](../src/aster/context.py)。

## 7. 向 pi 借鉴什么，哪些不需要照抄

源码参照为用户指定的 [earendil-works/pi](https://github.com/earendil-works/pi)，本次查阅版本 `5a3a03a7f5db43692915d6ae45e6d96497ea248d`。它的四个默认工具、持久会话、Skills/扩展边界和缓存用量呈现可以作为参照，不是 Aster 的行数或工具数量目标。

| 值得借鉴的思想 | Aster 的落点 |
|---|---|
| 小核心承载日常开发，可选能力向外扩展 | 保留单一模型—工具循环；优先完成环境、会话、验收；Memory/Worker 等不强行进入每个任务 |
| 会话是持续交互的基础 | 在现有原生协议历史与 checkpoint 上补续作/反馈语义；不必第一步就实现完整分支会话树 |
| 稳定上下文与可观察用量 | 消除每轮改写早部状态的做法；保留真实 cache usage；避免根据本地 token 代理值报告命中率 |
| 技能是能找到、能理解、能按需使用的资源 | 补元数据、标准目录及引用路径，并以实际任务验证；不照搬整个扩展生态 |
| 基础执行路径容易组合 | 把安装、运行、测试做顺；保留 Aster 已验证的沙箱、写前新鲜度、来源和验收约束 |

不需要为了“像 pi”删除安全检查、统一成一个万能 Shell、替换所有协议适配，或把 Memory/Worker/Skills 全部重做。Aster 现在已经有足够可复用的基础；当前证据支持的是**少数关键边界的局部重构与产品能力补齐**。

## 8. 建议执行顺序与下一轮真实验收

**明确顺序：先做小批已确认的基础修复，随后立即评测现有 Memory；不必等整份清单完成，也不在没有收益证据时重写 Memory。** 这是对前版“最后再评估 Memory”顺序的细化。上面的优先级代表目标能力缺口，不是一次性改完全部功能的工程范围。

1. **先修不依赖 Memory 收益判断的小问题。** 整理已有修复，补真实 cache/reasoning usage、额度耗尽原因、统一有效配置摘要，校准模型输出预算，修搜索/列表输出上限。这一批保持 Memory 的保存、检索与 Dream 算法不变，也暂不重写 prompt 布局；用已有回归与针对性检查验收。
2. **紧接着做现有 Memory 的真实连续任务对照。** 建议选一个基于 Python 标准库的 Markdown 链接检查 CLI，从实现可用版本，到新运行中增加功能，再到修改项目约定后返修，形成三阶段任务链。两组从同一项目起点和独立、空的持久记忆存储开始，一组启用 Memory/Dream，一组关闭；working memory 都保留。固定模型、输出/输入预算及需求，先各执行一条完整任务链。记录自主保存尝试、准入拒绝、实际召回、失效处理、重复阅读和独立验收；不手工预灌正确答案，也不把新任务当成自然续聊已经实现。先获得个案证据，差异需要复测后才用于收益判断。
3. **据结果调整 Memory，同时完成开发基础能力。** 只有实测暴露记忆发现、准入、检索或演化问题时才修改相应机制；继续补会话续作、失败后继续、任务预算入口、依赖复用、联网和 Node/Web 验收。Memory 试点使用现有支持的环境，是机制评测，不能冒充通用空目录交付能力验收。
4. **再做完整长程效率与 Skills 对照。** 优化稳定前缀、归档回读和恢复，配置一个真实技能包，并做下表中的新项目任务。每次固定其他条件，分别衡量，不把开启 Memory、改 prompt、换模型同时进行后单独归因。
5. **最后决定 Worker 等扩展的投入。** 补任务树共同预算与用量后再评估并行收益；没有证据时保留为可选能力。

下一轮至少应覆盖以下任务类型，并使用未把答案写进提示或技能的独立需求：

| 任务 | 检验内容 |
|---|---|
| 明确需求的 Python CLI | 真正空目录起步，安装一个依赖、编写功能和失败用例、测试、README/示例；在另一个干净环境按照 README 安装使用 |
| 模糊需求的小项目 | 用户只提供目标与限制；观察 Aster 是否主动澄清关键未知、形成可执行范围，并在用户中途反馈后继续，而不是丢掉前文重启 |
| Node/Web 小项目 | 授权联网查官方资料、安装并跨命令复用依赖、构建、单测及浏览器 smoke；在第三方干净目录中复现 |
| 中断与漂移场景 | 供应商短暂失败、取消后继续、用户外部编辑、修改后的测试失效、旧归档回读。先用确定性故障注入，再进行必要的真实模型验证 |

每类不以一次成功宣布通用能力，重复次数在开始前确定。固定模型、网关、推理/输出参数和预算，记录自主完成率、人工提示/改代码/重启次数、验收结果、已报告与未知用量、真实缓存字段、耗时与恢复结果。安装和测试通过是基础，还需有人从干净环境实际使用产物。

如果做 pi 对照，同样固定任务、模型和资源，并分别记录两者默认运行与可比配置；不能把操作员替一方调试后的结果当作同等条件。网站已经是有价值的工程案例，下一步应补“空目录持续开发”的新证据，不再仅用同一个已经修好的网站反复证明能力。
