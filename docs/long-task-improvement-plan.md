## 3. 优先级与最小修改范围

以下 P0 指阻碍目标开发流程的能力缺口，不代表已发现新的紧急安全事故。P1 是长程效率与日常可用性；P2 是有收益证据后再投入的扩展。严重程度与实现顺序可以不同，例如缓存统计和搜索截断应先作为小改动落地。

### P0：补齐连续开发、调研和交付的基本流程

| 问题与证据 | 最小修改建议 | 验收方式 |
|---|---|---|
| **执行环境不能可靠跨命令保留依赖。** 每次命令新建临时目录，`.venv`、`node_modules` 等不属于复制/回写清单。探针创建的 `node_modules` 在下一条命令消失，普通 `vendor/` 文件保留。实际 pip 安装成功与否尚未建立证据 | 区分“受管理源码”和“任务执行环境”。先为同一任务提供可复用、可清理的受控执行目录或依赖位置，明确哪些输出可回写源码。保留写范围、外部修改检测及隔离约束；不要仅把 `node_modules` 加进每轮全仓库复制 | 从空目录安装一个真实 Python 依赖及一个 Node 项目依赖，后续独立命令能导入/构建/测试；重启后的保留策略明确；取消和越界写不破坏主工作区 |
| **打开 network 还不能在本机完成普通域名访问。** 默认关闭网络是配置选择；开启后本地 HTTP 成功，但 required 沙箱访问 Python 官方文档 DNS 失败。宿主同一 Python 返回 200；沙箱不能读 `/etc/resolv.conf`，也不继承代理配置 | 修通授权联网场景所需的解析、证书与显式代理配置；启动时给出实际环境摘要和失败原因。先让已有 Shell 能完成有来源的网页检索/读取，再按真实任务需要增加小型 fetch/search 适配；不预设要建浏览器平台 | 同环境、同 URL 在授权沙箱中成功，禁网模式仍按配置工作；记录 URL、抓取时间和引用。再让模型自主寻找资料并引用，单个 GET 通过不能代替调研评测 |
| **正式验收偏向 Python。** `run_tests` 只支持 pytest/unittest 路径；`npm test` 和构建加测试的复合命令被拒绝。最终建站轮自行适应为先 Shell 构建，再独立 `run_tests`。Shell 返回成功不直接成为 formal verification | 保留一个统一验收入口，让任务明确声明验收命令和必需产物；先支持实际需要的 Python、npm/Node 命令。校验命令执行结果与测试是否有效运行；继续把验证证据绑定到当前工作区版本。网站再加入可选浏览器 smoke 检查 | Python/Node 各通过真实用例；零测试、测试失败、改代码后沿用旧通过状态都不能误报交付。验收深层页面、异常存储和可重建性；不能仅靠关键词推断或进程 exit 0 |
| **日常返修缺少自然会话入口。** `run(TaskSpec)` 会启动新任务并清空历史；`resume()` 校验身份和工作区，但只恢复原状态，失败/取消等终态不会因此继续。TUI 普通后续提交仍是新任务。CLI 不暴露任务步数/轮数和恢复入口 | 明确“继续未完成任务”“对已交付成果提出修改”“启动新任务”三种操作。复用现有 checkpoint/history，保留原需求和新反馈，重新判定修改后的验收；先开放已有预算与验收配置。恢复时显式处理工作区漂移和模型变化，不能跳过校验 | 不用专用 Python 驱动，CLI/TUI 就能完成需求澄清→开发→中断→继续→反馈修改。验证新反馈保留、旧验收失效、已成功工具不被无意义重放，外部编辑不被覆盖 |

源码入口：[执行器](../src/aster/safety/runner.py)、[工作区](../src/aster/workspace.py)、[沙箱](../src/aster/safety/linux.py)、[测试工具](../src/aster/tools.py)、[验收器](../src/aster/verifier.py)、[Runtime](../src/aster/runtime.py)、[CLI](../src/aster/cli.py)。

补充两个判断边界：Aster 没有内建 `web_search` / `web_fetch`，`search` 是仓库内字面搜索；这不代表只能靠专用工具才能调研。默认 required 沙箱中的 `git init` 探针被 `.git` 保护规则阻止，也不等于无法生成可以开源的代码。Git 初始化/发布应作为后续明确的操作能力，不需要为它取消全部元数据保护或关闭沙箱。

### P1：缓存、上下文和执行反馈

| 问题与证据 | 最小修改建议 | 验收方式 |
|---|---|---|
| **单次模型输出预算缺少任务与模型校准。** 产品默认 2,048；本次脚本使用 8,192，部分单文件及收尾阶段为 4,096。Responses 的预算包含推理与可见输出；现有日志未记录明确的输出额度耗尽终态，不能将 524/断流直接归因于它 | 按模型、协议及网关能力设置合理输出余量并显示生效值；保留推理用量与终止原因。普通编码任务可测试 32k 等候选值，但先确认网关支持并同步调整总上下文预算；不是直接把所有模型统一设到最大 | 验证预算映射、输入/输出合计、完整工具调用和额度耗尽分类；真正遇到额度耗尽时提供有界恢复，不执行不完整工具参数。固定其他条件比较总用量与完成质量 |
| **缓存使用量没有保留。** Provider 的 `_usage` 只留 input/output/total，无法分清缓存读写、未命中和未知 | 按协议保留可用的 cache read/write、cached input 等用量信息，区分缺失和 0；原始非敏感用量与统一字段可追溯。统计请求次数、失败、重试与用户等待时间 | 用带/不带缓存字段的响应验证归集；真实网关返回什么就报告什么，没有字段不能报 0% 或 100% |
| **高频变化的状态放在过早位置。** 106/106 对相邻请求最早差异均在第二条消息 `input[1]`；系统和任务文本都没变，但任务在动态状态之后 | 稳定系统约束、初始任务和工具定义；把新增状态作为后续事件追加，必要时省略可从记录直接推导的倒计数。为历史压缩设明确边界，保持完整工具调用/结果配对；不要每轮改写前面的历史摘要 | 固定模型、网关、参数和任务做前后对照；报告真实缓存字段、输入总量、延迟、压缩次数和成功率。必须通过现有预算、恢复及协议配对回归 |
| **工具目录有额外前缀变化。** 91/106 对请求的工具定义完全一致，另 15 对都是每个多轮任务首轮→第二轮时 `tool_load.names.enum` 增加 `observation_read`，不是突然加载了大量工具 | 在任务边界确定可稳定展示的目录；“暂时没有归档”通过当前状态/工具结果说明。实际权限变更仍必须生效，不能为缓存保留错误权限描述 | 相同能力下 schema 和顺序稳定；无归档、权限收紧、真正加载新工具仍有正确行为 |
| **工具输出控制不完整。** 单文件搜索 1,200 次命中返回 1,200 行，预期 500 上限只在一个文件扫描完后检查。503 文件只列前 500；总数在 `Outcome.data`，模型消息没带它 | 修正搜索上限检查；给现有 list/search 增加明确的范围、截断提示和续读方式。只向模型展示安全且必要的 `count/truncated/next` 等元数据，不原样倾倒全部内部 data | 大文件和大目录不再无界输出；模型能知道结果不全并读到余下部分；保留字面查询和路径过滤，不必先引入语义索引 |
| **反复小改不一定是真进展。** 06-build 进行了 46 次动作/35 轮请求，2,042,450 tokens，自测仍有 3 项失败后被操作员中止。当前停滞窗口遇到任意 changed_paths 即清空 | 在现有恢复器上补充“同一失败持续存在”的提示，结合失败签名、测试结果和最近修改，引导重新检查相关函数或简化方案；先给诊断反馈，再有界停止 | 重放本次无效补丁轨迹能更早改变策略；正常多次小修改和为新鲜度重新读取不应被误杀。不要把所有重复读取都禁止 |

缓存审计还发现：对紧凑输入 JSON 做本地 `cl100k_base` 计数，精确 token 公共前缀为 209–571，中位数 252。**这只是本地布局代理值**，不含服务端工具排列、隐藏内容及真实 tokenizer，不能据此断言缓存为零。应调整 prompt 结构，但先补观测，再验证收益。仅添加 `cache_key` 不能修复不断变化的早部前缀；也不应为追求缓存把网页、记忆或技能正文升为系统权限。

建议的请求组织是：稳定约束与任务起点 → 已确认的交互记录 → 本轮新增状态/反馈；压缩时记录一个新的明确边界。它是语义与布局原则，并不要求每个供应商采用完全相同的消息角色或缓存参数。供应商缓存策略和缓存写入价格可能不同，最终比较应包括质量、总成本与等待时间。

### 单次输出上限的补充核查

4,096/8,192 是每次模型响应的最大输出，不是整个任务或整个网站的总量，也不是读取文件或 Shell 返回内容的上限。工具调用参数中的代码也属于模型输出。按 [OpenAI 官方定义](https://developers.openai.com/api/docs/guides/token-counting#understand-output-token-counts)，输出预算包含非可见 token；[推理指南](https://developers.openai.com/api/docs/guides/reasoning#allocating-space-for-reasoning)建议初次实验为推理和输出预留至少 25,000 tokens，再按实际用量调整。这是起始建议，不是所有模型必须使用同一预算。

当时采用较小上限是操作员对单请求用量和等待时间的保守控制，没有建立足以证明 4k/8k 合适的对照。降低上限不能保证更快或更便宜：如果造成截断或额外交互，反而会重复输入和工作。提高上限也不等于每轮一定用完额度。16 次运行的可见记录中没有明确的 `responses:max_output_tokens` 等额度耗尽终止；已报告的成功响应最大输出为 4,809。缺失的失败请求详情与用量不能补推，不能断言上限完全无影响。

截至本次查阅，三个参照项目的策略如下：

| 项目 | 已确认行为 |
|---|---|
| pi，`5a3a03a7f5db43692915d6ae45e6d96497ea248d` | 常规 `streamSimple` 默认从 `model.maxTokens` 出发，按剩余上下文裁剪；4,096 是窗口安全余量，不是默认输出上限。普通 Responses 分支通常发送 `max_output_tokens`；专用 Codex Responses 分支不发送该字段；Anthropic 分支发送 `max_tokens`，并按 thinking 模式处理预算。不存在统一的 4k/8k 默认 |
| Codex，公开客户端 `7abf2a3b5cbe08ca875d677dcd027528f9556152` | 普通 Coding 的 Responses 请求结构与构造路径不主动设置 `max_output_tokens`；仍受模型/服务端限制。配置中的 `tool_output_token_limit` 是工具结果进入历史的限制，不能当作模型生成上限 |
| Claude Code，当前官方环境变量文档 | `CLAUDE_CODE_MAX_OUTPUT_TOKENS` 控制多数请求的最大输出；默认和 cap 随模型而异。未知模型 ID 默认 32,000，超过已知模型 cap 会钳制；不能把旧版统一默认/最大值当作当前所有模型行为 |

## 4. 工具是不是太多、太重

**不建议为了接近 pi 的四个默认工具，把 Aster 强行删成四个。** 当前注册表有 27 个工具，但默认按需加载；本次 122 份请求始终只有 9 个核心工具的完整 schema。

| 工具 | 本次结果条数 |
|---|---:|
| `read_file` | 109 |
| `run_shell` | 41 |
| `patch_file` | 34 |
| `search` | 17 |
| `write_file` | 14 |
| `list_files` | 8 |
| `run_tests` | 5 |
| `git_diff` | 5 |
| `tool_load` | 1 |
| 合计 | **234** |

模型共提出 236 个调用，其中 2 个 patch 因运行提前终止而未记录执行结果。唯一一次 `tool_load` 加载的还是已经在核心集合中的 `write_file`，没有增加新的能力。不能把这些数字解释成 234 次成功，实际有 211 success、11 error、12 blocked。

已记录的 `Outcome.duration_ms` 合计 **49.926 秒**。它只覆盖工具注册表执行阶段，不覆盖全部前置检查、上下文构造、审批和快照；与包含并行的运行累计时间不是完整分解。因此不能算出“99% 时间花在模型上”，但至少没有证据把数小时消耗归咎于工具函数本身。高输入量、反复交互和上游等待更值得优先测量。

| 部分 | 建议 |
|---|---|
| 读、搜、写、补丁、Shell | 保留。改输出上限、范围和修改反馈，让模型更容易正确使用；工具契约清晰比减少名称更重要 |
| 批量 `patch_file` | 借鉴 pi 的同一原文定位、唯一匹配及重叠检查，一次验证后写入；保留读取版本校验，保持 BOM/换行风格。先用精确匹配，不引入宽泛 Unicode 模糊替换 |
| Shell 输出归档 | 当前 runner 收集超过 256 KiB 的内容会丢弃，属于补充源码发现，未证明导致本次任务失败。保留有界摘要，将完整输出在明确资源上限内归档，并通过现有 `observation_read` 回读；超限明确报告，不承诺无限日志 |
| `run_tests` / 验收证据 | 保留统一验收语义，扩展实际所需命令；执行实现可复用 Shell，避免维护两套互相矛盾的命令规则 |
| `git_diff` | 保留当前任务基线差异能力。在 `.git` 不进入沙箱的设计下，它有明确作用 |
| `tool_load` 与可选工具 | 保留按需加载；目录补一句用途，减少仅凭名称猜测。根据任务配置使 `ask_user`、Skills 等必要能力容易发现，无需默认展开全部 27 个工具 |
| observation archive | 保留已有协议配对与来源保障；用真实回读任务检验交互设计，暂不新增检索平台 |
| plan/todo | 功能有重叠，可保留一份简洁计划/待办状态并兼容已有记录；不用再加工作流引擎。完成待办也不能代替验收 |
| 工具调用中的全工作区复制 | 每条修改/命令的复制成本随仓库增长，应单独 profile。环境生命周期需要改，但当前数据不支持为了本次耗时立即重写所有文件 I/O |

`src/aster` 约 5,309 行，Runtime 约 1,117 行。体量本身不能判定“重”；更应关注同一职责是否重复、改动是否容易测试，以及可选机制是否给普通任务制造额外约束。若拆分 Runtime，只在本轮修复触及明确边界时提取会话、用量或环境职责，不先做大规模目录重排。

## 5. Skills：已经有机制，尚未形成实际使用闭环

**“本次没用到”成立，“完全没有实现”不成立，“已经能像成熟 Agent 那样使用技能包”也不成立。** Aster 没有配置任何技能，自然无法从技能获益。操作员 Codex 使用的 Skills 不会自动传给 Aster。

| 现状（源码与离线探针确认） | 问题与最小建议 |
|---|---|
| 只扫描 `.aster/skills/*.md` 和 `.skills/*.md`；前者同名优先；不识别 `<name>/SKILL.md`，不扫描用户全局技能目录 | 若目标是复用现有技能包，兼容目录式 `SKILL.md`，保留现有平铺格式。用户级来源可以显式配置，不应隐式把操作员全部技能复制进项目 |
| 目录只展示文件名，没有 `name/description` 等元数据 | 增加简短用途、触发条件和来源路径，使模型能选择适合当前任务的技能；先不做 embedding 路由、市场和自动安装 |
| `skill_load` 分页返回正文，首次成功即激活；下一次及之后每次请求重新读活动技能全文，在早部 context 注入；历史仍有工具返回的页面 | 分页只限制工具返回，不限制最终注入。离线读取 30 字符后，下一请求已含完整正文。选择按内容版本稳定加载的策略；需要压缩或文件变更时显式更新，避免重复正文和不必要的早部变化 |
| 没有资源基准目录；不自动处理引用/脚本。`.aster/skills` 中脚本受保护，普通读工具和沙箱不可访问；`.skills` 普通资源可读且可作为输入 | 返回明确 `base_dir`，允许按需读取授权资源，脚本仍经原有执行权限。不能为了技能脚本而整体开放保存轨迹等元数据的 `.aster` |
| `skill_load` 在空目录时也出现在可加载目录中；调用前还可能要先 `tool_load` | 启动时明确“无可用技能”；有技能时给可理解目录与直接加载路径，避免无意义探索。它与工具 schema 稳定策略应一起设计 |
| 技能正文被标注为不可信观察材料 | 明确技能可以提供用户授权范围内的方法，但不能修改权限、联网配置或用户要求；无需把整个技能提升成系统指令 |

**下一步只需要一个有真实用途的技能试点。** 例如静态教学站的构建与验收技能：规定先理解来源材料、选择已有构建方式、检查深层相对路径/图示信息/移动端阅读，资源脚本按需使用。不要把本次每个页面的修补过程写死成通用 Runtime 规则。

对照任务应保持模型、网关、预算和需求一致，比较有/无技能时的漏项、返修次数、输入量和独立验收结果。至少验证模型能够发现、选择、读正文、使用一份引用资源并完成验收；`skill_load` 调用次数增加本身不是收益。

源码入口：[Skills](../src/aster/skills.py)、[Runtime](../src/aster/runtime.py)、[Context](../src/aster/context.py)。

## 7. 向 pi 借鉴什么，哪些不需要照抄

源码参照为用户指定的 [earendil-works/pi](https://github.com/earendil-works/pi)。2026-09-17 基线查阅版本为 `5a3a03a7f5db43692915d6ae45e6d96497ea248d`；以下新增的 provider、流式和并行核对使用 2026-09-18 查阅的 `46c9de402bddf46b03c3b9f46487b777aaa41861`（提交日期 2026-09-17），不混用为同一版本结论。pi 的四个默认工具之外还有搜索和目录等工具；默认工具数量不是 Aster 的数量目标。pi 没有内建沙箱，不应照搬其执行权限而移除 Aster 的隔离与写入保障。

| 值得借鉴的思想 | Aster 的落点 |
|---|---|
| 小核心承载日常开发，可选能力向外扩展 | 保留单一模型—工具循环；优先完成环境、会话、验收；Memory/Worker 等不强行进入每个任务 |
| 会话是持续交互的基础 | 在现有原生协议历史与 checkpoint 上补续作/反馈语义；不必第一步就实现完整分支会话树 |
| provider、API 协议、模型能力分开 | 复用已有三种协议适配，增加具名配置与统一历史；模型、地址、认证及预算一起切换，先实现启动后选择，再实现同一会话续聊 |
| 流事件与完整结果共用同一条处理路径 | 统一增量文字、工具参数和终态事件；界面可提前显示，工具执行仍等待完整响应校验 |
| 工具调度支持串行与并行 | 先做同轮独立只读操作的有界并发，保留修改顺序与结果配对；与多 Worker 调度分开评估 |
| 稳定上下文与可观察用量 | 消除每轮改写早部状态的做法；保留真实 cache usage；避免根据本地 token 代理值报告命中率 |
| 技能是能找到、能理解、能按需使用的资源 | 补元数据、标准目录及引用路径，并以实际任务验证；不照搬整个扩展生态 |
| 基础执行路径容易组合 | 把安装、运行、测试做顺；保留 Aster 已验证的沙箱、写前新鲜度、来源和验收约束 |

不需要为了“像 pi”删除安全检查、统一成一个万能 Shell、替换所有协议适配，或把 Memory/Worker/Skills 全部重做。Aster 现在已经有足够可复用的基础；当前证据支持的是**少数关键边界的局部重构与产品能力补齐**。

### 7.1 多 provider 与模型切换

pi 区分 provider（服务、认证与模型目录）、API（请求响应协议）和 model（ID、能力与预算）。当前实现由 `Models` 解析配置与认证，再交给 Provider 对象按 `model.api` 分发；会话另行保存模型变更。Aster 已有 Responses、Chat Completions、Anthropic Messages 三种适配，但历史仍含原生协议结构，不能仅修改 `settings.model/protocol` 就宣称支持跨 provider 续聊。

1. **启动后选择模型：** 增加具名 profile，包含 provider、模型 ID、协议、地址、凭证环境变量引用、上下文/输出预算及必要能力标记；本地服务允许显式无认证。保留原 `.env` 入口，实现 `/model` 列表和 `/model <alias>`。第一版只在空闲时切换，作用于后续任务，默认不修改全局配置；这一阶段不称为会话内切换。
2. **同一会话续聊与切换：** 区分持久会话与单个任务状态；普通追问延续上下文，`/new` 开新会话。引入带来源的统一消息结构，保留原始证据；转换完整工具调用/结果及 ID，移除不兼容签名，不承诺跨 provider 无损保留不透明推理数据。显式记录模型切换，恢复时分别校验模型变化与工作区/权限身份，不能直接移除原有校验。
3. **切换边界：** 切入小窗口模型前完成预算检查及必要压缩；配置或历史校验失败时原会话不变。新凭证进入脱敏范围，不写进会话记录；切换不放宽权限。Aster 第一版空闲切换是简化选择，pi 本身允许更新后续轮次模型，正在请求的响应仍使用此前配置。

验收覆盖 `/model` 不进入模型提示、配置/认证/预算一致、失败不污染状态，以及三种协议六个转换方向中的工具配对、取消、恢复和小窗口处理。先用离线 transport 验证，真实服务仅验证已配置的端点。兼容协议不等于模型具有可靠工具调用能力；跨 provider 切换产生的缓存冷启动单独统计。

pi 源码：[Models 与 Provider](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/ai/src/models.ts#L703)、[历史转换](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/ai/src/api/transform-messages.ts#L64)、[会话模型切换](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/coding-agent/src/core/agent-session.ts#L1752)。

### 7.2 正式流式响应：P1，随 provider 改造分批交付

流式响应是服务端生成内容时逐段发送，客户端随到随处理或显示；SSE 是常见传输形式，并非每个事件恰好一个 token。它主要减少看到首段内容的等待、改善取消与故障可见性，不自动减少 token、保证总耗时更短或修复 524。模型流式响应、Shell 实时日志和工具并行是三个独立能力。

**当前状态：** [Provider](../src/aster/provider.py) 等待完整 JSON，[TUI](../src/aster/tui.py) 只显示完整 `model_reply`。[网站实验 SSE](../learn_web/scripts/website_stream_transport.py) 接收事件并记录首事件/进度，但将终态响应交回原解析器，不向产品 UI 提供文字增量；不能把实验客户端算作正式支持。pi 会统一不同协议的流事件，由 agent 向界面传递增量更新；其工具执行也等待该轮响应结束，输出截断时拒绝执行该批调用。

**最小实现：**

- 在 protocol adapter 层统一开始、文字增量、工具参数增量、完成、失败事件及终态用量；保留可由流聚合得到的 `complete()`，避免维护两套不一致的解析与执行逻辑。先覆盖 Responses，再逐个适配其他协议，明确每种协议实际支持的模式。
- Runtime 将进度交给 TUI，界面增量显示并允许取消；等待期提供有界进度信息，记录首事件、首段有效文字和总完成时间，不把 SSE 心跳当作首段回答。
- 只在完整、成功且参数校验通过后调度工具。断流、失败、额度耗尽和取消均标记未完成；已显示的片段不成为有效工具调用或成功完成证据。重试区分不同尝试，不能重复拼接文字或执行已完成工具。
- 用量按终态一次归集，缺失仍记未知；新增事件沿用脱敏与日志容量限制。失败后可继续依赖第 7.1 节的会话恢复，不用无限重试代替恢复。

**验收：** 用可控的分段服务确认首段显示早于响应结束；覆盖跨分段字符与 JSON、多个工具调用、终态前断流、明确 error、额度耗尽、重复终态、取消和流式/非流式结果一致。断流不得执行部分工具；用量不得重复累计。真实对照固定模型、推理配置和预算，分别报告首事件、首段有效文字、总耗时与完整交付，不将改推理参数的效果归给流式。

pi 源码：[流事件处理](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/agent/src/agent-loop.ts#L339)、[完整响应后工具调度及截断处理](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/agent/src/agent-loop.ts#L218)。

### 7.3 同轮工具并行：P1，先只读，与 Worker 分开验收

| 能力 | Aster 当前实现 | 计划边界 |
|---|---|---|
| 模型一次返回多个调用 | 支持，但主 Runtime 逐个 `await self.step(call)` | 返回多个调用不等于并行执行 |
| 同一批工具并行 | 尚不支持；Runtime 有单操作门禁和共享状态 | 先允许明确独立的只读调用有界并发，其余保持串行 |
| 后台 Worker | `worker_start` 创建后台任务；独立 Runtime/历史，共用工作区；默认最多 2 个，core 下需加载工具 | explore 只读，写 Worker 受范围约束；不是独立 worktree，也不能代替批次并行 |
| Worker 等待与收尾 | `worker_status` 查询状态；父任务收尾取消尚未结束的 Worker 并清理 | 不宣传为父任务会自动等全部子任务完成；共同预算、用量及完成策略单独完善 |

pi 默认允许批次并行，先依次做调用预检，再并发执行允许的调用，按原始调用顺序写回结果；全局串行配置或本批任一工具声明 `sequential` 时，整批串行。其 `edit/write` 对同一文件修改排队，不同文件可以并行，但队列不能管理任意 Shell 副作用。Aster 不需要第一版就复制这个完整范围。

**最小实现：**

- 增加明确的并行资格与并发上限。第一版仅将一批中全部合格、互不依赖的只读调用并发执行，例如 `read_file/search/list_files`；混有写入、Shell、测试、审批、计划/记忆修改等操作时整批串行，避免跨副作用重排。实际并发不能仅创建 asyncio task，阻塞 I/O 也需要适当执行路径。
- 顺序完成权限/参数检查和步数预算预留；并发只覆盖可隔离的工具工作，读取证据、working memory、用量、历史、checkpoint 等共享状态由 Runtime 有序归集。不能直接对现有 `step()` 使用 `gather()` 绕过单操作门禁。
- 结果按调用顺序进入历史，保留 call ID 配对；单个失败不丢弃其他结果，取消后每个已接受调用都有可解释的结果状态，停止并清理在途操作。读取证据仍对应实际读到的版本，后续编辑继续做新鲜度校验。
- 两次真实任务都关闭了 Worker，没有证据证明并发必然带来显著收益。读工具并行和 Worker 分别配置、分别记录，不同时开启后混合归因。

**验收：** 用同步屏障或可控假工具证明至少两个调用真正重叠、上限有效，故意打乱完成顺序验证历史顺序；覆盖失败、取消、预算不足、权限拒绝、混合批次串行和外部文件修改。随后固定模型/任务对照串行与只读并行，报告工具阶段耗时、端到端耗时、结果一致性及验收成功率。不能凭工具名称减少或理论并发倍数宣称提速。

源码：[Aster Runtime](../src/aster/runtime.py)、[Worker](../src/aster/workers.py)、[pi 批次调度](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/agent/src/agent-loop.ts#L464)、[pi 文件修改队列](https://github.com/earendil-works/pi/blob/46c9de402bddf46b03c3b9f46487b777aaa41861/packages/coding-agent/src/core/tools/file-mutation-queue.ts#L29)。

## 8. 建议执行顺序与下一轮真实验收

**2026-09-18 更新：此前“基础小修 → 现有 Memory 三阶段对照”已经完成，保留冻结实验，不重复列为下一步。** 72/72 项阶段检查通过不代表 Memory 收益：自然存储与召回均为零，显式保存成功；下一步分别处理触发、中文检索和经验来源。上面的 P0/P1 是目标缺口，下列顺序是分批交付安排，不要求一次改完整份清单。

1. **修复两次任务中可复现的小问题。** 修合法 heredoc 误拒、pip 所需系统文件的最小只读兼容、旧 benchmark 缺失用量统计和被父 Git 忽略目录的启动边界。随后交付批量补丁与可回读的命令输出，保留版本检查和容量限制。
2. **模型配置、正式流式与会话分批交付。** 先 profiles 和启动后 `/model`；随 provider 接口改造分协议接入第 7.2 节流事件与 TUI；再统一历史、普通追问续接、同会话切换及失败恢复。每个提交明确实际支持范围，跨协议会话验收通过前不宣称无缝切换。
3. **补同轮只读工具并行。** 按第 7.3 节拆分执行与状态归集，先离线验证，再做真实串行/并行对照；不等待 Worker 重构，也不顺带并行写入、Shell 和测试。
4. **优化缓存与长程观察。** 固定其他条件调整稳定前缀、工具目录及归档回读，记录缓存、总输入、质量与耗时；不同时更改 Memory 算法，不把流式首字体验当作缓存或总成本收益。
5. **补项目环境，再分别验证 Memory 与 Skills。** 完成依赖复用、授权联网与 Node/Web 正式验收。Memory 先改善发现、保存时机、中文检索；环境经验等新来源必须明确出处、作用域和失效条件，Dream 仍按维护机制描述。Skills 补目录元数据、`SKILL.md` 和按需正文/资源，配置一个真实技能包单独评估。
6. **最后评估 Worker 扩展与训练执行。** 先补任务树共同预算、子任务用量和完成/取消策略，再评估多 agent 收益。数据集、SFT、GRPO 方案可并行设计；大规模采集前稳定消息、工具和恢复协议，划分新的 train/dev/test 任务，奖励不只依赖模型自测或自报完成。

所有 Python、测试、探针和真实 Aster 运行使用 `/home/dzh/.conda/envs/aster/bin/python`，不在 base 执行或安装项目依赖。新实战的可运行产品统一放在 `exam_project/`，实验协议、驱动、评分器和报告放在 `evaluations/`，网站成果保留 `learn_web/`；每批按范围运行必要检查并本地 Git 保存，不将文档计划提交当作功能实现。

| 任务 | 检验内容 |
|---|---|
| 明确需求的 Python CLI | 真正空目录起步，安装一个依赖、编写功能和失败用例、测试、README/示例；在另一个干净环境按照 README 安装使用 |
| 模糊需求的小项目 | 用户只提供目标与限制；观察 Aster 是否主动澄清关键未知、形成可执行范围，并在用户中途反馈后继续，而不是丢掉前文重启 |

| 中断与漂移场景 | 供应商短暂失败、取消后继续、用户外部编辑、修改后的测试失效、旧归档回读。先用确定性故障注入，再进行必要的真实模型验证 |
| 模型切换与流式交互 | CLI/TUI 选择 profile、同会话切换、较小上下文、分段显示与取消；断流后继续不重复写入，未完成参数不执行 |

如果做 pi 对照，同样固定任务、模型和资源，并分别记录两者默认运行与可比配置；不能把操作员替一方调试后的结果当作同等条件。网站已经是有价值的工程案例，下一步应补“空目录持续开发”的新证据，不再仅用同一个已经修好的网站反复证明能力。
