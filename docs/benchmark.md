# Aster 评测：任务正确性与机制收益分开看

当前 v4 评测对应代码提交 `fd2fe66`：**193 条主任务、69 个机制场景、12 组上下文配置**。主任务包含 164 道 HumanEval；只有固定子集调用真实模型，参考动作回放不算模型成绩。题目、初始仓库、参考动作和预期结果都在 [datasets](../datasets/README.md)。

最新报告：[参考回放](../artifacts/benchmark-v4-scripted/report.md)、[机制消融](../artifacts/benchmark-v4-mechanisms/report.md)、[真实模型](../artifacts/benchmark-v4-real/report.md)、[v3→v4 比较](../artifacts/benchmark-v4-comparison/report.md)、[工件核验](../artifacts/benchmark-v4-comparison/validation.json)。

## 复现命令

```bash
conda activate aster
python -m pytest -q
ruff check src tests scripts
python scripts/benchmark.py --task debug-and-fix --output artifacts/benchmark-v4-single
python scripts/benchmark.py --concurrency 4 --output artifacts/benchmark-v4-scripted
python scripts/benchmark_mechanisms.py --output artifacts/benchmark-v4-mechanisms
python scripts/benchmark.py --real --selection real_subset.json --repeats 1 --concurrency 4 --output artifacts/benchmark-v4-real
python scripts/compare_benchmarks.py
```

正式主评测先验证 169 条代码题的初始版本：目标测试必须失败，已有行为必须通过；再经真实 Runtime 回放参考动作，使用独立评分器验证最终候选。193 条主任务中，12 条记忆题各跑两个条件，因此共 **205 次执行**。机制评测为 **69 个场景、97 次条件尝试**，其中 27 个测试工具案例的内容与期望状态位于 `tool_contract_cases.json`。

简历仅展示 Harness 部分：排除 4 个 RL 环境场景后，为 **65 个机制场景、93 次条件尝试，93/93 符合预期**；加上 193 条主任务，共 258 个任务/场景。全量报告仍保留 69/97 的原始口径。

真实模型名单在运行前固定为 29 题：5 条仓库修改、12 条跨运行问答、HumanEval/0–11。每题每条件一次，共 58 次。模型为 GPT-5.6 Luna、Responses 协议，从 `.env` 读取连接配置，使用网关默认采样参数、并发度 4。

`--task` 可重复指定，`--suite` 选择题型，`--selection` 加载固定名单。`--repeats 3` 会让所有题、所有条件各跑三次，不是仅重跑失败题；失败仍写报告，退出码为 1。Ruff 检查运行代码与测试脚本，不把故意有缺陷的题目 fixture 当作项目源码修正。

## 四层证据

| 层次 | 观察什么 | 怎样判断 |
|---|---|---|
| 任务完成 | 候选代码、回答、隐藏测试与结束状态 | 任务正确性和完成条件均满足才通过，二者也分别保留 |
| 效率 | 工具调用、重复读取、token、耗时 | 同题同初始文件对照；仓库、函数和记忆分别统计 |
| 鲁棒性 | 无效参数、停滞、恢复、漂移和模型错误 | 检查中间结果、后续动作与终态，不能只看最终回答 |
| 安全 | 路径、权限、沙箱、记忆准入、奖励来源 | 危险动作是否被拒；任务高分不能抵消安全缺陷 |

## 对照具体改变了什么

**工具集合。** `core` 默认最多展示 9 个核心工具，其余通过 `tool_load` 加载；`all` 首轮展示当前可用全集。两组都会过滤关闭的能力及当前无法授权的工具。同题使用相同模型、初始文件、预算和评分器。每条件一次仅支持小样本观察，不能宣称统计显著。

**跨运行记忆。** 两组先通过相同的 `read_file → memory_store` 获取事实，各两次固定工具动作；然后新建 Runtime，历史与 working memory 为空、源文件仍可读取，只改变长期记忆开关。Luna 独立完成后续问答。报告仅比较后续成本，学习成本单独保留。这测量已有事实召回，不证明自主学习效果。

**记忆演化。** 24 个场景包括 12 个准入、4 个来源变化、6 个反馈调整和 2 个回滚。两个条件均保留安全准入和来源检查，关闭组只停用反馈排序与 Dream 维护。6 条反馈场景的共同目标达成 **2/6→6/6**，其中包含不应误删正常记忆的控制场景。反馈是预先标注的，不能写成真实 Agent 自进化成功率。

**恢复与 Hooks。** 恢复消融总共 2 个场景：重复读取、两种读取交替振荡各 1 个，每个执行关闭/开启两个条件，共 4 次尝试。两个条件使用相同的预设动作序列；开启组在检测到停滞后可继续执行事先写好的后续动作，关闭组停止。因此 **0/2→2/2** 只验证恢复机会是否生效，不代表真实模型能自主改变方法。Hooks 另有 2 个场景，检查重复调用 ID 和前置回调异常，关闭组仍保留权限与沙箱，共同目标也是 **0/2→2/2**。

另外有 4 个恢复控制，分别检查有效写入不误报、不同文件内容相同不误报、新任务重置恢复额度、续跑保留额度并在耗尽时停止；还有 3 个续跑、3 个停止生命周期、4 个 RL 环境场景。这些是补充边界检查，不能合并为恢复效果消融。两个恢复消融场景仅够基础机制验证，尚不能证明场景覆盖充分或真实任务纠偏有效。

**测试工具。** 27 个场景覆盖 pytest/unittest 正常执行、部分可选跳过、全跳过、假输出、提前退出、启动入口冒充、子测试、环境错误和无报告失败。工程集成回归另检查工作区在测试期间变化、记忆反馈及终态奖励。普通测试须真正执行至少一项；隐藏评分须全部选定检查通过。

“契约通过”与“目标达成”不同：关闭恢复时按定义停止，契约通过，后续任务目标未达成。**97/97** 是各条件表现符合事先定义，不是 97 次自主 Agent 任务成功。

## v4 实测结果

**293/293** 项工程测试通过，冻结提交在隔离源码中也通过全部测试；wheel 构建、临时安装、两个真实 CLI 入口及 3 项安装后 CLI 测试通过。Ruff 和差异检查通过。远端 CI 尚未运行。

参考动作回放 **205/205**；169 条代码题均满足“初始目标失败、已有行为通过、参考修复通过”；机制契约 **97/97**；12 组上下文预算、当前请求与指定证据保留均通过。共核验 263 次主评测归档的候选指纹、checkpoint 与 trace 哈希链。

真实模型为 **57/58**，分组如下。调用次数包含定位、读取、修改、验证与差异检查，不是模型重试次数。

| 类型 | 条件 | v3 完成 | v4 完成 | v4 平均工具调用 | v4 平均记录 token |
|---|---|---:|---:|---:|---:|
| 函数实现 | 全部可用工具 | 12/12 | 12/12 | 6.08 | 27,558 |
| 函数实现 | 核心工具 | 12/12 | 12/12 | 5.83 | 24,430 |
| 仓库修改 | 全部可用工具 | 5/5 | 5/5 | 15.00 | 47,008 |
| 仓库修改 | 核心工具 | 5/5 | 5/5 | 15.80 | 41,174 |
| 跨运行问答 | 关闭长期记忆 | 11/12 | 11/12 | 2.92 | 13,868 |
| 跨运行问答 | 开启长期记忆 | 12/12 | 12/12 | 0.00 | 5,084 |

同批次工具集合对照中，核心集合的函数题 token 减少 **11.4%**，仓库题减少 **12.4%**；仓库工具调用却从 75 增至 79，不能说全部效率都提高。长期记忆两组共同成功的 11 题，后续工具调用 **35→0**、token **161,255→55,929**，减少 **65.3%**。全部样本的完成率仍保留为 11/12 和 12/12。

唯一失败为 `memory_steps / memory_off`：模型未调用工具，直接回答 16，正确值为 17。运行自身满足结束条件，但答案检查判错。没有调整答案、重采样或剔除失败。这也是后续训练应关注的“先获取证据再回答”行为。

### 工具不能只看总成功率

真实批次共调用工具 **332 次**，其中 **324 次成功**。40 次 `run_tests` 均真正执行并通过；12 次 `run_shell` 中，2 次因模型命令缺少结尾引号被拒，经 `/bin/sh -n` 独立确认语法无效。另有 6 次 `patch_file` 因编辑前缺少最新读取被拒。两类拒绝后的任务最终均完成，不当作缺陷隐藏，也不把正常安全拒绝称为执行故障。

v3 曾记录 6 次 Shell 审批拒绝、1 次 Shell 执行错误、1 次读取参数错误和3次编辑前读取拒绝；v4 的逐工具统计见真实报告及 `validation.json`。两批模型选取的命令不同，这个观察不能单独证明某个组件带来了全部变化。

## 上下文预算与分页

12 组配置交叉组合 12/24/48/96 条观察与代码、日志、中文三类文本。输入上限 `4096 - 512 = 3584`；计量复用 Provider 的请求构造，覆盖消息、工具定义和协议字段。

输入由 `context_cases.json` 和 `scripts/benchmark.py::context_cases()` 构造，每条历史观察将对应模板重复 12 次，再追加人工标记为重要的证据。测试仅调用上下文构建器，检查预算及当前请求、指定证据字符串是否保留；没有调用模型，也没有后续修复任务或隐藏测试判分。较大的缩减来自裁掉大量构造的重复旧观察，不能据此判断其他必要信息是否丢失。

平均输入 **18,207→3,352 个本地估算 token**，12/12 均满足预算并保留当前请求和指定证据。这里用本地 tokenizer 对 JSON 统一计数，不是供应商计费 tokenizer，也不意味着真实任务费用减少同样比例。v3 同样为 12/12，v2 为 0/12，但更早版本的计量边界不同，原报告保留。

核对 v4 真实批次的全部 58 次尝试，其 trace 共记录 **205 次 `context_built`，历史裁剪触发次数为 0**，输入预算均为 21,952。因此，真实任务的 57/58 结果没有验证从约 18,207 裁至 3,352 后的任务完成能力。尚需同题比较充足预算与紧预算，确认紧预算实际发生裁剪，再以独立测试检查完成率，并记录总 token 与补读次数；任务应包含早期关键依赖、多文件修改，以及可重读和仅存在于历史中的信息。这是待补评测，不计入当前成绩。

此外，协议回归检查原生调用/结果配对、并行调用、推理元数据、checkpoint 与中断恢复；分页回归证明全局预算 4096、正文预算 64 时可以继续取回计划或技能的尾部。它验证数据可送达，不等于模型一定会主动翻页。不可进一步裁剪的必需输入会明确停止。字段解释见 [阶段 15](learning/15-paged-observations.md)。

## 独立评分与后训练边界

模型看不到参考动作、预期答案或评分条件。停止后，执行器复制候选、注入隐藏检查，固定 pytest 配置并禁止候选 conftest 和插件自动加载；以 Python 隔离模式加载已安装的 pytest，再在禁网沙箱中执行。父进程读取 JUnit，核对可信测试名称、数量与结果；空测、跳过、假输出和非零退出不能通过。HumanEval 使用官方断言；第 33 题固定官方参考预期，避免函数与自己比较。

内建 `run_tests` 当前只接受 pytest/unittest，其他语言的完成验证需要相应验证器；`run_shell` 成功不能代替测试证据。公开 `run_tests` 是运行观察，不能直接决定训练成功奖励。`AsterEnv.reset` 每次复制初始仓库；Final 或预算结束时停止并等待子任务，宿主独立验证器检查最终候选。成功奖励还必须满足任务自身条件；没有独立验证器时不发正的任务成功奖励。中间成本按轮数归一化，终态统一评分，避免拖延结束比明确失败更划算。字段与回报解释见 [阶段 14](learning/14-memory-and-rollouts.md)。

候选与 pytest 仍在同一解释器，不能声称完全抗任意恶意 Python 篡改评分；沙箱保护宿主与评分真实性是不同边界，详见 [评分边界](grader-boundary.md)。当前适用于可信任务和小规模 rollout，尚未实现 SFT/GRPO。所有评测题与轨迹属于 evaluation split，后续训练须另建按仓库、问题家族隔离的数据，不能直接混用或简单改变量名当作新题。

## 指标、工件与历史

`steps` 是工具次数，`turns` 是模型决策轮次，`passed` 要求题目所有判定成立。真实 token 优先采用服务端 `total_tokens`，缺失时使用输入加输出；无 usage 的失败或重试不能覆盖远端全部潜在消耗。Pass@k 使用 `1 - C(n-c,k)/C(n,k)`，每条件一次不报 Pass@3，也不把工具开关当成重试。

`report.json` 记录逐题数据、Git 版本与源码/数据指纹；`attempts.jsonl` 保留逐次结果；`runs/` 保存候选、trace、checkpoint、diff 及评分输出。完整工件本机保留且忽略 Git，汇总报告提交 Git。报告展示全部尝试，并补充共同成功题成本；后者不能替代全量通过率。跨批次模型和网关波动使耗时、token 差异不能自动归因于某个修复。

v2、v3 报告原样保留，v3 最终为 57/58，早期另一源码批次为 58/58；它们不是同一版本的重试，不能合并为 Pass@2。v4 开发中的机制试跑另存为 `development-report.*`，当时案例尚未齐全，当前正式结果以 69 场景、97 次尝试为准。每版源代码和数据哈希均在报告中，不挑更高分版本充当当前成绩。
