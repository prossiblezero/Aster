# Aster v12：Harness 开销、执行环境与评测可信度（2026-10-17）

本文记录 v12 的问题、证据、改法和验证方式。代码在分支 `perf/harness-v12`，每项改动单独提交并打标签（`v12-overhead` … `v12-rc3`），可逐项回滚。评测数据见 [评测报告](../evaluations/harness-v12-20261017/REPORT.md)。

## 1. 问题是怎么发现的

v11 之后，Aster 每个请求的缓存和 token 已经与 pi、Codex 持平，但端到端时间仍约为它们的 2 倍。把 old20 每题的耗时拆成“网关测得的模型时间”和“其余时间”：

| | 任务总秒数 | 模型调用秒数 | 模型之外 |
| --- | ---: | ---: | ---: |
| Aster v11 | 5,816 | 2,153 | **3,663（63%）** |
| pi | 3,999 | 3,825 | 174 |

一道 sympy 题的轨迹显示，308 秒里工具执行只占 1 秒，其余主要是 harness 自己每步的记账。

## 2. 开销来源与修复

用脚本化模型驱动真实 Runtime（`scripts/bench_harness_overhead.py`，不调用模型），在 35 MB 合成仓库上做 cProfile，并在任务容器里复现（`scripts/bench_container.sh`）。

| 来源 | 证据 | 修复 | 提交 |
| --- | --- | --- | --- |
| 每次 checkpoint 重新哈希整个仓库两次 | `snapshot` + `fingerprint` 72 s/140 s | 按 `(mode, size, mtime_ns, ctime_ns, inode, dev)` 复用文件摘要，同 git index；3 秒 racy 窗口内修改的文件不缓存 | `v12-overhead` |
| 每次 checkpoint 重新脱敏并写入整仓初始文本（sympy 36 MB），还要再打包进会话快照 | 脱敏正则 42 s，会话提交 48 s | 初始文本按内容哈希只存一次（`runs/<run>/baseline-<sha>.json`），checkpoint v3 只存引用；读取时校验摘要，兼容 v1/v2 | `v12-overhead` |
| `Workspace.files` 对每个文件逐级构造 pathlib 父路径来判断 git 忽略 | 35 万次调用 | 单次 `scandir` 遍历，忽略状态沿目录树继承 | `v12-overhead` |
| 每个流式事件都重读整个 trace 来取 seq 和 hash | 每题上千个流事件，O(n²) | 缓存每个 run 的 trace 尾部，文件大小不符时（有其他写者）才重读；1,500 次 emit 用时 1.95 s → 0.09 s | `64f3ffe` |
| 容器 overlayfs 上每次 fsync 88–225 ms（宿主机 1.4 ms），每个 checkpoint 触发多次 | 真实运行中 checkpoint 1.08 s/次，每请求 4 次 | SQLite 改为常驻连接 + WAL/NORMAL；checkpoint 组提交（每次原子写入，fsync 间隔 ≥5 s，终态必 fsync）；请求快照和计时文件不 fsync | `v12-rc2` |

持久化语义：

- 进程崩溃不丢数据：原子 rename 加 SQLite WAL 保证。
- 断电最多丢失最近 5 秒的 checkpoint 进度。
- 工具执行前写入的 in-flight 标记、操作账本和记忆仍逐次 fsync，避免不确定的副作用被重放。

## 3. 执行环境问题

## 4. 评测可信度

**判分环境漂移。** 2026-10-17 主机网络会应答 `10.255.255.1`，requests 的 `TestTimeout` 用例依赖这个地址是黑洞，因此任何补丁都过不了，包括官方参考补丁。`tarpit_grade` 把 SWE-bench 判分容器放到子网 `10.255.255.0/24` 的网桥上，容器地址取自 `.128/25`，于是 `.1` 是没有主机的链路内地址，连接必然超时。在这个环境下复判历史补丁：参考补丁 2/2，pi 和 Codex 的结果与历史判分完全一致，说明修正没有改变可比性。

**留出集。** 30 道 new30 题从未用于开发，只用 v12 rc1 跑一次；Jest 支持是这次运行暴露问题后才加的，不回头重跑以免污染留出结论。

## 5. 第二天：轮次

**既有失败证据（rc4）。** 运行时为每个新失败的测试，在恢复到原始文本的副本上把同一条命令复跑一次，比较规范化后的失败签名（异常行，屏蔽内存地址和临时路径）。签名一致说明这次改动没有影响它。处理分两步：

1. 先作为证据告诉模型："如果它覆盖你要改的行为，说明还没修好；否则是既有失败，报告为未验证即可。"此时仍然阻塞完成。
2. 到最终交付时，同时满足以下条件才不再阻塞：
   - Agent 确实改过代码；
   - 至少被完成门禁带着这条证据拦过一次；
   - 在当前代码上重跑时仍以相同签名失败。

   之后任何编辑都会让这条证据失效。

第一版设计是"在原始代码上同样失败就直接放行"，被现有测试否决：仓库里本来就失败、正是任务要修的那个测试，会因此不经修复就被放过。这也是 Stage 3 被撤回的根本原因。

**精简系统提示词（rc5）。** 基础提示词是针对 old20 的失败一条条加上去的，例如"检查相关实现和边界""检查输入边界、输出位置、状态变化""运行所要求的表达式"。同一个模型，在所有 Agent 都能通过的 10 道题上，Aster 每次运行用 155–169 个请求，而 pi 是 113、Codex 是 115。精简后保留了安全规则、先看再改、改后验证、先复现、走真实代码路径和如实报告，删掉了这些额外检查。提示词从 359 token 降到 248 token。

## 6. 没解决的问题

- **轮次仍偏多。** 留出集上，去掉 regex-chess 后请求数是 pi 的 1.65 倍。约 20% 的轮次花在完成门禁暴露的、与改动无关的既有失败上。按运行时证据（原始代码上以相同签名失败）自动豁免是可行方向，但它改变完成语义，需要用户决定。
- **单次 20 题测不出 ±10% 的轮次变化。** 工具反馈类改动（编辑后回显、正则或上下文搜索）没有在单次运行中显示出可测收益。
