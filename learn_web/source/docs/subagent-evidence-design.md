# 子 Agent 证据交付改进与调研（2026-10-01）

2026-10-02 的精选证据实现见本文末节；前半部分保留首轮调研与实现依据。

这轮的重点是让已完成的调查真正可用，并纠正交付时序。保持单 Runtime 执行链、共享预算、最多一个写入者和现有快照恢复，不增加依赖、编排服务、角色搜索器或另一套会话状态。

## 从本项目失败出发

[原六题评测](../evaluations/subagent-light-20260930/REPORT.md)中，48 个子任务正常交付，但并行与 Solo 严格通过同为 5/12、行为通过同为 10/12。并行全队已知 token 为 Solo 的 2.50 倍、耗时合计为 2.39 倍；父方 64 次 read_file 中 62 次路径也被子任务读过。这是按路径统计，不能直接说 62 次都是不必要的相同行段。

沿工具输出、Worker 交付、完成检查和历史快照追踪后，发现四个可以直接修复的机制问题：

1. **模型看不到准确引用位置。** read_file 的底层 Outcome 已有 path/start/end/hash，但模型输出只包含纯文本，丢弃了这些元数据。模型必须数行或再搜索；旧评测大量扣分恰好来自引用位置。这是工具接口缺陷，修复同时惠及 Solo，必须保留新版 Solo 对照。
2. **调查交付缺少源码正文。** 子任务交付含自由文本结论和文件哈希，父任务严格观察门槛却只承认自己的文件工具调用。文件哈希可以判断版本，无法让父模型检查结论。单纯加强“不重复阅读”的提示无法补齐这个接口。
3. **结束时序可以丢工作。** 旧版仅对用户显式启动或绑定 todo 的活跃子任务阻止提前 Final；普通自主子任务会被收尾取消。另外，父模型请求发出后才完成的子任务可能在 finalize 中投递，此时刚生成的答案还没看过交付。
4. **续问准入遗漏 token 检查。** start 检查了父方 token 保留量，continue 只检查工具/轮次额度。结果可能先创建新的子运行，再在首次模型请求被团队 token 门槛拒绝。

## 落地实现

生产修改集中在 core/runtime.py、core/workers.py、context/prompt.py：

- 模型可见的 read_file 输出携带 path/start/end/source_sha256，每行显示真实行号。原始 Outcome.content 仍是文件文本，精确补丁和直接工具调用不受行号前缀污染。
- 每个 Worker 复用原有 working_memory 的短摘录，保存实际读取起点、证据 ID 和原观察长度。交付最多四个既有 500 字符摘录，包含行段、文件哈希和 truncated 标志；不会复制整条轨迹。敏感内容在截断前脱敏。每个路径目前只保留最后一次读取的开头，可能没有覆盖最终引用的关键代码；父方仍可针对这些缺口补问或读取，不能声称已消除所有重复。
- 自动交付和模型 worker_status 接收时，核对摘录仍匹配当前文件及哈希；匹配的源码观察可以满足父任务已有的 observed 门槛。界面轮询不消费它。不会将子任务 read_evidence 复制成父任务编辑权限，不会把子任务 verification 冒充父任务最终测试。
- 摘录存于原有不可变子快照。回到旧父分支只拿旧摘录；当前文件变化时仍保留历史内容并显示 stale_paths，不用新文件内容伪造旧观察。
- 所有仍运行的子任务都阻止过早 Final。新交付若在父模型请求期间到达，先让父模型看见交付，再生成最终答案。用户取消、总预算耗尽仍正常清理，不会无限等候。
- token 准入检查移到启动与续问共有的 limits 路径，预算不足的续问不创建新子记录。

自动派工仍默认关闭。调用方应给出独立目标、已知事实、交付格式和 parent_work；细小查询优先父方直接完成。涉及同一文件的紧密依赖修改继续采用一个写入者。增加 Agent 数量、固定辩论链、模型路由或自动 worktree 合并均缺少本项目证据支持。

## 验证边界

离线场景覆盖精确行号、带源码交付后零父读取即可通过观察门槛、界面轮询、失效证据、历史快照隔离、编辑前强制重读、父测试责任、普通子任务提前 Final、迟到交付及 token 不足续问。确定性场景只能证明工程机制，不能证明模型会正确使用它。

真实模型采用[新的三组协议](../evaluations/subagent-evidence-20261001/PROTOCOL.md)。源码、驱动和任务在运行前冻结，原历史报告保持原样；最终成绩及局限见[完整报告](../evaluations/subagent-evidence-20261001/REPORT.md)。旧并行/新 Solo/新并行严格通过为 3/6、4/6、4/6；新并行 token 比旧并行少 16.3%，但仍为新 Solo 的 2.80 倍，父方重读未下降。子任务 search 从 40 次降到 4 次，与直接提供行号减少定位工作的方向一致；没有单独消融，不能作独立因果归因。六道已见的只读调查题无法证明自主任务拆分、复杂写入、所有项目上的质量与成本收益。

## 2026-10-02：按结论选择源码，再交付

首轮的真实模型没有减少父方读取。500 字符的文件开头不一定包含关键分支，因此本轮补齐选择接口：只向子任务暴露 `worker_finish(answer, sources)`，一次完成答案与来源选择，不增加额外模型轮次。普通父任务和 Solo 的工具目录不增加它。

每段来源由子模型给出已有 `evidence_id`、起止行号及所支持的结论或答案 ID；程序读取既有工具事件中的原文，不接收模型抄写的源码。最多四段，合计 4,000 字符，不悄悄截断选中的论据。校验失败给出明确反馈，仍消耗正常团队额度。超长片段需要缩小，过期片段需要重新观察；正常提交不需要再次读取。

来源事件正文继续放在既有 EvidenceStore。子状态只新增读取证据 ID 到运行 ID 的索引，以及最终选中的短摘录，两者都随原快照保存。使用不可变证据 ID 而不是单独依赖工具调用 ID，防止旧分支恢复后重用某个调用 ID 时越过历史边界。续问保留可核验历史读取，清空上一轮的交付选择。旧检查点的默认空字段保持可读；旧文本交付与预算耗尽的部分结果继续使用首轮回退方式。

交付工具复用原有 Final 完成检查，不为未完成编辑、未完成测试或未关闭需求放行。父方仅得到源码观察，不获得编辑授权或测试状态。结论标签是模型主张，哈希只校验来源；即使正文正确，也可能推导错误。父方应对照支持行段检查推理，并对缺口或矛盾进行针对性补查。

验证采用[四组固定协议](../evaluations/subagent-selected-20261002/PROTOCOL.md)：本轮前并行、新 Solo、新双子任务，以及父方与一个子任务同时处理不同工作包。双子任务的前后对照隔离本轮变化；单子任务组探索调度差异。该实验仍使用六道已见只读题，不冒充自主拆分或独立保留集。未增加调度模型、框架、运行依赖或用户配置项。

## 2026-10-02 后续：按完成顺序消费结果

现有列表查询使用 `asyncio.wait` 的默认行为，先完成的工作必须等全部任务结束或超时才能返回父模型。本轮仅改用标准库 `FIRST_COMPLETED`，结合既有 `pending_handoffs` 区分未读结果与已消费结果。已就绪的未读结果立即返回；消费后，再查同一组编号会等待剩余任务。恢复后的消费依据子运行编号清理持久化待交付项，避免重复通知；普通 Final 仍检查所有活跃子任务。

模型输入边界把整份文件哈希表换为已读路径列表，保留答案、所选源码及其版本、过期路径和验证信息，完整证据仍由既有磁盘记录与界面使用。只改四个生产文件，净增 21 行，没有新增状态字段、工具、配置或依赖。[离线验证](../evaluations/subagent-incremental-20261002/REPORT.md)使用事件控制的真实 Runtime 测试和历史 12 条固定消息重放。服务探测仍为 401，本轮不报告新的模型质量或总成本收益。

## 服务恢复后的真实检验

[24 次真实复测](../evaluations/subagent-live-20261002/REPORT.md)以最后 21 行改动前的版本为基线。六题中增量返回均实际触发；当前双子任务行为完整通过 6/6，原严格评分 4/6，补充嵌套函数索引后单列结果 5/6。但其父模型调用从基线 7 次增至 23 次，已报告 token 增加 18.0%，相对 Solo 仍需 3.61 倍 token、2.58 倍时间。

三个实际问题比继续增加交付字段更值得优先处理：没有独立工作的父方被唤醒后反复加载工具与等待；无新要求的催促消息在子方最后一轮到达时触发续跑；模型选取过大或未读范围造成额外交付修正。与此同时，合法嵌套函数被旧评分器遗漏，说明引用失败必须先分辨测量缺口和模型错误。保留这轮全部首次成绩，未来验证调度取舍与评分器修订时另建批次。

## 显式选择等待条件

`worker_status` 增加可选 `wait_for="any" | "all"`，默认 any。父方还有独立工作时先做；首份结果能解锁后续工作时等 any；只剩最终整合时可显式等 all。两种模式共用原有 0–300 秒期限，超时或取消查询不会取消子任务，0 秒始终是快照。all 不会被已有未消费交付提前唤醒，单个 ID 的行为相同。实现只复用 `asyncio.wait` 的两个条件，四个生产文件净增 10 行，没有新增调度器、状态、配置或依赖。

[同版三组对照协议](../evaluations/subagent-wait-modes-20261002/PROTOCOL.md)固定 Solo、首次 any、首次 all，每题各两次，并在开跑前修订嵌套符号索引。测量同时包含首份交付抵达父方的时间、端到端时间和全队用量，不能仅凭少调用几次就认定更快。


[36 回合结果](../evaluations/subagent-wait-modes-20261002/REPORT.md)显示，首次 all 相对首次 any 总 token 减少 30.8%、配对耗时中位数减少 15.1%，父模型调用从 70 次降到 15 次。any 的 26 次补问/催促伴随 9 次额外子会话续跑，all 没有这些调用；运行时仍保留迟到真实指导的续跑能力。代价是首份交付额外等待中位数增加到 38.7 秒。all 的严格整题通过为 9/12、any 为 8/12，但严格事实数为 86/96、90/96，不能声称质量已经提高；两次重复不足以证明普遍收益。正式批次中的传输超时、SSL 失败和缺失用量均保留，未替换为成功重跑。

## 短引用、修正反馈与父方展示
