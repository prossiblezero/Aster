# Aster v15：模型看到什么，与模型无关的评测（2026-10-19）

v15 的主线是：**系统内部记录的东西，与给模型看的东西分开。** 审计、恢复、训练需要完整的结构化记录；模型做决策只需要内容本身，以及少数它必须引用的游标。这一轮的所有改动都与具体模型无关，并且同时在两个模型家族上验证：

- **gpt-5.6-luna**：OpenAI Responses 接口，流式；
- **deepseek-flash**：DeepSeek 官方 Chat Completions 接口，非流式。本地开源模型（例如 Qwen）也走这种接口。

代码在分支 `perf/harness-v14` 上，每项改动单独提交并打标签，用 `git switch -c <新分支> <标签>` 就能回到任意一步。

## 1. 证据与模型视图分离（`8fb273c`、`a774b25`，标签 `v15-search`、`v15-view`）

**问题。** 每条工具结果原样把内部记录发给模型，形如 `{"status", "evidence_id", "content", "observation": {"id": <64位>, ...}, "output_bytes", ...}`。在 fresh30b 上，这层外壳平均每条约 111 个 token（pi 是 2 个），并且会随历史在之后的每个请求里重复发送。代码和测试输出还被塞进 JSON 字符串，每个换行和引号都要转义。

**做法。**

- `context/view.py` 在组装请求时，把每条记录渲染成纯文本：
  - 出错时第一行是 `[error: tests_failed]` 这样的状态行；
  - 中间是原文；
  - 只有模型确实需要引用的游标（翻页位置、归档编号）才放进页脚。

  历史里照旧保存完整记录，审计、恢复、上下文预算和训练用的都是它。渲染是纯函数、确定性的，所以供应商的前缀缓存不受影响。
- 搜索结果按文件分组：文件名只写一次，`12:` 表示命中行，`11-` 表示上下文行，重叠的上下文只显示一次。搜索结果原本是模型携带的最大一类观察（占重复携带的工具结果的 36%），分组后少 38%。
- 状态提示从带两串 64 位哈希的 JSON 改成几行可读文字。

## 2. 视图上的补漏（`8d5dbe1`、`9d9ca97`、`ce2b79e`，标签 `v15-rc2`、`v15-ids`、`v15-rc3`）

| 问题 | 发现方式 | 修复 |
| --- | --- | --- |
| 空结果只显示 `[done]`，搜索和列目录没有结果时，读起来像“完成”而不是“没找到” | 检查 DeepSeek 轨迹 | 改为 `[no matches]`、`[no files]`、`[no output]` 等明确说法 |
| Chat Completions 和 Anthropic 格式的历史里，渲染时认不出工具名，所有结果都按未知工具处理（例如写文件后多出一行“已修改”） | 检查 DeepSeek 轨迹 | 三种协议的调用名都能解析 |
| 每条命令和测试结果末尾都带着“完整输出见 observation_read <64 位编号>”，即使显示的就是完整输出 | 离线统计：占工具结果 token 的 1.8%（GPT）到 5.2%（DeepSeek） | 只在内容因预算被截成片段时才显示这一行 |
| 归档编号是 64 位十六进制，每次约 30 个 token，还容易抄错 | 同上 | 给模型看 16 位前缀；`observation_read` 接受至少 12 位的唯一前缀，存储仍用完整编号 |
| 每条结果都带 `[evidence ...]` 引用，但只有加载了 `memory_store` 才用得上（fresh30b 上 900 个请求里一次都没加载过） | 同上 | 只有 `memory_store` 在工具表里时才显示 |

## 3. 工具定义精简（`3e51777`，标签 `v15-schemas`）

去掉 pydantic 自动生成的样板字段：

- 每个字段的 `title`；
- 内联的 `$defs`；
- 可选字段的 `anyOf [..., null]` 和 `default: null`；
- 模型不会触到的边界值（`minLength 1` 等）。

参数仍由 pydantic 模型校验，行为不变。核心工具定义从 1,975 降到 1,638 个 token。

在 GPT 上，这部分几乎总能命中缓存，所以省钱很少。它的意义在于开源模型：聊天模板会把工具定义原样塞进上下文，在 32k 窗口里每个 token 都占地方。

## 4. 执行与运行时

- **绝对路径写入的说明**（`f3f2a1f`）：命令在工作区副本中执行。程序按绝对路径（例如 `/app/summary.csv`）写入原工作区会得到权限错误。DeepSeek 曾为此花了约 60 个回合去排查“时有时无的权限问题”。现在遇到这种错误，系统会直接说明原因和做法：改用相对路径，或用 `write_file`。用户明确要求保留副本模型，不在真实工作区直接执行命令。
- **输出被截断时的恢复**（`7abdba4`，标签 `v15-length`）：在 DeepSeek 官方接口上，120 个 episode 里有 8 个以 `provider_error` 结束，原因都是推理把 8,192 个输出 token 用光了，没来得及给出任何动作（`finish_reason=length`）。现在的处理：
  - 被截断的内容仍然不执行，也不进入历史；
  - 系统追加一句“上次回复在输出上限处被截断，请简短推理后给出一个具体动作”，再请求一次；
  - 每次运行最多恢复两次，每次计一个回合，用量全部计入。

## 5. 评测方法

- **两个模型家族**：任何改动都要在两个模型上都不变差，才算是 harness 变好了，而不是迎合了某一个模型。
- **两套题**：old20（20 题）和 fresh30b（30 题）。两者都已用于开发，所以结论都是开发性质。
- **专项消融**：BigCodeBench 一度在 v15 上显得变差。为此在 20 道 BigCodeBench 题上做了消融：
  - DeepSeek 跑 4 个变体，各 3 次；
  - GPT 跑 2 个变体，各 2 次。

  4 个变体分别是 v14.2、v15-rc2、v15 但工具结果改回 JSON、v15 但状态提示改回 JSON。
- **最终对比**：v14.2 对 v15-rc3，在两个模型、两套题上同时间段成对运行。
- **排除供应商故障**：统计时剔除供应商报错导致的中断（`provider_error`，或请求错误 ≥3 次）。

## 6. 结论（详见评测报告 15.4）

合并两个模型、两套题，共 98 个题目样本：

- **每请求输入 −9.8%**，95% 置信区间 [−14.2%, −5.1%]。四组（两个模型 × 两套题）的方向全部一致。
- **质量不变**：独立通过每 30 题 +0.36，区间 [−1.17, +1.99]。BigCodeBench 专项消融也显示新视图没有造成损害。
- **总成本不显著**：−1.9%，区间 [−16.6%, +17.0%]。请求数主要取决于少数长任务和模型的解题路线；v14.2 在 DeepSeek 上因输出截断提前崩溃，失败得“便宜”，也压低了它的请求数。
- **鲁棒性提升**：输出截断恢复、Chat 历史的工具名解析、失败签名对相对临时路径的归一化，这三处都修掉了会让任务失败或白跑几十个回合的缺陷。
- **与 pi、Codex 比较**（GPT，fresh30b）：通过数相当，成本约为 pi 的 1.07 倍，低于 Codex。

## 7. 下一步

1. **门禁提示更具体**：没有测试套件时，提示模型用 `run_tests(code=...)` 写一个运行程序并断言输出的临时测试。
2. **截断时保留推理**：DeepSeek 文档要求带工具的请求回传全部推理内容。可以评估把被截断那次的推理保留在历史中（只保留推理，不保留残缺的动作），让下一次在此基础上继续，而不是从头再想一遍。
3. **评测**：每种配置至少重复两次；凡是能离线计算的指标（如每请求输入）都离线算，这类指标波动小得多。
