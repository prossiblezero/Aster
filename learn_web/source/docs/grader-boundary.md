# 自动评分的实现与边界

代码任务的得分来自 `scripts/benchmark_support.py::external_check`。Agent 停止后，评测器复制候选仓库，再注入固定的隐藏测试；原候选仓库不会收到隐藏测试或测试报告。公开测试通过、Agent 声称完成、进程打印 `passed`，都不能单独决定这个得分。

评测器使用环境中安装的 pytest，关闭第三方插件自动发现和候选仓库的 `conftest.py`，指定评测器自己的配置。`python -I` 避免候选仓库用同名 `pytest.py` 替换测试入口。测试仍在 Landlock/seccomp 沙箱中运行，网络关闭。沙箱只允许将本次新建的 JUnit XML 报告回写到可丢弃副本；候选文件和隐藏检查发生修改时，整个回写被拒绝。stdout 保留用于解释失败，评分不扫描其中的“通过”字样。

父进程调用 `src/aster/testing.py::parse_junit` 读取结构化报告，再核对可信隐藏测试文件中声明的测试名称。当前数据集的隐藏检查都是顶层 `test_fix` 和 `test_regression` 函数；选择单项检查时只要求该项，运行全部检查时要求两项都存在且通过。报告缺失、损坏、测试数量不符、提前退出、跳过、预期失败或实际失败，均不能得到任务通过分。如果后续引入测试类、动态收集或参数化测试，需要同时显式定义预期测试清单，不能放松为“任意一条通过即可”。

报告中的字段如下：

| 字段 | 含义 |
| --- | --- |
| `tests.expected` | 本次选择的可信隐藏测试数 |
| `tests.executed` | 报告中实际产生结果的测试条目数，可能含跳过或失败 |
| `tests.passed` | 没有 failure、error、skipped 标记的条目数 |
| `grader_reason` | 进程/沙箱失败、隐藏测试不完整或全部通过的原因 |
| `passed` | 进程成功，且预期的所有隐藏测试均完整通过 |

普通仓库的 `run_tests` 和隐藏评分的要求不同：普通测试允许部分可选测试跳过，但至少有一项真正通过；隐藏评分要求全部选定检查通过。二者共享报告解析，分别保留各自的判定规则。

这个实现防止已复现的假输出、`pytest.exit(..., returncode=0)` 和跳过关键检查造成假绿，也防止候选提交中预先放置的旧报告被当作本次结果。随机报告名称仅用于区分本次运行，不是报告防伪机制。候选 Python 代码与 pytest 仍在同一个解释器进程中，恶意代码可能修改运行时对象、干扰测试框架或主动伪造报告；不能将此验证器描述为对任意恶意 Python 完全抗作弊。沙箱保护宿主机的边界与评分报告的真实性是两个问题。

后训练接入时应保留这一限制：当前可用于可信任务集和小规模 rollout，继续记录失败样本及奖励异常；如需要对抗主动修改评分器的策略，应另行实现候选执行进程与可信断言进程的隔离，而不是只增加一条输出正则。
