# Aster v13：执行能力、验证边界与防过拟合评测（2026-10-18）

本文记录 v13 改了什么、为什么改、哪些尝试被否决，以及怎样确认改进不是“过拟合评测集”。代码在分支 `perf/harness-v12`，标签 `v13-rc1` … `v13-rc3`、`v13-1` 和 `v13-2`，每项改动单独提交。评测数据见 [评测报告](../evaluations/harness-v12-20261017/REPORT.md) 第 10–11 节。

## 1. 防过拟合的评测协议

v12 的所有调整都在 old20 上完成，new30 跑过两次（rc1 一次、rc5 一次确认）。到 v13 时，new30 也已经被看过，不能再充当留出集。因此在动 v13 之前先做了三件事：

1. **重新抽一套新题 fresh30**（`datasets/fresh30-20261018`）。构成与 new30 相同：
   - 8 道 SWE-bench Verified、10 道 Aider Polyglot、10 道 BigCodeBench、2 道 Terminal-Bench；
   - 抽题规则：按固定种子 `20261018:` 的哈希排序，每个仓库或类别取排第一的题；
   - 排除所有曾经用过的题（109 道）。
2. **预检后冻结。** 每道题都确认初始代码判分失败、参考答案判分通过；仓库题在 tarpit 网络上判分。BigCodeBench/634 的参考答案在本环境中失败，按排序换成下一道（452）。预检完成后打标签 `fresh30-frozen`，此后不再改题。
3. **规定 fresh30 的用法。**
   - 只在开发集上确定候选版本，之后才在 fresh30 上跑；跑完不再根据结果改代码。
   - 同一天在同一套 runner 上比较 Aster v12-final、Aster v13、pi 和 Codex。
   - 两个 Aster 版本各跑两次，按题配对，用 bootstrap 给出置信区间（`evaluations/fresh30-20261018/analyze.py`）。
   - 主机上同时运行的任务总数固定为 6，以保证时间可比。

开发集（old20、new30）上的结果只用来发现缺陷，不作为结论。

## 2. 新能力

### 2.1 跨工具调用存活的服务（`service_start` / `service_status` / `service_stop`）

`run_shell` 的每条命令都在暂存副本中运行，结束时清理整个进程组。因此 gRPC、HTTP 这类需要常驻的服务无法交付。old20 中的 kv-store-grpc 要求交付后服务仍在运行，v12 的 4 次运行（c2、rc3、rc4、rc5）全部失败。

`service_start` 的运行方式：

- 用同一个 Landlock/seccomp 启动器，在工作区本身启动命令，放在独立会话中（`start_new_session`）；服务需要看到之后的代码修改，所以不经过副本。
- 日志写到工作区之外。
- 启动后等待 2 秒，报告进程是否存活以及日志末尾。
- 任务结束时按 SIGTERM、SIGKILL 的顺序停止。`keep_running=true` 的服务会保留，最终答案会列出它们。

权限上，必须开启沙箱、不是只读或计划模式、没有写入范围限制，并且需要审批。它不在核心工具集里，通过 `tool_load` 按需加载，不增加每次请求的 token。

在真实的 kv-store-grpc 任务镜像中验证过：服务在 Agent 退出后仍然存活，判分请求返回 200。v13 的两次 old20 运行都通过了这道题，分别用了 9 和 12 个请求（v12 为 13–19 个）。

### 2.2 按退出码判定的项目测试命令

`run_tests` 原来只接受能产出逐用例结果的框架，包括 pytest、unittest、node --test、Jest 和 go test。C++、COBOL 这类项目的 `make test`、`cmake --build && ctest` 无法形成正式验证，模型只能用 `run_shell` 跑，完成门禁随后又因为“没有正式验证”把它打回。

v13 让项目自带的构建加测试命令进入正式验证，规则如下：

- 在一次性副本中运行，不改动工作区；
- 退出码为 0 即通过，非 0 即失败；
- 失败只把验证状态置为失败，不记成必须由同一条命令消除的“失败测试”（v13.1 起，原因见第 8 节）；
- 只接受用 `&&` 串联的普通命令，其中至少有一步是测试工具（make、ctest、cargo、npm 等）或测试可执行文件；
- 编译器步骤（g++、javac 等）可以出现在链中。

不接受的情况和原因：

| 写法 | 原因 |
| --- | --- |
| `ctest \| tail -20` | 管道的退出码来自 `tail`，测试失败也会显示通过 |
| `make test \|\| true`、`make test; true` | 退出码被后一条命令替换 |
| `for f in test/*.scm; do ...; done` | 这是模型临时写的检查脚本，不是项目测试，应该走 `run_shell` |
| `python3 interp.py test/a.scm` | 普通程序运行，参数里出现 test 不代表它是测试 |

第一版（rc1）用“命令里出现 test 等关键词”来识别，在 old20 上把一个 shell 循环当成了测试，导致 scheme 解释器题一直被门禁打回。rc2 改成上面的逐步解析。

## 3. 修复的缺陷

### 3.1 测试留下了不发布的文件，结果被整个丢弃

测试在暂存副本中运行，副本里出现 `.git/index`、符号链接这类 Aster 不发布的文件时，运行器会以 `sandbox_protected_output` 拒绝整次运行，测试报告也一并丢弃。matplotlib 的测试会触发这种情况：

- 两个 Aster 版本在 matplotlib-26291 上都出现 5–9 次；
- 模型看到的是测试全部通过，完成门禁却看不到这份证据，一直报告“先前失败的测试仍未解决”。

修复：运行器在校验输出之前增加一个钩子 `_collected`，测试工具借此先取走报告。由于副本本来就会被丢弃，拒绝发布的文件不影响证据的有效性。对应的回归测试会在副本中写入 `.git/index`。

### 3.2 只含断言的内联脚本被判为“没有收集到测试”

模型常把 `run_tests(code=...)` 写成顶层断言脚本，没有 `def test_*`。这种脚本被报告为 `no_tests_collected` 或收集错误，模型随后要再花一轮把它改写成测试函数。在两次 new30 运行中，这种情况各有 5–7 次。

rc3 的处理：

- 代码中没有测试定义、但至少有一条 `assert` 时，把它放进单独的文件，通过 `runpy` 作为一个测试 `InlineScript::test_script` 运行；
- 回溯指向模型自己的代码行；
- `SystemExit(0)` 视为通过。

没有 `assert` 的脚本仍然判为没有测试，因为打印“10 tests passed”不能算证据，现有测试也保证了这一点。

v13.2 补充：所有脚本共用 `InlineScript::test_script` 这一个 id，它不是真正的用例身份。如果把失败记成必须消除的义务，后面任何一个能通过的脚本都能把它清掉，这与第 4 节的原则矛盾；old20 上的 custom-memory-heap-crash 还因此一直被门禁卡住。因此脚本失败与退出码失败一样，只把验证状态置为失败。

### 3.3 既有失败的门禁提示

既有失败（在原始代码上以相同签名失败）只有在“当前代码上重跑仍相同”时才不再阻塞。模型如果在门禁提示之后又改了代码，旧的重跑结果就失效了。原来的提示只说“再结束一次”，模型照做后仍被打回。提示现在改为“如果之后改过代码，先重跑这些测试”。

## 4. 被否决的尝试

**“最新结果覆盖”。** 为了解决 aider-cpp-meetup 的问题（cmake 构建失败后，模型改用 g++ 命令跑通，但旧命令的失败记录一直留着），曾让同类证据中最新的一次覆盖之前的失败：退出码命令以最后一次为准，内联测试以最后一版为准。

全量回归中有 3 个已有测试否决了它，它们保护的正是这条原则：只有让同一个检查重新通过，才能消除一条失败；写一个能通过的新测试不算。如果允许覆盖，模型可以写一个必然通过的检查，把真实的失败清掉。这一改动已撤回，改为 3.3 的提示。

## 5. 时延：分析后没有改

| 阶段（new30，v13-rc2） | 每次耗时 | 每题合计 |
| --- | ---: | ---: |
| checkpoint（约 4 次/请求） | 93 ms | 4.8 s |
| prepare_request | 189 ms | 2.4 s |
| context_build | 128 ms | 1.6 s |
| 暂存副本 | 74 ms | 0.6 s |

- checkpoint、prepare_request 和 context_build 三项合计约占任务时间的 7%。
- 把一批工具调用的 checkpoint 合并成一次，估计每 30 题能省约 25 秒；`run_tests` 的双重复制约 6 秒。
- 这两项的收益都不到 1%，而改动 checkpoint 粒度会影响崩溃恢复语义，因此不做。

另外发现，两个评测各开 6 个并发、同时在 24 核机器上运行时，所有 harness 计时都会变成原来的约 3 倍：checkpoint 从 126 ms 升到 365 ms，暂存副本从 66 ms 升到 539 ms。这是资源争用，不是代码退化。评测 runner 现在把并发数写进 manifest（`--concurrency`），主机上同时运行的任务总数保持为 6。

## 6. CI 中的开销回归门禁

`tests/test_harness_budget.py`（core 标记，CI 必跑）用脚本化模型在 200 个文件的仓库上跑 16 步，统计以下两项：

- 工作区哈希的字节数：预算为仓库大小的 6 倍，当前约 4 倍；
- fsync 次数：预算为每轮 4 次，当前约 3 次。

它统计的是次数而不是时间，所以不受 CI 机器性能抖动影响。在 v11 代码上它会失败：哈希 136 MB，相当于仓库大小的 165 倍，fsync 137 次。

## 7. 成本口径

加权成本 =（未缓存输入 × 1.25 + 缓存输入 × 0.125 + 输出 × 10）/ 1e6。这个比例就是 GPT-5 公开价目表上每百万 token 的美元价格，因此加权成本可以理解为“按公开价目折算的美元”。供应商的实际账单无法取得，本项目的所有成本数字都是这种折算值，不是实付金额。

## 8. 留出集结论与 v13.1

fresh30 的完整数据见评测报告第 11 节。要点：

- **v13-rc3 相对 v12 没有质量提升。** 按题配对：
  - 独立通过 −1，95% 置信区间 [−3, +1]；
  - 正常交付 −2，区间 [−4.5, 0]；
  - 请求 −8%、成本 −9%，区间上界都略过 0。
- **v13 的收益不在通过率上。**
  - 新能力：常驻服务，使 old20 上的 kv-store-grpc 首次通过；C++ 和 Make 类项目也能形成正式验证。
  - 工程化：CI 中的开销预算测试、评测 runner 的并发隔离、留出集协议本身。
  - 开发集 old20 上的 16/20 是 Aster 的最好成绩，但开发集不作结论。
- **留出轨迹暴露了一个 v13 引入的缺陷。** 按退出码判定的失败原来记在命令字符串下。命令因为调用方式出错而失败时（例如链接输出到不可写的 `/tmp`），之后无论怎么跑都无法消除这条失败，任务只能以门禁失败结束。
- **v13.1 的修法：** 这类失败只影响验证状态，不再记成必须消除的义务。

v13.2 把同样的规则推广到断言脚本（见 3.2）。概括起来：只有带真实用例身份的失败才必须由同一个用例重新通过来消除，没有身份的证据只影响验证状态。

这与第 4 节“同一个检查重新通过才能消除失败”并不矛盾。那条原则的前提是失败有明确的身份（某个用例）；退出码证据没有用例身份，也就谈不上“同一个检查”。

这个缺陷是看了留出集轨迹才修的，所以 v13.1 不对 fresh30 做任何声明，只在开发集上验证。今后若要再声明留出成绩，需要重新抽一套题。
