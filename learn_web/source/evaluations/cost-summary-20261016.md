# Aster 降本工作总结：c6b651d → v11

整理于 2026-10-17，覆盖 2026-10-12 以来的缓存与轮次优化。最终保留 v9/v10 上下文策略和 v11 Stage 1、2，撤掉 Stage 3，并修复请求存档误伤推理密文的问题。在同一 old20 开发子集的首次尝试中，含后台记忆的加权成本从 **7.158624 降到 3.098510（−56.7%）**，请求从 **405 降到 339（−16.3%）**；独立通过从 **15/20 变为 14/20**，正常交付且通过仍为 **12/20**。这些结果支持成本机制有所改善，不足以证明质量不变或稳定排名。

主表均取 old20 的首次 20 题，不合并重复尝试的最好结果。模型为 `gpt-5.6-luna`，Responses / medium，64000 上下文、8192 输出上限、900 秒/题、4 CPU / 8 GiB、6 路并发；Aster 使用单 Agent，自动记忆开启。请求计入原生重试、失败、超时和后台记忆，token 仅计实际返回的用量，缺失用量不估填。

**v9：先消除历史改写和计量误差。** 原实现会反复裁剪、改写已发送历史，本地估算把推理密文当普通文本，估算中位数约为实际的 1.78 倍，且未发送缓存键。改为会话缓存键、回执校准、只追加历史，以及在观察首次进入上下文时限制输出体积。前台改写从 146/368 降至 2/360；这里使用排除最后一项动态消息的历史口径，不代表完整前缀从未改变。输入量增加导致总 token 反而上涨，说明仅减少改写不等于请求总量下降。依据：[方案](../docs/context-cache-plan.md)、[实施与评测报告](context-cache-20261013/REPORT.md)。

**v10：消除替换式尾部消息。** 每轮重建的状态尾部可能跨过供应商缓存块边界，下一轮替换后无法复用快照。改为状态变化时追加上下文更新条目，并保留已发送内容。前台缓存占比从 72.30% 升至 88.53%，完整前缀改写从 360/360 降至 4/358，后者均为显式压缩；主表含后台，因此显示 72.09% → 88.00%。此前的 81 次付费探针中，纯追加且带缓存键的 13 次有效后续请求均命中至少 85% 的稳定前缀，这些后续请求的缓存占比为 87.8%；替换约 1300 token 尾部的 7 次有效后续请求均未达到该命中标准，对应缓存占比为 32.8%。12 次 403/503 已另列并排除，探针结论仅适用于当时的供应商链路，不能据此断言其他供应商的内部缓存实现。依据：[方案及探针解释](../docs/context-state-plan.md)、[探针原始结果](cache-probe-20261014/results.jsonl)、[汇总脚本](cache-probe-20261014/summarize_probe.py)、[v10 报告](context-state-20261014/REPORT.md)。本次只读取已有探针数据。

**v11 Stage 1、2：减少不必要的交互。** 自己成功编辑后保留读取凭证，外部修改仍要求重读；搜索增加可选正则，一次覆盖多个名称。前台被拦编辑 11 → 0，最终转录中的模型轮数 358 → 304，纯重读 27 → 8。不过原定纯重读门槛是 ≤5，第一轮整体验收未通过；后来用户明确豁免这一项并授权第二轮，原失败结论仍保留。第一轮前台成本从 3.524968 降至 2.966459，但约 84.6% 的净节省来自解释器因路径权限问题提前停止；排除该题后，其余 19 题仅下降约 2.9%。不能将全部降本归因为本次机制优化。依据：[方案](../docs/turn-reduction-plan.md)、[第一轮报告](turn-reduction-20261015/REPORT-round1.md)、[成本拆分](turn-reduction-20261015/comparison-round1.json)、[第二轮冻结协议](turn-reduction-20261015/PROTOCOL.md)。

**质量如何解读。** 历史六轮同一组 20 题通过数为 12、14、15、15、13、13。其中 14 道稳定题由 10 道稳定通过和 4 道稳定失败组成；另 6 道波动题累计通过 21/36。因此 v11 每轮先跑 20 题，再让波动题各追加两次，费用比较始终只取首次 20 题；稳定通过题若恰有一道失败，只允许补两次且两次均通过。第一轮稳定通过组 10/10、稳定失败组 0/4、波动组 12/18；第二轮波动组 11/18，Xarray 唯一稳定通过题首次失败，补测两次均通过。两轮的质量门槛通过，不表示通过率相同的统计证明；20 题上相差两题就是 10 个百分点，既有波动、无配对重复的主表不能支持 ±2 题差别来自优化的结论。分组和规则见[方案第 1.3、7 节](../docs/turn-reduction-plan.md)。

**撤掉的 Stage 3。** 它在新测试失败时复跑未修改基线，再允许模型声明 pre-existing。第二轮质量门槛通过，但首次 20 题有 46 次请求异常（第一轮为 3 次），4 题以 `provider_error` 提前终止；排除这 4 题后，两轮的模型轮数为 252 → 230、全部请求为 279 → 281，无法证明稳定降本。Requests-2931 带失败轮数反而从 3 增至 9；pytest-10356 中与任务相关的测试也被运行时接受为 pre-existing，直到用户人工复核才否决。“基线上失败”不足以证明任务无关。故以 `30bd0b3` 撤销源码和测试，保留 Stage 1、2；Stage 3 原实现仍在 `v11-stage3`，评测证据未撤销。依据：[第二轮报告](turn-reduction-20261015/REPORT-round2.md)、[审计补充](turn-reduction-20261015/audit-notes-round2.md)、[人工核对](turn-reduction-20261015/preexisting-review-round2.json)、[收尾方案](../docs/v11-closeout-plan.md)。

第二轮还暴露了请求存档对协议密文误脱敏的问题。该问题已在 `v11-final-fix1` 修复，5 个出错请求离线重放均与实际出站内容一致；普通凭证脱敏保留，冻结审计中的证据失败结论不变。修复不改变模型请求和 Agent 决策，没有新付费成绩。实现与验证见[记录](turn-reduction-20261015/IMPLEMENTATION.md)、[检查结果](turn-reduction-20261015/closeout-stageB-checks.json)。

**限制和剩余差距。** old20 是反复接触的开发子集，不是未见测试集；主表每个版本仅一次运行，重复尝试只检验 v11 的波动题；加权成本不是账单；pi、Codex 使用历史运行；各轮供应商故障率不同，缺失用量不能当作零收费。v11 全部请求仍是 pi 的 1.41 倍、Codex 的 1.33 倍，加权成本分别为 1.37 倍、1.32 倍。尚有读取范围偏小、探索文件较多、工具输出包装和完成门禁带来的轮次；这些因素在[方案第 8 节](../docs/turn-reduction-plan.md)只作问题线索，本次没有继续改变它们。沙箱路径权限问题也仍待单独修复，不能把异常提前停止包装为效率提升。
