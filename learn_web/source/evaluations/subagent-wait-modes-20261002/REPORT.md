# 显式 any / all 等待：36 回合真实对照

本轮保留 `any` 为默认，新增显式 `all`，生产代码净增 **10 行**。在父方只剩最终整合的本批任务里，首次等齐相对首次等任一结果：全队已报告 token 减少 **30.8%**，配对耗时中位数减少 **15.1%**，父模型调用从 **70 次降至 15 次**。代价是首份交付在子方完成后额外等待的中位数从 **0.081 秒增至 38.7 秒**。

这支持按工作条件选择等待方式：有独立工作就继续做；早期结果能解锁工作时用默认 any；只剩整合时显式用 all。结果不足以证明正确率提高或支持默认启用委派。在正常完成的 11 对任务中，all 相对 Solo 的耗时比值中位数仍为 **2.58 倍**，已报告 token 比值中位数为 **3.50 倍**。

## 实现

```json
{"worker_id":["worker-a","worker-b"],"wait_seconds":300,"wait_for":"all"}
```

`wait_for` 只允许 any/all，省略时为 any。复用现有 `asyncio.wait`，按参数选择 FIRST_COMPLETED 或 ALL_COMPLETED。all 不被已有未消费交付提前唤醒；两种模式共用一个期限，0 秒始终立即返回，单个 ID 行为相同。超时或取消查询不取消子任务，外层 finished 仍只表示选中任务均已终止，须检查各项成功、失败、取消或缺失状态。

四个生产文件增加 22 行、删除 12 行；55 个文件、12,014 行变为 55 个文件、12,024 行。没有新增运行依赖、调度器、状态字段、用户配置或工具。交付消费、恢复、源码观察权限及父方最终测试门槛沿用原实现。具体差异见 [candidate.patch](candidate.patch)。

## 冻结的比较条件

三组都使用同一个候选源码、模型配置、六道已见只读调查/受限审查题、两个工作包和团队预算，每组每题预定两次，共 36 个首次回合。Solo 指本候选版本由父方独立处理全部问题，不是另一套单代理实现。

- Solo：不创建子任务。
- any：两个 Explore 并发，首次真实 Runtime 状态工具调用显式 any。
- all：相同委派，首次工具调用仅把等待条件改为 all。

之后模型自主整合。本实验没有把整段运行强制锁在一种模式：any 组后续四次状态查询中，三次显式选 all、一次使用 any。也不能据此声称模型已经会自主选择最佳初次等待条件。

回合串行，回合内子任务真实并发，三组顺序平衡。每回合限制为全队 36 次模型请求、60 次工具、300,000 已报告 token、600 秒；Memory 和网络工具关闭，严格完成门槛开启。模型响应报告名称为 gpt-5.6-luna，使用 Responses 流式接口；这不验证供应商内部路由。

开跑前修正旧评分索引遗漏嵌套函数的问题，保留旧索引全部范围，通过 48 个可执行事实、42 个负例、40 个新增嵌套符号引用正例。行为 oracle 和评分规则未变，只补齐合法符号索引；没有修改历史报告的冻结分数。详见 [协议](PROTOCOL.md)、[预检](PREFLIGHT.json)和[冻结清单](FREEZE.json)。

## 结果

| 组 | 严格整题通过 | 严格事实正确 | 纯行为整题通过 | 已报告 token | 耗时合计（秒） | 父模型调用 |
|---|---:|---:|---:|---:|---:|---:|
| Solo | 7/12 | 83/96 | 7/12 | 358,451* | 621.4* | 32 |
| any | 8/12 | 90/96 | 9/12 | 2,095,034 | 2,040.8 | 70 |
| all | 9/12 | 86/96 | 10/12 | 1,449,076 | 1,726.5 | 15 |

严格通过要求行为值、审查题的回归判断、合法引用、问题 ID、可解析 JSON、正常父方完成及源文件完整性全部通过。纯行为评分只忽略引用定位，仍要求 JSON 可解析、完整答案和正常完成。它不修补模型输出。

\* Solo 第二遍 Django 审查在约 2.55 秒时因 SSL 连接错误终止，没有答案或 usage。它保留为首次失败，不能当作模型能力错误、一次快速解题或零 token 请求。表中 token 是已报告量，不是完整费用。any 第一遍 Django 调查还包含一次约 120 秒传输超时及成功重试，该次失败尝试的 usage 同样未知。

all 相对 any 的配对结果：

| 指标 | 结果 |
|---|---:|
| 总已报告 token | −30.8% |
| 每题每次的 token 比值中位数 | 0.582，即 −41.8% |
| 总耗时 | −15.4% |
| 每题每次的耗时比值中位数 | 0.849，即 −15.1% |
| 更快 / 已报告 token 更少 | 8/12 对 / 9/12 对 |
| 严格通过配对胜 / 负 / 平 | 4 / 3 / 5 |
| 全队模型请求 | 184 → 124 |
| 父模型请求 | 70 → 15 |
| 父方累计输入 token | 788,867 → 183,759 |

第一遍 all/any 严格通过 5/6、3/6；第二遍为 4/6、5/6，方向反转。整题通过的总差仅一题，且 all 的严格事实数反而更低，不能说准确率已经提升。all 一次无效 JSON 使该回合八条事实均无法正常评分，这是整题率和事实率方向不一致的主要原因。

all 与 Solo 的主配对耗时比值中位数为 2.70；排除非正常父运行后的 11 对为 2.58。token 配对只计算两组都有已报告量的 11 对，中位数为 3.50。这个补充分析不删除主结果中的 SSL 失败，也不把缺失用量补成零。

## 首份交付与最终完成

以下均为回合内测量后再取中位数。跨组子模型自身推理时长不同，不能直接把两组首个子完成时间之差归因于等待条件。

| 相对回合开始的时刻 / 间隔 | any | all |
|---|---:|---:|
| 首个子任务完成 | 47.2 秒 | 40.1 秒 |
| 父方首次收到交付 | 47.3 秒 | 97.5 秒 |
| 首个子任务终止 → 父方收到交付的间隔 | 0.081 秒 | 38.7 秒 |
| 父方首次模型响应 | 58.6 秒 | 127.1 秒 |

any 的 12 次初次等待都返回了一个交付与另一个仍运行的任务。all 的 12 次初次等待都等到了两个任务结束，没有依赖超时返回。any 在最后一个子任务完成前收到 41 次父模型响应，all 为 0；提前响应不自动意味着有效工作已经完成。

因此 all 会推迟父方利用第一份结果，甚至可推迟超过一分钟。需要以首份结果驱动后续实现或反馈的场景应保留 any；这批纯整合任务的最终耗时收益不能推广到那类工作。

## 协调开销从哪里来

any 组共发出 26 次 worker_message：21 次接受、5 次因 worker_finished 被拒绝，均未显式请求 resume。已接受的消息中有在最后响应期间到达的要求，既有机制为此产生了 9 次子会话续跑。因此 any 有 33 个子运行：24 次初始委派和 9 次续跑；32 个正常完成，一个续跑在执行工具前被 team_token_limit 停止。all 则只有 24 个初始子运行，全部正常完成。

例如第一遍 OpenLibrary 调查，父方连续发出五条“请现在交付”之类的催促。两遍该题的 any/all 父模型调用分别为 9/1、10/1，耗时为 99.4/52.9 秒、121.3/65.0 秒。第二遍两组都严格通过，是减少协调消耗的具体正例。

不能把全部额外父调用都归为浪费：any 也进行了源码复核。父方此前已被子方读过的源码行数为 any 2,311、all 1,034，重叠读取本身不证明无意义。运行时仍保留迟到真实指导的续跑能力，本次通过选择等待条件减少触发机会，没有丢弃子方收到的消息。

## 失败与剩余问题

all 的三次失败分别是：第一遍 Django 审查把 `&nbsp;` 放进 JSON 值而导致解析失败；第二遍 OpenLibrary 审查的 c1 行为值错误；第二遍会话调查 v2 引用行号不在所写符号内。后两种分别是推理错误、引用错误，均未放宽评分。

any 有三个回合的行为值错误，以及一个 OpenLibrary 调查回合把多个函数名拼接成一个 symbol，导致三条引用不合法。Solo 有四个正常完成回合的行为错误和一个上述 SSL 连接失败。全部具体问题保存在 [diagnostics.json](diagnostics.json)。

精选来源的修正轮次仍在：all 的 worker_finish 共 39 次尝试、24 次接受，另有 9 次未读范围和 6 次超长来源拒绝；any 为 37 次尝试、25 次接受，另有 8 次未读范围和 4 次超长拒绝。这不属于此次等待条件修复的收益，后续可单独改进反馈与来源选择。

本批 340 次模型请求中，339 次获得成功响应，一次在 SSL 层失败。记录到 340 次 HTTP 诊断（339 成功、1 传输失败），SSL 失败另外没有产生 HTTP 尝试诊断。正式回合共报告 3,902,561 token，健康请求另外报告 4,396；一条失败 HTTP 尝试和一个 SSL 请求缺失用量，不能将其当零成本。35 个父运行正常完成、一个失败；工作区、源码和已报告 usage 对账全部通过。

六道题都是开发期已见样本，每题每组仅两次。初次调度由驱动指定，不涵盖自主拆分、写入合并、依赖早期结果的流水工作或默认启用委派。一次传输超时也影响 any 的总耗时；保留它的事实，不把总量差异全解释成调度收益。
