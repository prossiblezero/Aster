### 可直接从轨迹确认的原因

1. **交付重试**：七次拒绝中六次是超过 4,000 字符（Django 四次、Boltons 和 ItsDangerous 各一次），一次是引用范围超出已读行段。重新提交会再次生成整份答案和支付上下文输入。
2. **语义与格式交接**：Django 子方解释正确但数组嵌套错误，父方继承；Session 子方的状态累计漏了一次贡献，父方也继承。More Itertools 子方给出的 maxsplit 边界答案正确，被父方改错。
3. **引用契约**：Django 和 Cachetools 把多个方法拼成单个 symbol，行为正确仍不满足引用契约。这与查不到源码或引用索引错误不同。
4. **固定双孩子成本**：多数题父方仅 1–2 次调用，但两个孩子各自阅读、检查、交付。全队 114 次调用对 Solo 34 次，仅减少父输入不足以抵偿成本。

归因中可解析的单份子报告覆盖 72 个事实：69 个正确答案被保留、2 个子错误被继承、1 个正确答案被父方改错。另八个事实没有可独立解析的子报告，不能据此判断谁修复了错误。

结论：保留基线与全部失败。先验证小范围的交付/核验改动，再比较父方和一个孩子共同完成两个工作包；不引入角色训练、图路由或常驻 critic。

## r2 准备：父方与一个孩子并行

r1 前四题配对的全队 token 比率中位数仍为 2.74，继续验证先前登记的节点简化方案。使用同一题目中的第一个工作包交给孩子，父方承担第二包再整合，所有题采用同一规则；不读取隐藏答案选择分工。父方在孩子运行期间开始工作，用已有自动交付或 worker_status 取回结论。计划同时在通用父方提示中明确优先保留一个独立工作包，只有额外实质性交付才增加孩子。没有新配置、权限或运行组件。

这验证的是明确分工下的协作拓扑，不是自主拆分能力。r1 已使用独立源码快照，工作区为下一轮准备提示不影响正在运行的回合；评测驱动在 r1 完整结束后才更新及重新冻结。

补读 2026-10-02 的单孩子负结果：仅减少节点仍花费当时 Solo 的 3.36 倍 token；父方重复探索，并通过懒加载获取等待工具。r2 因此明确父方在子任务运行期间完成自己的 parent_work，并在当前分支已有子会话时直接暴露 worker_status。增加两行已有工具选择逻辑；其他管理工具继续按需加载。现有续问/分支测试新增可见性断言，在旧逻辑下确实失败，同时覆盖恢复后可见、回到委派前不可见。

另一个实际成本是命令形式：r0 的 run_shell 有 16 次 team、3 次 Solo 因缺少交互审批而被拒绝，大多使用 heredoc；部分 `python -c` 因双引号内的 `$` 也被识别为 shell 展开。只读沙箱本来允许直接命令，并非禁止一切运行。r2 仅在既有工具描述中说明 Python 探针可用单引号包住一个 `python -c` 参数；双方得到相同说明，继续通过原审批和沙箱检查，不扩大许可。其作用是减少无效尝试、使模型有机会验证真实实现，而非改变评测答案。
