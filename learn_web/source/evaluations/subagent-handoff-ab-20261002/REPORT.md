# 短引用等三项改动的真实模型对照

2026-10-02 批次，2026-10-03 汇总。12 个预定首次回合全部完成。本次没有证明三项改动提高整题通过率或降低整体开销：新旧严格通过均为 **3/6**，纯行为完整通过也均为 **3/6**。新版可解析答案的引用校验错误较少，但行为正确数由 38/48 降至 36/48，来源提交拒绝由 3 次增至 4 次，父方读取由 4 次增至 12 次。

新版已报告 token 合计少 9.1%，但包含两次用量未知的服务失败，不能解释为完整成本下降。只看双方接口正常的四对，新版 token 合计反而多 **4.0%**，配对比值中位数为 **1.041**。工程机制可用，模型是否有效使用仍存在明显问题。

## 比较范围

比较上一轮改动前的 55 文件、12,024 行版本与当前 55 文件、12,060 行版本。唯一生产差异是 12 位短引用、具体修正反馈，以及父方收到带行号的精简源码展示；详见[实现报告](../subagent-handoff-20261002/REPORT.md)和[源码差异](../subagent-handoff-20261002/candidate.patch)。本批仅增加评测与文档，没有继续修改生产代码、依赖或配置。

三个新问题集分别使用 Django、OpenLibrary、Session 的既有固定源码，每组八条行为问题、两个工作包，每版各跑两次。问题代码未在旧批次使用，但项目、源码和部分行为主题已经见过；不是未见仓库泛化评测，也不是原 benchmark 修复题。三个改动一起比较，没有消融实验，不能把某项差异单独归因于短引用或行号。

每回合固定创建两个 Explore 子任务，通过真实 Runtime 首次调用 `worker_status(wait_for="all", wait_seconds=300)`，之后父方自主整合。回合之间串行，第二遍反转同题新旧顺序。没有 Solo 组，也不测自主拆分、委派时机或写代码能力。

配置沿用现有 `.env`，记录模型名为 `gpt-5.6-luna`、Responses 流式协议、64k 上下文、8,192 输出上限；模型名不证明供应商内部路由。每回合全队上限为 36 次模型请求、60 次工具、300,000 token、600 秒，单请求超时 120 秒。源码只读，Memory 与工具网络关闭；模型调用前断言父任务只要求观察。协议、24 个可执行事实、24 个评分负例、源码、评分依赖、顺序、设置和环境摘要在正式请求前冻结，见[协议](PROTOCOL.md)、[初始冻结](FREEZE-INITIAL.json)与[当前冻结](FREEZE.json)。

## 耗时与用量解释

完整耗时取单调时钟，覆盖执行及关闭；首回合的该数值无法恢复。事件时长统一取首个父运行 `worker_started` 至最后一个父/子 `run_completed` 或 `run_stopped` 的 UTC 时间差，十二回合均可计算，是补充口径。

| 新版 / 旧版的配对比值中位数 | 样本数 | 比值 |
| --- | ---: | ---: |
| 完整耗时 | 5 对完整计时 | 1.009（+0.9%） |
| 事件时长 | 全部 6 对 | 0.818（−18.2%） |
| 已报告 token | 全部 6 对，含未知用量 | 1.041（+4.1%） |
| token：双方接口正常的补充分析 | 4 对 | 1.041（+4.1%） |
| 事件时长：双方接口正常的补充分析 | 4 对 | 0.770（−23.0%） |
| 完整耗时：双方接口正常且计时完整 | 3 对 | 1.009（+0.9%） |

完整耗时与事件时长的中位数使用不同配对集合，不能把差异解释为两种计时器本身的差别。六对事件时长合计为 1,292.22 → 1,073.96 秒；已知完整耗时只有旧版五回合、新版六回合，不比较这两个合计。两次重复及服务波动不足以支持稳定加速的结论。

补充分析在观察到服务失败后加入，只保留双方全部请求与 HTTP 诊断都成功且有 token 用量的配对：Django 两遍、OpenLibrary 第二遍、Session 第二遍。主成绩仍包含全部失败。四对 token 合计 375,334 → 390,452（+4.0%），来源拒绝 1 → 4，父方读取 4 → 6，首次提交成功 7/8 → 5/8。因此，即使暂时排除服务故障，本样本也不支持交接重试和整体开销已经下降。

token 为服务报告的全队输入与输出总量，包含报告的缓存输入，不等于货币费用。原有 48 份交付正文的离线 token 减少 10.6%，不能替代本次全流程计量。

## 失败和机制观察

- **短引用被实际使用，但仍会抄错。** 新版来源选择中 37 次使用 12 位引用、6 次使用完整 ID，含被拒绝的尝试。旧版有 35 次 64 位引用、4 次 62 位和 1 次 49 位。旧版 Session 第一遍的两次 `handoff_source_unread` 经轨迹核对都是未知 ID：成功读取存在，错误 ID 的前 12 位可匹配，但完整值不符。新版 Django 第二遍也提交了一条无法匹配的 12 位引用，明确提示后修正；没有自动猜测或放宽来源边界。
- **具体大小反馈没有减少本样本的超长重交。** 旧版超长拒绝 1 次，新版 3 次。新版 Django 第一遍从 8,645 字符缩到 6,234 字符，仍超过 4,000，第三次才成功；第二遍也先提交了 7,243 字符。重复或重叠行段仍占额度，已有可读反馈不保证模型下一次就选对范围。
- **可定位引用与正确推理是两件事。** 新版 OpenLibrary 第一遍把零长度切片当作全部元素，并漏掉重复解压结果；Session 第一遍混淆事件时间与事件值，并误判回收边界。旧版 Django 第二遍误把命名捕获内的重复量词推导成两个占位符，还使用了拼接符号名；六次父模型调用没有纠正子方原有错误。
- **最终格式仍是实际失败点。** 两版 OpenLibrary 第二遍的子任务 JSON 均可解析，父模型重写时在 c1 字符串中产生相同的反斜杠加空格非法转义。原始 `model_reply.text` 已含该问题，评分没有修补。短引用和源码行号不约束最终 JSON 的合法性。
- **服务失败触发父方接手，不保证恢复正确。** 新版 OpenLibrary 第一遍的一名子任务因 `SSLError` 失败，约 4.26 秒，无 HTTP 诊断和 token；Session 第一遍的一名子任务收到 `incomplete_response`、终态 failed、零输出，约 24.52 秒，无 token。两回合父方最终均正常完成，但各只严格答对 6/8。其他已完成子任务也存在行为错误，不能把所有错误都归因于服务。

这轮保留三项轻量能力及其严格来源校验，不把它们包装为性能提升，也不据此启用默认自主委派。下一步应优先用独立小实验验证两处具体问题：最终结构化结果的可靠交付，以及超过证据额度时无需反复生成整份答案的修正方式。行为推理仍需针对真实缺口核查，增加父方调用次数本身没有保证。

## 测量修订与审计
