Aster 的设计与演进

Aster 是一个用 Python 编写的本地 Coding Agent。给它一项代码任务，它需要自己查资料、读文件、修改实现、运行测试，再把结果交给用户。这个项目关心的是：怎样把模型的工具调用能力，组织成一套可以持续工作、可以恢复、可以检查的运行系统。

这篇文章把项目的设计和实验按问题串起来。先理解最小循环为什么不够，再看上下文、会话、子 Agent 和记忆怎样逐步加入，以及真实评测怎样反过来改变设计。读完后，再进入 00–15 章源码教程，会更容易理解每个模块为什么存在。

记录范围为 2026 年 9 月 11 日至 10 月 20 日。各阶段围绕不同问题设计实验，文中随结果说明题目、预算和评分口径，并链接原始报告。

一、为什么要做一个 Coding Agent Harness

假设用户提出这样的需求：

修复 CSV 导出中的金额舍入问题，保留原来的列顺序，并补充回归测试。

这是一个用于解释流程的例子。模型即使知道十进制计算，也不能只回复一段建议代码。它必须找到真正的导出入口，确认金额在哪一层转换，了解项目的舍入约定，修改合适的函数，再检查列顺序和已有行为有没有被破坏。

更麻烦的是，任务可能中途断网，测试依赖可能缺失，用户可能临时纠正需求，模型也可能读错文件或误以为任务已经完成。随着工具输出不断加入，对话还会越来越长。

这些问题组成了 Aster 的工作范围。

Harness 可以理解为模型与执行环境之间的运行系统。 模型决定下一步想做什么；Harness 准备它能看到的信息，判断动作能否执行，记录执行结果，并决定任务还可以继续多久、是否满足交付条件。

参与者 在金额修复例子中负责什么
模型 判断根因、选择文件、提出补丁和测试
工具 真正读取文件、应用修改、启动测试进程
Harness 管理调用顺序、权限、上下文、预算、状态和完成检查
独立评测 在 Agent 结束后，检查交付是否满足预先规定的要求

最后两项尤其容易混在一起。Harness 能要求“修改后必须运行测试”，却未必知道模型选择的测试是否足够。独立评测可以发现遗漏，但正式做任务时，模型不能提前看到隐藏答案。

因此，Aster 从一开始就同时需要运行系统和评测材料。前者让任务有机会完成，后者帮助判断到底改善了什么。

项目采用本地文件、JSON、SQLite 和 Python 异步机制组织这些能力。涉及外部模型、数据校验和终端界面时，分别使用已有的 HTTP 客户端、Pydantic 和 Textual。设计参考与取舍保存在设计来源（Markdown 原文下载），当前结构见模块说明（Markdown 原文下载）。

二、先把一次任务跑成闭环

2.1 一轮模型请求之后，事情才刚刚开始

Aster 最基本的路径可以这样读：

最后一条返回边很重要。模型给出最终回答后，如果任务要求的修改或验证没有完成，Runtime 可以把缺口反馈给它，允许在已有额度内继续修正。反馈也有次数和预算限制，不能无限循环。

源码中有三个容易混淆的单位：

单位 含义 为什么要分开
run 一次任务运行 保存任务、预算、产物和最终状态
turn 一次模型决策轮次 一轮可能没有工具，也可能提出多个工具调用
step 一次工具动作 可以单独判断执行是否成功、是否修改了文件

例如一次模型回复同时要求读取两个文件，模型决策只有一轮，工具动作却有两个。只限制其中一个计数，很容易误判任务已经使用了多少资源。

当前主入口在 Runtime：run() 维持循环，prepare_request() 准备本轮输入，工具执行路径更新状态，finalize() 处理完成请求。CLI、TUI 和外部策略环境都使用这一套内核。

2.2 为什么聊天记录之外还要保存状态和证据

聊天记录适合回答“模型刚才看到了什么”，却不适合单独回答“这份测试结果对应哪个版本的文件”。

因此，Aster 把信息分开保存：

信息 主要用途
模型历史 维持对话和工具调用协议
RunState 记录当前预算、待办、修改路径、验证状态等事实
执行事件与工具归档 复盘具体动作，查阅较长的原始结果
checkpoint 保存恢复运行所需的状态和身份
跨会话记忆 保存后续任务可能复用的知识和方法

这些材料会引用同一次工作，但保留条件不同。某段测试输出可以移出本轮模型输入，同时继续留在归档中；一次已经失败的测试也不能因为聊天窗口变短就失去记录。

这种区分后来成为上下文压缩、历史分支、子任务交付和记忆学习的共同基础。如果一开始只维护一份不断追加的字符串，后面每增加一个功能，都需要重新猜测字符串里哪些内容仍然可信。

三、先弄清楚“做对了”是什么意思

项目很早就遇到一个评测问题：程序正常结束、内部检查通过、用户任务完成，可能是三件不同的事。

例如，模型为金额修复写了一条只检查普通整数的测试。测试确实执行并通过了，进程也正常退出，但小数边界仍然错误。另一个任务可能已经留下正确补丁，却在最后整理答案时超时。

这两种情况都值得保留。前者暴露验收覆盖不足，后者暴露交付与预算问题。

Runtime 是否正常交付 独立验收是否通过 应当怎样理解
是 是 完整交付成功
是 否 内部完成判断没有覆盖真实需求
否 是 产物正确，但运行或交付流程仍有问题
否 否 同时检查任务实现与执行失败原因

不同实验可以选择不同主指标。例如 SWE-bench 官方评分主要判断补丁是否修复问题；跨会话任务可以要求“正常交付且独立通过”。比较前必须先确认分子和分母是什么。

Aster 的验证材料也因此分成几类：

  • 工程回归检查明确的程序契约，例如错误的工具配对是否被拒绝。
  • 固定动作回放让工具按预定顺序执行，用来确认环境、工具和评分器能够工作。
  • 真实模型评测观察模型能否自主选择有效动作，并记录所有失败和消耗。
  • 机制分析回看轨迹，确认新增的机制是否触发、交付是否被使用。

固定动作回放可以全部通过，真实模型仍可能选错工具；真实模型成绩上升，新增机制也可能一次都没用到。后面的子 Agent 实验就出现过第二种情况。

实验前固定协议、候选源码、任务和判分规则；分析过轨迹的题目转为开发集。旧失败、服务故障和补测分别保留，读者可以追溯每份成绩来自哪次尝试。

早期 artifacts 中还有旧指标口径的记录。工件说明（Markdown 原文下载）列出了 token 重复相加、任务重复等问题；阅读时以修订后的报告为准。

四、上下文越来越长，应该删掉什么

4.1 只保留最近几轮为什么不够

修复一个跨文件问题时，用户可能在第一轮强调“不能改变公共 API”，几轮后补充“旧格式还要兼容”。随后几十次读取和测试会把这些要求推到历史前面。

简单丢掉最旧内容，会连要求一起丢掉。给每个工具输出固定截断长度，也会在窗口还有空间时过早损失信息。反过来，全部保留又可能挤掉后续推理所需的空间。

还有一个更基础的约束：工具历史本身是一种协议。某条结果对应特定调用编号；结果与调用不能随意拆散，一些服务要求的推理元数据也不能被当作普通文本删除。

因此，Aster 在 9 月 16 日的改造中采用确定性预算管理：先保存可回读的原文，再计算整个请求是否装得下；只有存在压力时，才按规则减少发送给模型的内容。

4.2 全局预算、成组压缩、按需回读

9 月 16 日的方案有三个相互配合的选择。

第一，预算针对完整请求。 系统指令、工具定义、历史消息、动态状态和协议包装都会占空间，同时还要给输出留额度。只数用户正文和文件内容，会低估真实请求。

第二，压缩保持交互完整。 当时先移出可删除的旧普通消息，再缩短工具结果或移出完整交互组。10 月的 v10 进一步改为先遮蔽旧观察正文、再移出旧组，并追加状态便笺；当前顺序见 06 章。两版都保留必要协议关系，必需内容仍放不下时报告预算不足。

第三，详细结果有归档入口。 被移出的工具正文可以通过 observation_read 查找和分页读回。较小的完整结果不必额外挂长引用，回读工具也按需加载，避免为“可能需要”增加每轮固定开销。

可以把它理解成：桌面放当前工作需要的材料，文件柜保存已经采集的原文。清理桌面后，模型还可以按线索回读文件柜；实验会继续检查它是否真的这样做了。

具体规则及其研究取舍见上下文设计（Markdown 原文下载），当前代码从 ContextBuilder 进入 BudgetCalculator。预算计算先生成候选，成功后再安装压缩结果，避免失败预检破坏原历史。

4.3 最有价值的结果，包含没有改善的那一组

上下文实验使用 12 道预置长历史的代码题，每题运行三次。v8 在原来的 6,144 输入预算下，完整完成数从 v7 的 28/36 降到 22/36。虽然隐藏功能检查有改善，但更多运行在正常收尾前用尽动作额度。

同预算下，压缩改造的完整完成数下降，下一步需要检查任务是否仍有足够输入空间。

随后按预先确定的规则比较 8,192、10,240、12,288 三档输入预算，选择满足门槛的最小档位，再用全新尝试确认。选定 8,192 输入预算后，主任务 36/36 完成；首次请求长度从平均 18,434.83 压到 7,779.25 个本地估算 token，平均压缩 57.8%。

这份 36/36 来自压缩机制与预算选择的共同结果：前者组织材料，后者给任务保留足够空间。

另外，一次性历史证据控制题在新确认批次中 0/3 完成，模型没有主动使用归档读取。这说明“原文没有丢”和“模型能利用原文”之间还有距离。

57.8% 对应首次请求的本地长度估计；完整选参、失败与确认过程见上下文结果（Markdown 原文下载）。8,192 是压力实验档位，日常配置按模型窗口与用户设置管理。

五、工具能执行，还要让它适合真实仓库

5.1 从“允许操作”到“能正确完成操作”

一个只有读文件、写文件、运行命令的 Agent，已经可以完成简单任务。进入真实仓库后，问题会集中到操作细节：补丁匹配到多个位置、测试日志超过返回上限、依赖安装后下一条命令找不到、模型使用了过时的文件内容。

9 月 18 日的长任务改造逐批处理了这些问题。

批量补丁会先在同一份原文里定位所有修改，要求位置唯一且互不重叠，再统一应用。这样可以减少工具往返，也避免第一处修改已经发布、第二处才发现无效的半成品状态。

命令输出增加有界采集、脱敏归档和分页回读。模型先看预览，必要时查询已采集的详细日志；超过采集上限会明确标记。

对于权限，工具名称本身没有特殊通行证。读取、写入、命令执行和结果发布仍要通过各自的检查。文件在等待用户批准期间可能已被另一进程修改，因此实际执行前还要复核版本。

这些机制共同服务于一件很具体的事：模型基于刚才读到的内容提出修改时，程序要确认它现在面对的仍是那份内容。

5.2 保护边界也会改变模型面对的环境

隔离执行会带来真实的使用约束。工作区路径可能变化，被忽略的临时文件可能不进入测试副本，进程生命周期也可能与普通终端不同。

10 月的成本诊断发现，模型会先把一次性测试写进临时目录，再启动隔离测试。由于测试文件没进入副本，它又要重新写、重新执行。模型在做合理的验证准备，却被工具之间的契约迫使多绕了几圈。

后来的修正允许一次 run_tests 调用直接携带临时测试源码，由工具在隔离副本中创建和执行。这既减少了准备动作，也让“临时测试文件应该在哪里”成为工具明确负责的事。

10 月 11 日又发现另一类问题：临时 pytest 项目位于仓库树内时，会向上继承仓库配置，受到原项目 --strict-markers 等选项影响。改动把每条命令的临时目录放到项目树之外，并授予相应的有限访问权限。

这些案例说明，分析 Agent 失败时除了看模型思路，也要问：模型预期的文件和进程语义，与工具真实提供的语义是否一致。

5.3 流式显示、并行读取和 Skills 分别解决什么

流式响应让用户更早看到输出，但半截工具参数不能提前执行。Aster 的工具动作仍等完整响应确认；服务断流后也要区分可以重试的请求失败与已经发生的工具副作用。

只读工具并行可以缩短独立读取的等待。它和多个 Agent 各自推理不同：前者并发执行模型已选好的工具，后者还会产生分工、子推理和汇总成本。

Skills 则把任务方法打包成可发现、按需加载的文本与资源。方法能指导模型，但不会自动授予写文件或联网权限。加载后的技能正文保留快照，后续请求不应因为磁盘内容变化而悄悄切换到另一份指令。

这三项能力分别改善交互、工具调度和知识组织。是否提高任务成功率，都需要各自的实验来回答。

六、任务会中断，探索也会走弯路

6.1 恢复运行需要检查什么

长任务不可能只考虑一直顺利执行的情况。模型请求可能失败，终端可能退出，用户也可能主动取消。

checkpoint 保存恢复线索。恢复前，Runtime 检查工作区变化、协议兼容性、归档是否存在，以及上次中断时有没有状态不明的动作。

如果写入动作可能已经执行，盲目重放会产生第二次修改；如果文件已经变化，旧测试通过也不能继续当作当前版本的验收证据。

因此，Aster 的恢复路径复用正常运行的权限、协议和来源检查。遇到无法确认的状态会明确拒绝，让用户或后续操作处理实际差异。

6.2 “回到之前”逐渐变成一个会话树问题

单个 checkpoint 能解决中断续跑，却不太适合这样的工作方式：先完成一版方案，尝试几轮新方向，再回到原来的位置重新探索。

9 月 20—21 日的会话改造引入类型化历史树，用 SQLite 保存位置与关系，允许选择祖先位置继续，或者明确带回另一条探索中的摘录。

每个历史位置保留当时可见的内容。复用另一条探索的结论时，显式带回材料及出处；子会话恢复也沿用这个原则，让父子分支的时间线保持一致。

会话分支并不回滚磁盘文件。对话回到了旧位置，工作区仍可能保留新修改，因此恢复要检查文件差异；如果需要文件也分支，应配合 Git 或独立工作区。

6.3 这轮改善的是使用流程

六类固定工作流、每类三个变体的离线对照中，两版都完成 18/18，规定路径的操作数从 69 降到 36，减少 47.8%。减少的是按协议计数的命令、确认、复制等操作，没有测量人的思考时间。

后续真实编码回归中，核心工具集两版均 5/5 完整完成，完整工具集两版均 4/5。这轮的收益是固定流程更省操作，编码通过数持平。

七、为什么中途还要重构代码

功能增加后，运行时、工具、协议和界面的边界会变得模糊。例如，为估算新配置下的上下文，先临时修改全局状态再改回来；或者同一份工具参数在多个入口被重复解析。

9 月 19—20 日的源码整理，主要目的就是把这些状态归属说清楚。

边界 重构后的职责
Runtime 持有任务状态，控制执行、授权和结果归集
ContextBuilder / BudgetCalculator 计算请求和压缩候选，成功后安装
Provider client / codec / usage 分开网络请求、协议转换和每请求用量
ToolRegistry 与具体工具 分发动作，执行各自业务
Session lifecycle / navigation 准备恢复候选，检查后切换
TUI 展示状态和接收操作，调用共同内核

一个贯穿这些边界的做法是：先准备并验证候选，再提交状态变化。 模型切换预检失败时保留原会话；上下文计算失败时保留原历史；后台记忆生成候选时，也不能直接覆盖前台的新纠正。

阶段报告中，Python 模块从 27 增至 51，源码物理行从 9,350 增至 9,707。重构增加了模块与少量代码，换来更明确的职责和状态归属。

重构的价值要落到具体的重复逻辑、修改范围和状态边界上。上述数字属于当时的重构批次，后面会话树和记忆维护继续增加了代码；当前目录结构应看模块说明（Markdown 原文下载）。

八、多个 Agent 为什么没有自然地变得更好

8.1 第一层困难是孩子交不出东西

把一个问题交给两个 Agent，直觉上应该更快。真正执行时，却要先决定怎么分工，让孩子理解任务，再等待、核对和整合它的结果。

Aster 在 9 月下旬连续做了等待、交付和预算方面的修正。早期发现父任务的正式测试要求被沿用到子任务后，只负责调查或局部实现的孩子也可能被完整交付条件挡住。于是区分子任务交付与父任务最终验收，让孩子按自己的职责返回，最终由父方检查整体结果。

但机制修好，整体收益仍没有自动出现。

9 月 28 日的 20 道混合代码题对照中，Solo 通过 14/20，Worker 通过 13/20；全队 token 多 5.9%，耗时多 3.4%。18 个实际启动的子任务只有 5 个正常交付，不少孩子把额度花在调查上，最后没有交付报告。

报告也保留了一次有效协作：COBOL 任务中，孩子指出父方验证数据矛盾，反馈被采纳。这个案例为后续分工设计提供了线索。

因此，后续改造先处理“能交什么、什么时候交、预算由谁负责”。子任务收到必要的原始需求和局部分工；接近额度时尝试有界交付；父方收到的部分结果明确标记为 partial；全队统一统计消耗，避免每个孩子各自拥有一份看似独立的无限预算。

相关记录：Worker 基线（Markdown 原文下载）、交付与预算改造（Markdown 原文下载）、需求归属评测（Markdown 原文下载）。

8.2 孩子答对了，父方仍可能重复做一遍

进入十题源码调查与审查实验后，问题变得更细。

r2 采用父方加一个孩子的分工，两遍严格通过为 Solo 12/20、team 16/20。但父方在子交付前读取的 11,490 个不同源码行中，有 4,673 行与孩子重合；完整用量配对的成本仍然很高。

父方需要核对关键结论；这批轨迹里的重复则发生在孩子尚未交付时，父方已经独立做完同一个工作包，调查成本花了两遍。

于是后续迭代加入更明确的父方分工、精选来源片段、交付通知、等待方式和工具目录精简。它们分别减少重读、轮询和消息开销。

r3 的交叠行数确实下降，但质量收益仍有限；r4 的固定分工总体通过数甚至略低于 Solo。到 r5，策略改成按需要自主决定是否委派，20 个 team 回合只有 3 次实际派工。严格通过为 13/20 → 15/20，19 对完整用量的总 token 增加 17.3%，耗时配对中位数减少 19.0%。

这轮选择减少派工，让少数分工形成实际交付。六个胜对中四个没有派工，说明分数变化还包含提示与其他行为的影响。

完整 r0–r6 的失败、修改和采用理由保存在十题迭代记录（Markdown 原文下载）。它比单看最终通过率更能解释设计怎样收敛。

8.3 新机制一次没触发，应该怎样验证

r5 留下了一个很明确的失败：孩子耗尽 token，父方只收到程序生成的部分读取摘要，接管后又花光全队额度，最终没有答案。

r6 据此增加按剩余 token 提前收尾，让孩子趁还能负担一次请求时生成部分结论。

第一次完整复测中，team 分数有所变化，但 20 个 team 回合没有一次实际委派。新分支根本没执行。因此当时保留 r5，把 r6 候选和负结论一起存档。

后续才专门设计受控实验：确保发生真实派工，并用已读取证据和预先冻结的压力预算检验交付。44 个回合全部启动孩子，r6 的六个压力回合全部触发提前总结。压力组严格通过从 0/6 到 4/6，空答案从 6 到 1，token 增加 10.2%。

这轮在预算紧张时提高了可用交付率，代价是更多 token；子答案错误和父方额度耗尽仍在失败记录中。采用决定见受控续测报告（Markdown 原文下载）。

这段经历给项目留下一个很实用的评测习惯：新增机制后，先确认真实运行经过了那条路径，再讨论它贡献了多少。

当前默认 max_workers=0，模型自主委派仍默认关闭；用户可以按需使用显式子 Agent 入口。产品能力与默认策略需要分开理解。继续读：13 交互与 Worker、Worker 使用边界（Markdown 原文下载）。

九、记忆是怎样从文件摘录变成知识的

9.1 保存原文解决不了所有跨会话问题

早期 Memory 主要保存有出处的文件摘录。它适合记住某段项目说明：原文来自哪里、文件是否变化，都容易检查。

但用户可能直接在对话里纠正约定，或者一次修复只在执行记录中留下经验。仅允许逐字文件摘录，就很难保存这些信息。

更重要的是，代码本身与可迁移的方法不同。一段支付实现可以被再次读取；“金额转换要使用明确的十进制舍入方式，以及这条规则适用于哪些路径”才是后续退款任务可能复用的知识。

10 月 5 日的改造把条目扩展为三类：原文摘录、事实和方法。派生知识可以引用真实用户请求、文件观察及实际执行结果，同时带上适用条件。存储继续使用本地 JSON 和已有检索，没有因为增加“知识”一词就引入图数据库或向量服务。

一条可复用记忆需要回答的问题 对应设计
它说了什么 摘录、事实或方法正文
在什么情况下适用 when 等适用条件
为什么允许保存 文件、用户消息或执行事件的出处
后来是否被纠正 替换关系和有效状态
有哪些使用反馈 明确应用并验证后的记录

出处检查确认材料真实存在，实际使用与用户纠正继续检验归纳是否准确。

9.2 召回、使用和正确使用要分开

假设某次请求同时召回“金额用 Decimal”和“项目说明用法语”。代码测试通过，并不能说明法语约定被正确应用。

旧逻辑中曾出现无关召回条目连带获得成功反馈。改造后由测试调用明确说明正在检验哪些已召回记忆，没有声明的条目不跟着计分，环境错误也不作为知识对错的证据。

反馈归属因此更明确；使用关系仍由模型声明，知识收益还需对照实验检验。

十题定向学习对照中，新版复用严格成功从 4/10 到 7/10，约束通过从 17/30 到 25/30，学习加复用总 token 增加 1.7%。学习阶段明确要求记住，实验测量的是定向学习后的复用。

这一轮也发现模型说“已经记住”却没有写入，金额与用户纠正题仍然失败。计入学习阶段后，全流程成功为 6/10。

设计与结果：知识记忆改造（Markdown 原文下载）、十题报告（Markdown 原文下载）。

9.3 自动学习为什么需要独立的后台路径

要求主 Agent 既完成当前任务，又恰好在正确时机主动保存经验，并不稳定。于是 10 月 6—7 日加入从已结束经历中自动提炼和批量整理的路径。

前台仍可及时保存用户纠正。后台读取有来源的经历，提出少量新增、替换、停用或不操作的候选；Runtime 在合适的工作区边界检查后再提交。

生成与提交分开的原因很具体：后台开始处理之后，用户可能已经更正了旧规则。如果它完成时直接写回旧理解，就会覆盖刚发生的纠正。候选必须接受当前版本和来源检查。

保存回执也来自实际提交结果。后台正在处理、决定跳过、候选被拒绝，都不能显示成已经学会。

十题、44 会话对照中，正常完成且通过从 4/10 到 7/10，独立功能通过从 4/10 到 9/10，14 次新增或替换回执都对应实际条目。已报告总 token 增加 12.6%，超过预设降耗目标；基线中的服务失败也影响了分差。

因此，异步整理解决的是时机、并发和漏存问题。它是否减少总成本，要由下一轮单独回答。

当前默认开启 memory_enabled、memory_evolution、auto_dream。交互会话自动整理，单次 CLI 自 10 月 18 日起默认延期到下次交互会话。这条路径更新外部知识和召回材料，后训练接口另见第十三节。

继续读：自动学习设计与交付（Markdown 原文下载）、自动学习实验（Markdown 原文下载）、10 分层记忆、11 记忆演化。

十、降成本之前，先看看钱花在哪里

自动整理增加了模型调用，很容易让人先想到把它关掉。但上一轮账本显示，维护只占已报告总 token 的约 7.8%，主要开销仍在前台任务。

因此，10 月 7 日的优化先回看真实轨迹，找具体的多余工作。

一类是前面提到的临时测试文件反复准备。另一类是新会话对同一份没有变化的材料再次请求后台整理。还有一类发生在最后收尾：虽然要禁止继续执行工具，但没有必要同时改动已经提供给模型的工具定义。

对应的改动很集中：

  1. 临时测试源码随 run_tests 一起提交，在现有隔离副本中执行。
  2. 已成功整理、来源及记忆版本等条件没有变化的相同材料，跳过重复提炼；失败、取消、纠正和来源变化继续重新处理。
  3. 父任务预算收尾保留工具定义，由执行入口阻止继续调用，减少请求前缀的不必要变化。

“保留工具定义”和“允许执行工具”是两个不同控制点。把它们分开后，可以限制后续动作，同时保持请求结构相对稳定。

两组各 24 会话的对照得到：

指标 基线 降耗版
正常交付且独立通过 9/10 9/10
独立功能断言 30/30 27/30
已报告总 token 1,629,128 978,713
后续任务已报告 token 1,274,240 689,437
工具调用 226 146

总 token 减少 39.9%，后续任务减少 45.9%。真实新版运行中用了 12 次临时测试源码入口，跳过了 2 次相同材料整理，因此可以确认这些机制确实执行过。

一条 CSV 约定没有保存，功能断言退步了三项；修正提炼说明后单题补查通过，主表仍保留原始失败。工具与提示同时改动，这组降幅对应整套方案。

缓存输入占比从 61.26% 降到 59.17%，未缓存输入减少 36.8%。这轮通过减少输入总量降耗，即使缓存比例稍低，需付更高单价的输入仍然更少。

上述降幅按已报告 token 计算；供应商账单、缺失用量和后台消耗另列。汇总跨阶段成本时，还要按请求身份去除报告间重复收录的尝试。

十一、真实仓库评测把哪些问题重新暴露出来

11.1 从内部任务走向 SWE-bench

前面的专项实验分别检查上下文、协作和记忆。它们能帮助定位机制，但真实仓库修复还需要模型理解复杂 API、找到正确测试入口，并处理跨文件的语义影响。

10 月 8 日先做了十题 SWE-bench Verified 本地隔离评分，Aster 为 4/10。随后 Aster、pi、Codex 使用固定模型和十题进行官方 Docker 评分，原始结果分别为 2/10、3/10、2/10。

本地与官方评分环境各有一套口径。官方对照中五次尝试因主机或模型连接故障留下空补丁；替换这五次补测结果后，合并成绩为 2/10、3/10、3/10，原始尝试和费用另行保留。

官方评分会同时检查原来失败、修复后应通过的测试，以及原来通过、仍应保持通过的测试，通常记为 F2P 和 P2P。这样才能区分“目标问题修好了”和“顺便破坏了其他行为”。

原始材料：本地十题（Markdown 原文下载）、官方三方对照（Markdown 原文下载）、故障补测（Markdown 原文下载）。

11.2 一个通过的测试，不能擦掉另一份失败

这轮诊断推动了验证状态修复。

假设第一次正式测试发现 A、B 两项失败，随后模型只重跑 A 并通过。如果程序把“最近一次测试通过”当成全部验证通过，B 就会被遗忘。测试受环境阻碍或没有真正采集到用例，也可能被误解为完成。

当时的修复让 Verifier 跨验证保留失败；10 月 18 日进一步区分具名用例和匿名证据：具名失败由同一用例重新通过来解除，退出码和共用编号的断言脚本只更新验证状态。文件修改后，旧版本的通过证据失效。具体规则见 08 章。

修复后的十题官方结果仍为 2/10。九份非空补丁的已有通过测试都保持通过，七份仍没通过目标修复测试。这一轮改善了证据追踪，模型对共享根因和边界的遗漏仍需解决。

结果与限制见验证机制复测（Markdown 原文下载）。

11.3 多加一次“再检查”为什么最后被删除

下一版尝试在完成前自动追加复核，同时改进过载处理。官方结果仍为 2/10。

六次复核触发后，记录到 34 次请求和 931,400 个已报告 token，其中四次没有文件修改。部分复核确实调整了实现或测试，但没有足够证据支持默认追加这一流程。最后删除自动复核，保留故障处理修复，并补齐断流重试。

这批结果使项目放弃默认追加复核。931,400 token 是触发后的观察量，净节省需要另做关闭对照；十题成绩对应带复核的冻结候选，删除后的版本完成了本地回归。完整决策见复核实验报告（Markdown 原文下载）。

11.4 10 月 10—11 日二十题：环境适配与语义遗漏

10 月 10—11 日扩大到三来源的 20 道通用编码题：12 道仓库修复、6 道终端编码、2 道小型实现。三者原始单次都使用同一模型，每次尝试 900 秒。

Aster 运行批次 独立通过 怎样产生这份成绩
原始单次 12/20 各题一次，与 pi、Codex 同批比较
纳入五题补测 15/20 对应五题全部替换，包含选择性补测与环境适配

pi、Codex 的原始成绩为 15/20、14/20，后两轮没有重新跑它们。第二版 Aster 与 pi 的历史成绩持平。

这一批同时改进 Harness 和评测环境：前者调整临时目录、故障退避和验收指引，后者适配解释器、导入、信号权限与持久服务。结果对应整套运行条件。

第二版正常交付且独立通过也是 15/20。内部正常完成的 18 题中有 3 题独立失败：Django 遗漏共享 API 的排序行为，SymPy 漏掉通用零矩阵加法，pytest 的实现不满足返回类型和继承顺序要求。

另一次解释器任务反复使用隔离副本中不合适的绝对路径，停滞退出，产物也未通过独立验收。它同时留下执行环境和实现正确性两个问题。

这些失败把下一步问题指向更具体的地方：怎样让模型定位共享语义、选择有区分力的验证，并在环境反馈后有效调整行为。继续追加泛泛的自查提醒，还不足以解决它们。

这 20 题已经用于诊断和优化，属于开发集复测。两版优化共 40 次正式尝试，已报告 16,746,634 tokens，另有健康探测和缺失用量说明；全部失败仍然保留。详见原始对照（Markdown 原文下载）、补测合并（Markdown 原文下载）、第二版完整结果（Markdown 原文下载）。

十二、10 月中旬：从开销定位走到双模型检验

10 月 12—16 日，优化先从请求前缀入手：回执校准本地计量，历史尽量只追加，状态变化通过 [Context update] 便笺传递。这样既让模型得到新事实，也减少替换旧消息造成的缓存失效。过程与成本口径见缓存和轮次总结（Markdown 原文下载）。

接下来，分阶段计时和逐轮对照把问题拆得更细：一次请求为何迟迟发不出去，任务为何多做几十轮，以及更短的输入最后是否真的省钱。

12.1 先量 Harness 自己花了多少时间

v11 的 old20 账本中，模型之外的时间占任务总时间 63%。逐段计时发现，每次 checkpoint 反复哈希仓库、复制文本基线，trace 追加时又重读历史；容器 overlayfs 上一次 fsync 需要 88–225 ms，频繁落盘进一步放大了等待。

改动围绕这些重复工作展开：用文件属性缓存摘要并保留短时间内修改的复核窗口，基线按内容寻址，trace 缓存尾部，SQLite 使用常驻连接与 WAL。checkpoint 仍逐次原子写入，把强制同步改成至少间隔 5 秒的组提交，终态强制同步。

同容器、脚本化模型、各重复三次的 A/B 中，每个模型轮次的 Harness 开销，小仓库从约 1.24 秒降到 0.18 秒，35 MB 仓库从约 6.65 秒降到 0.50 秒，分别改善 6.7 倍、13 倍。真实任务 rc1 到 rc5 的模型外时间从 3,259 秒降到 622 秒（−81%）。前者隔离了框架开销，后者记录整批任务实际耗时。设计见 v12（Markdown 原文下载），测量条件见报告第 4、7、9 节（Markdown 原文下载）。

12.2 官方补丁也失败时，先检查判分环境

requests 的超时测试假定 10.255.255.1:80 是黑洞地址。主机网络开始应答它后，连官方参考补丁也过不了测试。项目改用 tarpit 判分网络，为该地址保留无人应答的链路内位置；随后复判的 24 个历史补丁全部重现原结果。这一步修正了测量环境。

题目来源也需要保持清楚。fresh30 和 fresh30b 都先抽题、排除已用题、预检环境、冻结名单，再运行候选。看过轨迹并据此修改设计后，它们就转为开发集。比较时尽量让版本在同一时段运行，按同一道题配对，并用 bootstrap 给差值区间。

由此形成两条习惯：用参考补丁检查评分器，用冻结协议约束开发过程。网络复现与两套题的过程见报告第 5、11、12 节（Markdown 原文下载）；具体方法见 14 章。

12.3 多出的 83 个请求，主要花在收尾

fresh30 上，v13 平均发出 356 个请求，pi 为 273 个。逐轮拆解后，差额集中在两处：

来源 每 30 题多出的请求 轨迹给出的线索
后台记忆整理 17.5 单次任务结束后仍发出维护请求
最后一次编辑后的收尾 55.5 Shell 已跑通又换测试工具重跑、反复查看 diff、完成反馈后继续绕路
探索 9.5 与对照接近
编辑和修复 0.5 与对照接近

v14 据此统一测试与 Shell 的执行路径，让已识别的 run_shell 测试进入正式验证；通过结果附带改动，最终代码上的必要复跑由 Runtime 完成。单次 CLI 默认将记忆整理留到后续交互会话，减少任务末尾额外请求。

第一次调整只取消了等待，后台仍会启动；冻结的评测 driver 也保留等待逻辑。检查轨迹后才修正启动条件，并将这次后续修改记为开发修复。这个例子说明，减少一次调用要核对真正的启动路径。分解与改动见 v14 方案 A.1、A.2（Markdown 原文下载），运行结果见报告第 12 节（Markdown 原文下载）。

12.4 完整记录留给系统，决策内容呈现给模型

工具结果原先直接把内部 JSON 发给模型：状态、证据编号、64 位归档编号、输出字节数包在正文外面，代码中的换行和引号还要转义。fresh30b 的离线统计中，这层外壳平均每条约 111 token，并随历史反复发送。

v15 在请求组装时增加 模型视图：完整记录继续用于审计、恢复、预算和训练，模型看到原文、必要的错误状态，以及真正有用的引用或翻页入口。搜索按文件分组，完整结果省去回读页脚，状态便笺改成可读文字。相同输入产生相同文本，便于复用稳定前缀。

固定轨迹的离线回放能估计表达方式缩短多少；真实运行还会改变模型的后续路线。因此又在 GPT、DeepSeek 和两套题上做同时段对照。合并 98 个题目样本，每请求输入减少 9.8%，95% 置信区间为 [−14.2%, −5.1%]，四组方向一致；总费用变化为 −1.9%，区间 [−16.6%, +17.0%]，质量与总费用均未测出显著变化。

这轮得到了稳定的输入缩减；整项任务花费还受请求数和少数长任务支配。尤其旧版 DeepSeek 会因输出截断提前退出，失败得更“便宜”，恢复后继续探索反而增加请求。BigCodeBench 的工具视图和状态视图分别回退为 JSON 的消融，也帮助核查早期分数波动。设计见 v15（Markdown 原文下载），完整数据、缺失用量处理及排除规则见报告第 15 节（Markdown 原文下载）。

12.5 完成检查到底值不值

完成契约从 9 月 11 日首版 Runtime 就存在：模型提出结束请求，程序再检查任务要求。后来评测 driver 对每题强制要求“修改且验证”；产品默认则按提示推断。这次 fresh30b 中，产品默认要求 18 题测试，另 12 题没有这项强制要求。

10 月 20 日在同一源码上比较严格评测、产品默认、关闭三组。严格组复用较早运行，新增两组同时开跑；按预定供应商故障规则共同剔除后，14 道可比题均通过 13 道。各组可读终态中的补做次数为 3、4、0，没有救回任务。关闭组正常结束的 22 题中，19 题为 verified，3 题带警告交付：多数运行自行满足了当前交付要求。

关闭组在共同题目上请求多 13.3%、已知费用高 6.5%。全表中它看起来更便宜，约 61.4% 的费用差来自压缩器一题被供应商提前中断。

这份强模型对照未测出完成检查的质量收益，也未测出关闭后的成本收益。产品保留默认检查，作为低成本保险，并用 completed_with_warning 标明未满足的交付条件；它对弱模型的作用留待验证。数据见对照报告（Markdown 原文下载），19/3 的终态分布可从 comparison.json复算。

12.6 规则越补越多，意味着什么

测试识别先后遇到编译后运行、npm run lint、python -c 断言脚本等情况。关键在于证据类型：具名用例有可追踪身份，退出码只说明一次命令的结果，共用编号的内联脚本也缺乏稳定身份。按这层区别管理失败，比把所有失败都堆成待消除义务更贴近实际。

另一些问题发生在文本匹配上。失败签名若保留副本的相对临时路径，同一个旧失败每次都会看起来不同；需求推断把 without changing existing values to NaN 理解为禁止改代码，则误读了解法约束。10 月 20 日的 476f09f 修复了这类否定与单词片段误判，并补充对应回归。

这些例子推动下一步重新考虑抽象：命令、测试用例、运行环境和任务要求分别需要怎样的证据。新增规则应回到这些职责上评估。失败分类的取舍见 v13（Markdown 原文下载），当前实现见 testing.py 与 verifier.py。

12.7 第二个模型让协议和环境问题显形

GPT 使用 Responses 流式接口，DeepSeek 使用官方 Chat Completions 非流式接口。加入后者后，两处缺陷更容易看见：模型视图从 Chat 历史中认不出工具名；推理用满输出额度时，Runtime 直接结束了任务。

修复后，三种协议的工具名都能正确提取。遇到输出上限截断，Runtime 保留用量记录、追加简短行动提示，每次运行最多恢复两次；残缺内容不执行、不进入历史。第二个模型因此既检验输入优化的可迁移性，也补足了协议覆盖。

执行环境仍保留“副本中运行、检查后发布”的产品选择，以保护真实工作区。绝对路径映射、符合条件时对原目录的只读访问、写入失败后的具体说明，逐步弥合副本与普通终端的差异。这个选择带来的兼容成本，会继续通过真实任务检查。协议与路径修复见 v15 第 2、4 节（Markdown 原文下载）及 04 章。

十三、这些演进留下了怎样的设计方法

13.1 用明确的程序事实约束执行

Aster 逐渐把适合程序判断的事实放进运行系统：工具参数是否合法，文件是否变化，历史配对是否完整，额度是否足够，哪些失败尚未解除。

模型负责理解需求、选择证据和提出实现。框架为这些开放判断提供信息与反馈，独立评测检验最终效果。

这也是为什么某些改动适合写成硬检查，另一些需要通过实验选择。禁止执行半截工具调用是明确的协议约束；要求所有任务额外复核一次，则是有成本的策略选择。

13.2 轻量意味着每项复杂度都有用途

上下文先采用确定性预算和归档，知识记忆继续使用本地 JSON，后台整理复用 asyncio，子任务复用同一个 Runtime。源码重构增加了模块，却尽量让状态只在明确位置修改。

当前的本地记忆规模适合简单检索，单机锁服务于工作区提交。增加系统规模时，重新测量检索成本和并发需求，再选择相应组件。

判断是否需要更复杂的组件，应回到具体失败。例如只有证据显示跨条目的关联检索是主要瓶颈，才有理由承担知识图或新检索服务的维护成本。

13.3 记忆演化和模型训练处于不同层

记忆整理更新外部知识，后训练更新模型参数。Aster 已提供共同执行内核、外部策略环境，以及带来源、划分、请求匹配和分组校验的数据契约。

10 月 18 日又加入 Qwen 工具调用解析和 token 采样接口：prompt token 直接送入生成器，采样出的 token、logprob 与 loss mask 原样记录；上下文前缀被改写时切成新段，避免重新分词改变训练样本。终止标签用于区分任务失败与基础设施失败。

这些接口已有离线验证。GPU 实测、R0 与 R4–R7 阶段、训练器和权重更新仍待完成；verifier 异常的轨迹标签还需与数据契约对齐。继续推进时沿用冻结题集、独立奖励和完整成本记录。
