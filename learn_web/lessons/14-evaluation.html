14｜从“能跑”到“证明有用”

上一章：交互与 Worker · 目录 · 下一章：环境接口（选读）

先定义要证明的结论，再决定任务、对照和指标。

一个看起来成功的实验

你给 Agent 很长的历史，它压缩了 60%，最后说“完成了”。这能证明什么？只知道输入变短、循环结束，还不知道代码是否正确。再补隐藏测试，才能判断压缩后任务是否完成。若要说“压缩节省了任务成本”，还需要同题对照，以及全部请求的真实用量。

这正是 Aster 把评测分层的原因。不同层回答不同问题，不应把几百条规则检查、少量真实模型任务和若干 token 配置加成一个总成功率。

评测层 想回答的问题 主要入口
基础回归 工具、状态、权限、恢复能按约定工作吗？ benchmark.py 的参考动作模式、tests/
上下文治理 输入是否合法、是否变短、压缩后还能做对吗？ 上下文压力配置及真实代码专项
记忆收益 项目约定与修复经验能否跨会话使用？旧事实会不会误用？ 跨运行任务、记忆演化场景
恢复正确性 重复、震荡、中断、漂移是否按边界处理？ Runtime 机制场景、故障注入任务

任务完成、效率、鲁棒性、安全是观察这些层的评价维度。例如权限拒绝可以是安全成功，但绝不能不分任务要求就算成任务完成。

题目、执行器和评分器分开

datasets/benchmark_tasks.json：题目与条件
           ↓
fixtures/ → 复制成干净工作区 → Runtime + 策略
                                     ↓ 候选代码
checks/   → 评分副本加入隐藏测试 → 独立验收
                                     ↓
结果目录：逐次记录 + 轨迹 + 检查点 + patch.diff

fixtures 是初始仓库。checks 是评测器持有的测试文件，在模型结束后才加入评分副本。这里“隐藏”指没有交给本次执行中的模型，不表示开源测试从未出现在基础模型的预训练数据中。

具体读一条 debug-and-fix 任务：它要求根据错误日志修复 src/handler.py 的循环，并执行测试。以下是原始数据节选，省略参考动作：

{
  "id": "debug-and-fix",
  "suite": "repository",
  "split": "evaluation",
  "fixture": "fixtures/long_session_debug_fix",
  "max_steps": 32,
  "max_turns": 24,
  "require_edit": true,
  "require_verification": true,
  "checks": {
    "phase": "completed",
    "verifier": "checks/debug-and-fix.py"
  }
}
字段 意思
id 稳定题号，跨批次用它对齐
suite 题型，例如仓库修改或函数实现
split 数据用途；当前这些题属于评测
fixture 在 datasets/ 下查找的初始文件目录
checks.phase 运行必须达到的状态
checks.verifier 结束后运行的独立代码测试
actions 参考动作，只给确定性回放使用

先读 checks/debug-and-fix.py：test_fix 检查最后一个元素是否被计入，test_regression 检查空输入仍返回 0。然后读 benchmark_support.py 的 prepare、run_task、external_check，跟踪一条题目如何变成一次实验。

三种“通过”分别是什么

第一种是 Runtime 完成检查：有没有看过工作区、发生修改、执行有效测试、产生要求的文件。这是约束执行过程，不能单独证明代码满足所有功能要求。

第二种是 独立代码验收：结束后在评分副本运行隐藏测试，检查候选代码。在 Aster 的主代码任务中，它与运行条件一起决定是否完整完成。代码通过但工具预算耗尽、没有正常收尾，报告仍保留这个差异。

第三种是 机制符合预期：例如关闭恢复时应停止、开启时应继续。这两组都符合各自预期，不等于两组都完成了同一个目标。因此机制报告把 expected（是否按约定工作）与 goal（目标是否达成）分开。

独立评分读取结构化 JUnit 测试结果，核对测试数量、名称、跳过、采集错误等；不是在 stdout 里搜一个 passed 就算通过。但候选 Python 代码与测试仍共享解释器，这不构成对任意恶意代码的绝对防作弊隔离。详见 评分边界（Markdown 原文下载）。

实验一：真正运行一条参考回放

本实验不调用真实模型。它从数据文件加载已有参考动作，走实际 Runtime 和 Linux 沙箱，保留一次临时报告，并检查原始版本失败、参考修复通过。需在项目根目录、Conda aster 中执行。

# 可运行实验
import json
import subprocess
import sys
from pathlib import Path
from tempfile import TemporaryDirectory

repo = Path.cwd()
assert (repo / "scripts/benchmark.py").is_file(), "请从 Aster 根目录运行"
with TemporaryDirectory(prefix="aster-eval-lesson-") as directory:
    result = subprocess.run(
        [sys.executable, "scripts/benchmark.py", "--task", "debug-and-fix",
         "--env-file", "/dev/null", "--output", directory],
        check=True, text=True, capture_output=True, timeout=180,
    )
    print(result.stdout)
    report = json.loads((Path(directory) / "report.json").read_text())
    row = report["rows"][0]
    baseline = report["baseline_checks"][0]
    assert baseline["fix_fails_before"] and baseline["regression_passes_before"]
    assert report["mode"] == "scripted" and row["passed"]
    print("参考动作通过:", row["passed"], "模型用量:", row["total_tokens"])

预期看到 baseline_target_fails=True、regression_passes=True、PASS，最后模型用量为 0。它证明参考动作能穿过真实执行链并产出正确候选，不能写成模型自主修复成功率。

需要保留文件慢慢看时，单独执行下面这条命令，打开报告中的运行目录：

python scripts/benchmark.py --task debug-and-fix --env-file /dev/null --output artifacts/learning-evaluation

如果 Linux 隔离能力不可用，应检查 第 04 章 的前提；不应为了得到绿色结果而绕过当前评测的 sandbox="required"。

实验二：自己算一次 Pass@k

每道题采样 3 次，不等于“36 次通过数就是 Pass@3”。设某题做了 n 次，其中 c 次成功，从这些尝试里随机选 k 次，至少一次成功的估计是：

Pass@k = 1 - C(n-c, k) / C(n, k)

C(a,b) 是从 a 个元素中选 b 个的组合数；失败次数不够选 k 个时，全失败概率为 0。对每题算完再平均，才是任务集合的指标。

# 可运行实验
import sys
from pathlib import Path

sys.path.insert(0, str(Path.cwd() / "scripts"))
from benchmark import pass_at_k

# 教学数字，不是 Aster 的实测成绩。
rows = [
    {"task_id": task, "passed": passed}
    for task, attempts in {
        "easy": [True, True, True],
        "hard": [False, False, True],
    }.items()
    for passed in attempts
]
print(f"Pass@1 = {pass_at_k(rows, 1):.2%}")
print(f"Pass@3 = {pass_at_k(rows, 3):.2%}")
assert abs(pass_at_k(rows, 1) - 2 / 3) < 1e-9
assert pass_at_k(rows, 3) == 1

输出是 66.67% 和 100.00%。这说明“每题三次内至少成功一次”可以很好看，但单次可靠性仍有不足。若每题只有一次样本，项目函数对 Pass@3 返回 None，不会编一个三次成功率。

如何设计一个可信的模块对照

以记忆为例，先让两组经历相同的读取与记录阶段，再在新的 Runtime 中回答同一问题；开关只控制长期记忆召回，源文件仍在。分别统计答案是否正确、重复读取次数和调用成本。不能只给开启组看过资料，再说关闭组输掉证明设计好。

以恢复为例，先固定重复调用或交替震荡的故障前缀，再比较后续是否达到同一目标。规则回放能证明运行时识别、阻止、纠偏是否触发；真实模型接手实验才能观察它是否会利用反馈。若真实模型两组都成功，应如实写“当前任务未显示增益”，继续按机制作用范围解释，不能硬造提升。

以压缩为例，要同时看下面四件事：

指标 计算或判断方式
压缩前后输入长度 对同一初始任务请求、相同协议和工具定义计数
平均压缩率 每次算 1 - after/before，再平均
压缩后的完成率 模型实际执行代码题，通过独立验收及运行条件
完整任务成本 汇总所有模型请求的 usage、工具调用和耗时

首请求压缩 60% 不能直接写成总计费节省 60%。提前失败的任务往往更便宜，所以成功率和全部尝试成本必须同时保留；比较成功任务成本时，最好列出共同成功样本数量，防止两组恰好留下了不同难度的题。

实例：用十个任务判断知识记忆是否值得保留

2026-10-05 记忆对照（Markdown 原文下载）选了 10 道针对性开发题，覆盖用户口头约定、纠正、适用范围、文件事实、修复经验及无关反馈。每题先学习，再用全新 Runtime 完成相关编码任务；纠正题多一次学习，每版共 21 个会话，两版合计 42 个会话。两组使用相同的 gpt-5.6-luna、任务、预算和初始文件，每题每组运行一次。

对照任务与三项断言和逐题汇总，可以直接核对下表的分母与失败项，无需重新调用模型。

这里比较的是“旧摘录记忆”和“可提炼知识的记忆”：两组都开启记忆、自进化与 Dream。学习阶段明确要求记住，由模型自己选择并调用存储工具；源文件和学习后代码继续可读。因此结果衡量定向学习后的复用，不能解释为打开默认开关就带来以下提升，也不直接代表日常任务中的自主保存率。

指标 定义 旧版 → 知识记忆版
严格复用成功率 复用阶段正常完成交付，且该题独立断言全部通过 4/10 → 7/10（40% → 70%）
功能通过率 仅看独立断言，不要求 Runtime 正常收尾 5/10 → 8/10
全流程通过率 学习、复用均完成，且复用断言全部通过 4/10 → 6/10
约束满足率（自定义） 每题三项行为断言，通过数除以 30 17/30 → 25/30（56.7% → 83.3%）
学习阶段 token 全部学习尝试的供应商 usage 418,533 → 601,745（+43.8%）
复用阶段 token 全部复用尝试的供应商 usage 1,320,700 → 1,166,425（−11.7%）
总 token 学习加复用，包含失败尝试 1,739,233 → 1,768,170（+1.7%）
复用工具调用 复用阶段实际工具次数 187 → 168（−10.2%）

任务成功率和 token 用量是常见评价维度；本项目定义的 30 项约束进一步检查是否遵守具体约定，分母与断言必须公开。可以使用自定义指标，但应解释它为何能体现用户需要的行为，同时保留功能、完成状态与成本，防止一个高分掩盖其他退步。这里文档读取仍为 5 → 5，不能套用旧实验的阅读节省比例。

为什么三个成功率不同？新版 CSV 代码通过断言，却耗尽预算没有正常交付，所以功能通过、严格失败；支付题在学习阶段反复写入失败，但复用仍可凭保留代码完成，所以严格复用通过、全流程失败。金额和用户纠正题还出现“口头说记住、实际没保存”。这些失败能指出下一步该修什么，不能从汇总中删掉。

主表冻结后只针对金额与支付做了两题补查。其中支付案例在去掉“记住”要求后完成了修复、自动提醒、保存及新会话召回，退款任务通过 3/3 断言；金额案例仍未保存。补查单列，不替换主表。最后的来源准入修正与默认开启调整也不属于主表源码的重复测量。

这组任务已经用于开发，足以指导本次轻量改造，但不是未见测试集或公开 benchmark，也不能证明统计显著性或记忆的独立因果贡献。简历可以写成：“在 10 道跨会话任务的内部对照中，后续任务完成率由 40% 提升至 70%，后续任务的 token 消耗降低 11.7%，工具调用减少 10.2%。”这里的“完成”指正常交付并通过全部验收检查；两个降幅包含全部后续任务的尝试，但不含首次学习与提取。完整报告保留两阶段成本，面试时解释统计范围即可。可直接参考简历草稿（Markdown 原文下载）。

后续实验：不说“请记住”，还能自动保存吗

2026-10-06 的自动学习十题对照（Markdown 原文下载）改变了这个触发条件：学习提示只介绍约定或要求修复，不再要求保存；增加两次补充同一规范的情形，并给最后一题较小的任务预算。两版各 22 个会话，包含相同的临时干扰标签。正常完成且通过从 4/10 → 7/10，功能检查从 4/10 → 9/10，30 项约束从 13 → 27 项；14/14 保存回执对应真实条目。已报告总 token 增加 12.6%，后续会话增加 20.0%，没有达到降耗目标。两组存在缺失 usage，基线服务失败更多，这些分差不能全部归因于记忆。它沿用开发题，不能与前一表混合成独立重复试验。

预先固定的协议（Markdown 原文下载）、任务和汇总分别记录条件、断言和数值。并发更正、取消恢复、无操作与失败不重试另由 test_memory_maintenance.py 检查，不把受控模型输出算成真实任务成功。

这里还需要三个观察：自动保存了多少任务中的知识；用户看到的保存回执是否对应实际条目；临时标签有没有混入长期知识。后续任务成功且召回旧知识可记为经验迁移，但不能证明记忆是成功的唯一原因。维护 token 已包含在总 token 中，不能重复相加；本地输入估算与供应商实际 usage 不同，未知消耗不能按零处理。CLI 的最多 15 秒收尾也计入总耗时。

金额题中，冻结版本曾因模型漏填适用范围而拒绝保存。这个失败保留在主表，后来把该字段改为输出必填项，只单独补查该修复。用户更正和文档题还出现代码通过独立检查、最终验证状态未满足而部分交付的情况：不能只看“有答案”就记为完成。这些区别比为了凑成功率增加多轮评测更有用。

降耗实验：缓存比例降低，费用也能降低吗

2026-10-07 的一日降耗对照（Markdown 原文下载）沿用十道开发题，在两题各增加一次重复学习请求，两版各 24 个会话。减少单项任务的流程往返，让 run_tests 直接携带临时测试源码，跳过已整理且内容未变的重复材料，并在父任务收尾时保留工具定义。记忆、自进化与 Dream 均保持开启，没有增加模型服务。

观察 当前版 → 降耗版 怎样解释
正常交付且独立验收通过 9/10 → 9/10 失败题不同，不能只凭这个数字说质量全面不变
独立行为断言 30/30 → 27/30 新版遗漏一条 CSV 约定；修改提炼指令后单题补查 3/3，保留主表失败
全部已报告 token 1,629,128 → 978,713（−39.9%） 包含首次学习、后台整理和全部后续尝试
后续任务 token 1,274,240 → 689,437（−45.9%） 包含失败；不是每道题都减少
未缓存输入 616,101 → 389,648（−36.8%） 与缓存输入、输出一起看，三个分量均下降
缓存输入占比 61.26% → 59.17% 命中占比没有提升，仍可减少完整任务开销
用量完整的尝试 186/188 → 121/124 未知失败和取消不能按零计费

总费用取决于输入量、缓存计价、输出及调用次数。减少往返后，便宜的缓存 token 也可能减少；不能为了提高命中占比保留无用请求。系统提示、原始任务和历史放在动态记忆之前，保护了固定前缀；加载工具、必要的历史压缩及版本升级仍可能影响缓存。这里的缓存占比是“供应商报告的缓存输入 token / 全部输入 token”，不是“有命中的请求 / 全部请求”。

最终交付只在后台提炼指令补充了适用范围的说明，修复 CSV 约定被“本轮确认”误带入临时信息过滤的问题。只补查这一题，没有重跑十题拼出更高成绩。主对照三个分量都下降，九种公开列出的价格权重均下降 37.4%–39.9%；缺少真实单价和部分 usage，不能写成账单节省。一次性模型研发消耗 3,181,015 tokens 另列，不混入用户任务成本，也不隐藏中止候选。

可下载运行前协议（Markdown 原文下载）、任务与断言、汇总数据、请求检查和单题补查。正式新版完整请求副本在临时目录消失后未保留，报告明确列出证据缺口；质量、用量 trace 和记忆快照仍可复算。基线与最终单题补查的完整工作区归档仍在。

SWE-bench 子集：官方评分与 Agent 完成状态

2026-10-09 的十题重测（Markdown 原文下载）使用 SWE-bench Verified 固定子集，按标注工作量划分为简单 3 题、中等 5 题、困难 2 题。每题一个新容器、一次新尝试，统一模型与预算，由 SWE-bench 5.0.2 官方 Docker 评分器检查目标修复和原有行为。Agent 看不到金标补丁与隐藏验收测试；十题都导出了非空补丁并完成评分。

最后的练习

为“修改后旧测试结论失效”设计一条机制场景。先明确目标，再列操作：跑测试成功 → 改文件 → 尝试结束。预期应是旧验证失效、要求重新测试，而不是仅检查返回值含有一个错误单词。场景参数放在 datasets/；执行器读取场景，复用现有 Runtime。

再想一个反例：如果关闭与开启 Hooks 两组都阻止重复 call_id，能把差异归给 Hooks 吗？不能。重复编号还有不可关闭的协议校验，需要隔离你真正消融的那项机制，见 第 08 章。

会话便利性的评测

会话管理可以改善操作体验，而没有提高模型任务通过率。可测量指定工作流的操作次数、需要手动补充的背景字符数、可恢复位置的覆盖和本地导航延迟。真人历史定位耗时与状态辨认正确率必须由真人操作采集；自动化脚本只能证明规定操作路径可执行。

本次会话操作协议（Markdown 原文下载）将旧历史定位、分支保留、模型恢复、摘录交接、重启恢复和多会话切换分别报告。旧版可行的恢复与多终端路径保留为对照；不把脚本模型调用数当作真实费用，不把三个内容变体当作三个使用者。

便利性也需要质量检查配套：真实编码回归（Markdown 原文下载） 让改造前后版本用同一模型与预算，分别完成相同的 5 道仓库修改题。core/all 工具集分别算完成率，另列独立代码测试、全部尝试的 token、工具调用和耗时；缺少计价信息时，货币费用保留为未测。若本批任务质量未下降，而操作次数减少，可以如实写这两个结果，不需要声称模型能力或成本改善。小样本不能证明所有任务都不退步，从新会话开始的编码任务也不能替代分支切换后的质量专项。
