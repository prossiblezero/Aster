## 实验配置

- 使用已有 `.env` 中的模型连接，不记录凭证或网关地址。
- 01–03轮使用`gpt-5.6-luna`，04–07轮使用`gpt-5.6-sol`，08–10轮使用`gpt-6-astra`，11轮使用`gpt-5.5`，12–14轮回到sol；协议均为Responses。切换不改变原`.env`，通过操作脚本参数覆盖并记录。
- 单次输出上限通常8,192 tokens；单文件阶段及最后收尾采用4,096；请求超时300秒。每轮实际配置见各自`launch.json`。
- 01–03轮总上下文884,092；04轮换模型时回退到24,000（可用输入约15,808）；05轮起显式配置128,000。04轮属于操作员漏配预算，不能把其重复阅读直接归咎于模型能力。
- 单任务最多140次工具动作、100次模型请求；不启用子Worker及跨运行记忆，便于核对单条自主执行轨迹。
- `sandbox=required`、`network=false`、`write_scope=["website"]`、`completion=strict`。
- 成功必须包含实际工作区观察、修改和 `run_tests` 验证；必须交付index.html、README.md和.nojekyll。此判定不代替独立的内容与浏览器验收。
- 浏览器独立验收使用安装在aster环境中的Playwright与Chromium，它不是Aster现有内建工具。操作员的浏览器检查不计入Aster自主验证能力。

## 本次实测支持的判断

网站主体可以由Aster的真实模型—工具循环生成，任务范围已超过单文件小修改：包含课程转换、站内源码、构建、样式、交互和验证。但默认模型的首次执行没有独立完成交付；后来需要操作员定位问题、明确返修要求、调整预算、切换模型、拆分任务和浏览器验收。这是一份有监督的真实工程案例，不能包装成“一句提示全自动完成”或Aster自主多Agent成果。

当前证据支持继续修具体执行闭环，不足以支持照搬pi并整体重写核心。下一轮优先级：

| 优先级 | 要解决的实际问题 | 最小可验证改进 |
|---|---|---|
| P1 | 工具误用与无效动作循环 | 启动时提供可用命令/环境摘要，明确search与patch契约；用本次反复读取/修改失败轨迹做回归任务 |
| P1 | 网关慢响应、断流与未知用量 | 在产品Provider中设计可取消的进度显示和有限恢复；完整终态前不执行工具，继续保留失败证据和未知usage |
| P1 | 模型切换后预算回退、长历史重复发送 | 展示生效的模型/预算及回退原因；用本次轨迹衡量总输入、重复读取与归档回读，验证再调整压缩策略 |
| P1 | 自测与成品质量脱节 | 让任务按产物声明验收命令；网站任务加入可选浏览器检查，至少覆盖深层路径、异常存储和固定页头锚点 |
| P2 | 返修依赖新任务及操作脚本 | 提供已有任务的明确续作/反馈入口，保留原规格与验收状态，区分checkpoint恢复和持续聊天 |

pi适合作为小核心、清晰工具与会话抽象的参照；本次没有做相同模型、同网关、同预算的pi对照运行，不能据此宣称Aster优于或落后pi多少。网关稳定性、模型能力和Harness设计的影响也不能从这些连续返修轮中单独分离。
