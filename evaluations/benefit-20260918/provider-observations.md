# 本轮服务端响应诊断

**目前可以确认两次项目启动都因不可用的空模型回复停止，不能据此认定输出上限太小、Memory 无效，或 Aster 不会编写这个项目。** 第二次已经记录到服务端 `completed` 配合空 `output` 数组；首次缺少这个观测，证据强度不同。缓存实验还发现同一请求对应不同服务端统计，后续评测必须将服务可用性与功能收益分开记录。

## 首两次项目启动

| 记录 | 模型轮 / 工具步 | Runtime 终态 | 已报告输入 / 输出 tokens | 缓存读取 | 可确认的响应结构 |
|---|---|---|---|---:|---|
| [base](results/base.json) | 1 / 0 | failed / empty_model_reply | 6,591 / 129 | 0 | 产品解析出空正文和零工具；未采集原始 output 结构 |
| [base-recovery-1](results/base-recovery-1.json) | 1 / 0 | failed / empty_model_reply | 6,591 / 120 | 5,632 | status=completed，output_type=list，items=[]，即 output=[] |

两次配置均为 `gpt-5.6-sol` / Responses、非流式、128,000 总上下文、**32,768 单响应输出上限**，产品源码冻结于 `dfe64ef50601b74acc75a7ebc8a309939c3eb38b`。本地 launch 与首轮请求归档确认：两次模型输入完全相同，输出参数均为 32,768，工具定义均为 9 个，源码与需求文档未漂移。

129 和 120 个已报告输出 tokens 都远低于客户端上限，各含 8 个推理 tokens，不能把推理量再次加到输出中。第二次返回的是 completed，没有已记录的长度终止证据。因此不应将这两次失败归咎于我们给 coding 任务设置了过低输出上限；服务端是否另有未披露限制，现存证据不能判断。返回的 usage 有输出计数，也不保证对应的内容或工具调用实际交付到客户端。

两次均启用 Memory，但从新工作区开始，没有预置经验、没有激活 Skill，工具动作和记忆保存均为零。它们尚未进入经验积累与跨会话复用阶段，也没有形成 Memory 开关对照。因此不能拿这两次终止评价 Memory 收益，亦不能确定 Memory 是空回复的原因。第二次已经命中 5,632 个缓存 tokens，仍然停止，说明缓存命中和能否拿到可用回复是不同指标。

失败投入必须保留：两次已报告总 tokens 合计 **13,431**，运行墙钟合计 **51.85 秒**，没有候选实现可验收。两份结果中的 `http_attempts` 都是 null，只能说各发生一轮模型调用，不能补写成各一次 HTTP POST 或零传输重试。

这两次仍属于用户实际遭遇的整体交付失败，不能因为可能涉及网关而从 Aster 的可用性评测中剔除。当前 Runtime 遇到空回复直接停止，是否应提供有界恢复及更明确的诊断属于后续产品问题；本轮人工恢复不证明自动恢复已经可用。

## 流式恢复和缓存观测

按 [执行修订](AMENDMENTS.md)，最后一次允许的基线恢复改用已有 Responses 流式接收，名称为 `base-recovery-2-stream`，其他需求、产品源码和预算保持一致。本次诊断读取时，其轨迹已有 **7 个成功工具结果**，包括文件枚举、差异检查和文档读取，尚未有任务完成事件。这证明流式尝试已越过前两次首轮空回复的位置，不代表项目已交付，也不证明非流式一定有缺陷或流式普遍更快。

三次 Runtime 归档的首轮请求主体相同；流式的 `stream=true` 是在传输层添加的，所以不能说三次实际 HTTP JSON 完全相同。恢复过程算人工恢复，前两次失败不能从成功率和总投入中删除。后续 Skills/Memory 对照的传输模式按修订统一，不能混合两种模式作收益归因。

[独立缓存实验](cache/report.md) 的六次完全相同请求返回缓存读取 `0、0、0、0、9984、5632`，确认当前服务在部分请求中确实提供缓存。它同时记录到：请求模型始终为 `gpt-5.6-sol`，三次响应 model 标签为 `gpt-6-sol`；相同 JSON 的报告输入在 5,874/10,184 之间变化，instructions 归因在 66/4,529 之间变化。即使布局组 model 标签相同，统计差异仍然存在。这是服务端返回值的观测，不能仅凭标签断言底层模型身份，也不能仅凭这些差异判定具体网关实现。

缓存实验最后一次同样解析到空正文，但未保存完整 output 结构；不能将它回填解释为本次已确认的 output=[]。本轮对第二次项目启动新增结构观测，正是为了区分“服务端空数组”和“客户端未识别输出块”。后续仍需同一响应的请求 ID 和结构信息才能继续定位。

## 今后核心日志建议

1. 同时保存请求 model/profile/protocol 与响应 model；标记不一致，保留原标签，不自行认定或替换底层模型。
2. 保存 response ID、白名单 request-id/路由/缓存响应头及连接指纹，不记录地址、认证信息或全部响应头。用这些信息关联服务端排查。
3. 原始 usage、统一计数和字段覆盖率一起保存；保留 attribution，并标记总计与分项不一致，不擅自补零或改成看起来合理的数。
4. 按每次 HTTP attempt 记录请求哈希、开始/首事件/终态时间、状态和重试，区别模型轮数与真实请求次数；网关内部重试仍标为未知。
5. 保存脱敏的终态结构摘要：status、incomplete_details、输出 item 类型/phase、内容块类型、文本长度和工具数；对 completed 但无可用内容单独发诊断事件，不保存推理正文。流式也保存终态摘要，不能只监测非流式 `_post`。

本诊断只读取既有结果、launch 和轨迹，没有追加模型请求、修改候选或产品源码。上述原因分析保留未知项，不以恢复成功反向改写前两次失败。
