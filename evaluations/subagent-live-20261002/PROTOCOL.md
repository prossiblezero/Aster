# 恢复服务后的增量交付对照（2026-10-02）

本协议和驱动在第一个任务回合前冻结。健康请求已成功，服务仍配置为 gpt-5.6-luna、Responses 流式接口；健康请求单列，不纳入任务成绩与成本。

## 24 个首次回合

复用 subagent-light-20260930 的六道已见只读调查/受限审查题、源码快照、行为 oracle、AST 引用评分器及输出契约，每组每题一次，固定四组：

1. `baseline_parallel`：本轮 21 行改动前的版本（11,993 行，包含 worker_finish 精选来源），两个子任务同时调查，父任务发起列表等待；该版本等待全部结束。
2. `candidate_solo`：当前版本，父任务独立完成，不创建子任务。
3. `candidate_parallel`：当前版本，同样两个工作包、同样的列表等待；新版本任一结果就绪即可返回，父任务随后运行并决定如何整合和继续等待。
4. `candidate_overlap`：当前版本，第一工作包交给一个子任务，父任务立即处理第二工作包并整合。

双子任务两组均由驱动在启动后执行一次真实 `Runtime.step(worker_status(ids, wait_seconds=300))`，该工具计入父方历史和团队额度。之后由模型继续控制父任务。不使用旧驱动的 Python gather 屏障，以免绕过本次优化；不将这次调度协议的结果与旧实验直接拼接成因果比较。首个列表等待是明确的实验操纵，不代表模型自主选用了最佳调度。

基线来自上轮保存的未提交源快照，逐项核对哈希；不是 Git HEAD，也不是 2026-10-01 版本。因此两组双子任务的源码差异恰好是增量等待、消费修复、模型消息精简及对应提示，共净增 21 行。Solo 和父子同时工作两组是使用方式对照，不能分离精选来源接口本身的贡献。

任务回合串行，回合内部真实 Runtime 并发。固定六种组内顺序沿用 selected 实验，每组在每个位置出现一到两次；全部首次结果保留，不择优重跑、不修补 JSON、不调整评分。每组 6 回合、48 个事实，总计 24 回合。

## 条件与统计

全部组使用相同模型、端点、任务数据、工具权限、团队上限：36 次模型请求、60 次工具、300,000 已报告 token、600 秒。Memory 关闭，严格完成检查开启，读取并行度为 1，网络工具关闭。健康请求使用更小输出上限；正式任务使用既有 8,192 输出上限。

主要指标：严格整题通过、严格事实正确、全队已报告 token、耗时。通过同时要求父任务正常完成、评分通过、源码与任务文件未变且驱动无异常。JSON 不可解析仍失败，但不等同于所有行为答案都错。

诊断包含父方读取次数/行数、父读取中子任务此前读过的相同版本行段、worker_finish 尝试/接受次数、选中来源字数、父方在最后一个子任务完成前收到的模型响应次数，以及状态等待返回时同时存在已交付/仍运行子任务的次数。行段重叠不自动等于无意义复核，提前收到父响应不代表有效整合已完成。

HTTP 重试全部记账，未知 usage 单列，token 不换算价格。若一个回合的所有 HTTP 尝试均被服务拒绝，驱动停止后续批次并保留该回合，不将鉴权失败当模型能力。其他失败如超时、预算耗尽和格式错误保留正常评分，不以成功重跑替换。

六道题来自三份源快照，是开发期已见样本；每组一次不足以证明显著性、保留集能力或普遍收益。该实验是显式只读分工，不涵盖自主拆分、写入/合并或默认启用委派。
