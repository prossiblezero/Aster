## 改动与已验证的原因

- **临时项目的配置隔离。** 原先 `TMPDIR` 在工作区 `.tmp` 下，嵌套 pytest 项目会
  向上找到仓库的 `pytest.ini`，错误继承 `--strict-markers`。新增回归用例在旧代码
  上因未知 marker 失败；修复后通过。现复用每个命令的临时目录作为项目树之外的
  `TMPDIR`，Landlock 仅额外允许这个目录，退出后删除。工作区发布和依赖保护保留。
- **通用验收提示。** 强调原复现步骤、被修改共享代码的邻近测试、真实接口的类型和
  顺序、空输入、组合操作与生命周期故障路径；先完成实现与回归，再处理可选整理。
  明确工具在工作区副本运行，应使用相对路径。没有加入题目 ID、答案或隐藏断言。
- **评测解释器适配。** 旧适配器用任务的 Python 3.6 启动 Aster 的现代 Python
  沙箱脚本，导致 Django 11400 的测试和写文件都无法启动。现在用 Aster 的 Python
  启动隔离器，仅任务命令切换解释器，只读允许其运行库路径。真实旧版镜像预检已通过。
- **沿用已披露的环境修正。** 两道 pytest 题使用随当前执行目录导入源码的适配，保留
  镜像中已有的生成版本文件；gRPC 使用前轮专用 Docker 容器的后台服务生命周期适配。
  持久服务适配仍不是生产 Aster 的功能。

生产改动范围为三个文件，见 [source.patch](source.patch)。完整测试 **1229 通过、
4 跳过**，Ruff 检查通过；[测试输出](production-tests.txt)与[真实镜像环境预检](environment-preflight.json)已保存。

本轮另确认了一项尚未修改的评测准备缺陷：Sphinx 9230 镜像原本跟踪
`tests/roots/test-pycode-egg/sample-0.0.0-py3.7.egg`，但旧运行器删除 Git 历史后用
`git add .` 重建基线，该文件因忽略规则失去跟踪，未被复制到 Aster 的执行工作区。
已分别读取原始镜像与本轮容器的索引核对。其 egg 相关自测因此导入失败，最终达到
900 秒上限；产出的补丁通过独立评分。本轮未中途修改适配器，也不把这次超时称为正常交付。

## 复测条件

模型 `gpt-5.6-luna` / medium、Responses 接口、64000 上下文、8192 输出上限、
每题 900 秒、4 CPU / 8 GiB、单 Agent、空会话；两题并发。原二十题的题面、镜像
和独立测试保持原样，源码及评测输入已经[冻结](manifest.json)。本轮不与旧尝试择优合并。

这些题的失败已用于诊断和优化，因此本轮属于开发集复测。pi 和 Codex 沿用历史成绩，
环境和运行时间也不完全一致；结果不能解释为未见测试集上的稳定排名或单一改动的因果收益。
