# GPT Worker 与跨会话 Memory 真实执行评测

本批使用现有 GPT 配置（返回模型标签 `gpt-5.6-luna`）、真实流式 API 和 Aster 工具执行，产品版本固定为 `7462e8b`。没有改动产品源码、人工修复候选代码或接入 DeepSeek。题目是围绕实际维护需求构造的小型 Python 仓库，不是线上用户任务样本。

## 结论

- 基础 Memory：两个项目、各三轮新会话维护，关闭与开启均通过 **6/6**；累计文档读取 **27→22（减少 18.5%）**，已报告总 token **718,454→574,576（减少 20.0%）**。包含一次共享熟悉任务的对称成本后为 **799,231→655,353（减少 18.0%）**。这是本批样本的观察值。
- 反馈维护：同样通过 **6/6**，但六组配对任务首请求召回的条目集合与基础 Memory 相同，其中一组排序改变；本批没有建立反馈维护改善召回覆盖或正确性的独立证据。它确实将两个过期来源记忆显式标记失效；基础检索也已能过滤这些旧来源。
- Worker 自主选择：开启组 **0/6** 实际委派。工具名称在 `tool_load` 的可加载目录中，默认 core 并未直接加载 Worker schema，因此这一结果包含工具发现和工作流选择因素，不能当作并行执行效果。

- Worker 明确委派：两题均启动两个子任务，整体验收 **2/2**，但正常完成的子任务只有 **1/4**；总耗时 **+21.0%**、已报告 token **+132.0%**，本批没有建立委派的效率收益。

## 记忆维护究竟做了什么

两个项目迁移协议时，basic 和 maintained 各 **2/2** 没有在实际首请求的 memory 区块中带入旧 wire 摘录，且迁移与前序功能均通过外部验收。来源哈希失效过滤本来就存在于基础检索中，不能将这一共同结果独占归因于 Dream。

maintained 的六次 Dream 都执行了：四次没有停用条目，两次各将一条旧 wire 记忆标为 `stale_source`。没有出现需要通过失败反馈淘汰的条目；六组配对任务首请求召回的条目集合均与 basic 相同，其中 Agenda 协议迁移的两条记忆顺序互换（1/6 组排序不同）。这批任务确认了维护动作和排序变化，尚未证明它改善召回覆盖或带来额外交付收益。较低的汇总 token 不能单独证明“记忆自进化”。

事后检查发现具体的检索缺口：首次导出各需 wire、identity、weight/time、order 四类约定，两个项目首请求都只覆盖 **2/4**。Parcel Top-3 含泛化 README 说明，漏掉 wire 与 identity；Agenda 含 display 规则，漏掉 wire 与 time。证据来自保存的实际请求，不是事后猜测模型是否看到记忆。该覆盖口径仅作诊断，未在中途修改检索、提示词或保存内容。不能将本批收益不足简单归因于 GPT 太强，也不能用本批结果推出必须换用 DeepSeek。

## 明确委派补充

两题的新 solo 与 directed 都通过 **2/2** 独立验收。明确要求委派时，实际启动率是 **2/2**，与自主选择的 **0/6** 分开报告。

| 任务 | solo 秒 | directed 秒 | solo token | directed 父 token | directed 子 token | 子任务正常完成 |
|---|---:|---:|---:|---:|---:|---:|
| csv-ledger | 307.2 | 376.4 | 118,413 | 167,168 | 102,088 | 1/2 |
| access-report | 111.7 | 130.5 | 91,538 | 198,115 | 19,726 | 0/2 |
| 合计 | 418.9 | 506.9 | 209,951 | 365,283 | 121,814 | 1/4 |

全部父子总 token 为 **487,097**，相对对照 **+132.0%**；总耗时 **+21.0%**，配对耗时变化中位数 **+19.7%**。两次 directed 尝试都存在真实并行，保存的 `ModelClient.complete` 调用区间最多有 **3 个重叠**（父任务加两个子任务；区间含传输等待和重试，不是纯模型计算时间）。并行发生不等于端到端加速。

四个子任务中，一个正常完成，一个达到 `step_limit`，两个被父任务主动 `worker_stop`。第一题父任务在集成时还修改了子任务负责的导入模块；第二题取消子任务后，父任务继续实现并验收。整题通过不能当作四个子任务都完成了委派。

两题合计 **22 次协调调用**：4 次启动、16 次状态查询、2 次停止。三个实际写入的子任务均只修改了各自声明的文件，另一个取消前没有写入；未观察到范围外写入。没有主动构造并发冲突，也没有依据可以填写“冲突拦截率 100%”。

这批小模块任务暴露了发现工具、状态查询、子任务预算和提前取消等具体问题，支持保留真实执行证据来改进委派工作流；不支持把“并行提速”写进简历，也不支持据此断言所有更大任务都不会受益。

## 验证、成本边界与复现

独立评分器在模型执行前验证了 12 个任务/阶段配置：空实现失败、参考实现通过、逐模块删除失败；这是评分器预检，不是新增主工程测试数。模型完成后才在隔离副本中放入验收文件，检查实际执行的测试名称、数量与结果。候选与评分器仍共享 Python 解释器，未声称抗恶意候选执行。输入行歧义的修订也说明该预检不能覆盖所有需求遗漏。

主批次 32 次与补充 4 次全部完成；其中 **34 次编码尝试**按最终统一口径均通过独立验收，另外 2 次为只读熟悉任务。各条件结果已分组给出，不将这些相关重复样本解释为普遍通过率 100%。

全批次共 **362 次逻辑模型调用、368 次 HTTP 尝试**，其中 360 次有 usage，覆盖率 **97.83%**；6 次传输失败与 2 次取消没有 usage，不能视作零消耗。已报告输入 **3,778,116**、输出 **108,887**、总 token **3,887,003**；缓存输入 **2,333,184** 和推理 **31,325** 是其中子集。360 次有模型标签的响应均为 `gpt-5.6-luna`；这是网关返回标签，不额外声称验证了服务端模型实现。

核对通过：36 次矩阵完整、父子运行用量与逐请求账本一致、所有冻结驱动与产品源码摘要一致、被要求保留的任务文档未被候选更改、实际首请求包含记录的召回文本。Ruff 与 `git diff --check` 通过；本轮没有向主工程增加测试项，也未为评测材料重复运行全量工程测试。
