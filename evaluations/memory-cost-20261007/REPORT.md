# Aster 一日降耗：十题对照与缓存检查

2026-10-07。十道跨会话任务中，已报告总 token 从 **1,629,128 降至 978,713（−39.9%）**，包含首次学习、后台整理和后续任务。未缓存输入、缓存输入、输出三个计价分量均减少。正常交付且通过独立验收的任务同为 **9/10**，但功能断言从 **30/30 降至 27/30**：新版漏存一条 CSV 约定。修正提炼指令后，这一题的单独补查通过 3/3，不替换主表，也不能据此宣布整组质量没有退步。

供应商未提供可核实的实际单价，两组分别有 2、3 次尝试缺少用量。因此本文报告已知 token 和明示价格权重下的估算，不把它们写成真实账单降幅。

## 改了什么

调研与实施前设计见 [一日降耗方案](../../docs/cost-optimization-20261007.md)。五篇 2026 年 arXiv 论文、pi 源码、LightMem 源码以及 Codex/Claude Code 的文档分别用于判断维护触发、工具往返和缓存代价；不把预印本写成已接收的 CCF-A 论文。来源与原始阅读材料保存在 [research-sources.json](research-sources.json) 和 [research-reading.zip](research-reading.zip)。

生产修改集中在六个文件，没有新增依赖、服务或配置开关，记忆、自进化、Dream 仍默认开启：

1. `run_tests` 接收可选临时测试源码，在已有隔离副本运行 pytest/unittest，沿用结构化结果、来源版本和文件写入检查；无需先把一次性测试写到工作区，再读、执行、清理。
2. 单项实现及其验证视为一个交付，直接从指定文件开始；独立的多项交付仍使用待办。必要的项目测试与检查保持原有要求。
3. 父任务进入预算收尾时保留工具定义，由执行入口禁止继续调用，减少一次工具前缀变化。子任务保留原有收尾行为。
4. 已成功整理且工作区、日期、提炼契约、记忆内容版本均未变化的相同材料，不再触发提炼调用。失败、取消、候选被拒和来源变化仍重新考虑；后台输入只保留真实证据，省去助手答案摘要。

工具与提示词同时改动，这一组实验不能分离各项机制的独立贡献。正式新版实际使用了 12 次临时测试源码入口、跳过了 2 次相同材料整理。

## 条件与版本

依据 [运行前协议](PROTOCOL.md)，使用同一 `gpt-5.6-luna`、Responses、32,768 上下文预算、4,096 输出预算和本机原有模型账户。每会话上限 20 轮、30 工具步、200,000 团队 tokens；最后一题沿用 8 轮、80,000 tokens。Memory/Evolution/Dream 全开、Workers 关闭，CLI 维护收尾最多 15 秒，计入耗时。

[cases.py](cases.py) 沿用已参与开发的十题和 30 项独立行为断言，只在时区、文档两题各原样增加一次学习请求。两组各 **24 个会话**（14 次学习、10 次后续任务），共 48 个。每题每版一次，失败不重跑覆盖；它不是未见测试集，不报告统计显著性，也不能与上一轮每组 22 会话的总量直接比较。

| 版本 | 证据与用途 |

| 当前版基线 | [baseline-source.json](baseline-source.json)、`baseline-sources.zip`；本轮改动前工作树，包含上一轮交付后的修正 |

两组 `environment.json` 中的全部 56 个生产文件哈希、题库哈希与运行器哈希均与冻结记录一致。最终交付版与当前生产文件逐项一致。初始工程候选及其失败另存于 `prototype/`，没有从多轮成绩中选择最好结果。

## 缓存前缀与费用分量

当前请求顺序为 **固定系统规则 → 初始任务 → 已有历史 → 动态状态和记忆**。记忆变动不会被插入系统规则之前；后台整理有独立的固定提炼指令。父任务收尾继续保留工具定义，因此本次优化没有把动态记忆搬入固定前缀。

但不能承诺命中比例不下降：版本升级修改了系统提示与工具 schema，旧缓存不一定适用于新版；按需加载工具、必要的历史压缩、模型/权限变化也可能改变连续前缀。服务端缓存寿命与路由不由 Aster 控制。

| 已报告费用分量 | 当前版 | 降耗版 | 变化 |
|---|---:|---:|---:|
| 未缓存输入 U | 616,101 | 389,648 | **−36.8%** |
| 缓存输入 C | 974,336 | 564,736 | −42.0% |
| 输出 O | 38,691 | 24,329 | −37.1% |
| 缓存输入 / 全部输入 | 61.26% | 59.17% | −2.09 个百分点 |
| 前台缓存输入占比 | 63.29% | 58.12% | −5.17 个百分点 |
| 后台缓存输入占比 | 37.24% | 71.00% | +33.76 个百分点 |

缓存占比下降与整体输入减少可以同时发生。新版前台调用更少，长历史重复输入也更少；本实验没有控制服务端冷热缓存，不能把比例变化全部归因于某一处提示词改动。结果支持已报告费用分量减少，不支持“缓存命中率提高”的宣传。

可重算的请求检查见 [cache-audit.json](cache-audit.json) 和 [audit_requests.py](audit_requests.py)：基线归档 163 份请求，系统与初始任务在会话内均无变化；最终交付版 CSV 补查归档 10 份请求，7 对相邻请求中系统、任务、工具和此前历史均保持原样，动态内容全部位于末尾。正式新版的完整请求归档存在下文所述缺失，不能把全组前缀检查当作可独立复核的证据。实测缓存 token 则来自已保存的供应商诊断 trace，可以重算。

## CSV 修正与单题补查

失败并非模型不知道 BOM 和分号：它提出了正确约定，却在 `when` 中写入“这是本轮确认的项目约定”，被已有临时信息过滤拒绝。下一次补充列名时，只存下了列名以及“沿用此前规则”，已丢失的编码/分隔符无法自动恢复。后续 Agent 采用普通 UTF-8 和逗号，自测没有覆盖遗失的约定。

最终交付只增加一句提炼指令：适用范围描述规则适用于哪里，不描述哪次对话确认或当前任务省略什么。没有放宽临时信息准入，也没有增加失败后的模型重试。54 项相关工程检查通过后，在新工作区运行一次同题的两次学习和后续实现，保存正确约定，后续正常交付并通过 **3/3** 独立断言。

补查成本 **93,292 tokens**（学习 23,578，后续 69,714），12/12 次尝试用量完整，最终待整理数为 0。见 [scope-followup/summary.json](scope-followup/summary.json)、对应 `results/` 和 `workspaces.zip`。首次学习已经落盘后，进度打印因相对输出路径报错；改用绝对路径续跑，直接读取已保存的第一轮，没有重复任何完成的会话。日志保留该错误。

这说明已观察到的遗漏得到修复，不能把单题补查拼成“最终版本十题 10/10”，也不能把主表降耗数字视为对最终一行修正重新测量后的数字。

## 研发成本、异常与证据边界

最初候选在完整工程检查暴露小上下文及子任务收尾回归后中止。其源码、失败日志、完成结果和未完成工作区保留在 `prototype/`。已报告开发消耗 **479,882 tokens**，67 次尝试中 1 次缺少用量，不计入正式两组胜负。加上两组主对照与 CSV 补查，本轮模型实验累计已报告 **3,181,015 tokens**；这是一次性研发消耗，不是运行一个用户任务的费用。

主对照未知用量：基线有一次 15 秒维护取消、一次前台传输失败；新版有一次 15 秒维护取消、两次前台传输失败（其中一次约 120 秒）。耗时受服务波动影响。没有使用重试成功后的单次费用覆盖之前的尝试。

结果整理阶段发现 `/tmp/aster-cost-*` 临时目录已消失，正式新版完整工作区 zip 未保留下来。该组全部 24 个会话结果 JSON、24 份压缩 trace、最终代码产物、记忆前后快照、审计与维护事件、pending 数及冻结源码仍完整，可以重算质量与费用；但该组原始 `requests/`、完整 `jobs/` 和 checkpoint 不能再从归档恢复。这偏离了最初计划的全量工作区留存。基线与单题补查的完整工作区归档仍在且通过 ZIP 完整性检查；不为了补齐附件重新付费运行实验，也不把缺失请求当作零次变化。
