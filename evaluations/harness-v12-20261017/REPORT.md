# Aster v12 评测报告（2026-10-17）

设计和每项改动的说明见 [docs/harness-v12.md](../../docs/harness-v12.md)。本报告只列数据和结论。

条件与此前一致：

- 模型 `gpt-5.6-luna`，Responses / medium，上下文 64,000，输出上限 8,192；
- 每题 900 秒，4 CPU / 8 GiB，6 槽并发，单 Agent，自动记忆开启；
- 每题只跑一次，不择优。

加权成本 =（未缓存输入 × 1.25 + 缓存输入 × 0.125 + 输出 × 10）/ 1e6，含后台请求，只用于相对比较，不是账单。pi、Codex 和优化前 Aster（`c6b651d`）的数据来自 2026-10-12 的 50 题评测。

## 1. 结论

0. **v13（第 10–11 节）**：在冻结的留出集 fresh30 上按题配对，v13 相对 v12 的独立通过为 −1 [−3, +1]，没有显著提升；请求和成本约 −8% 至 −9%，区间上界刚越过 0。v12 与 pi 通过率持平（0 [−2, +2.5]），请求数仍显著多于 pi 和 Codex。v13 的收益是常驻服务、构建类项目的正式验证和 CI 中的开销门禁；留出轨迹暴露的门禁缺陷在 v13.1 和 v13.2 中修复，修复后的版本只在开发集上验证。
0. **v12 最终版（rc5，第 9 节）**：留出集独立通过和正常交付均为 23/30，与 pi 持平；成本比优化前降低 57%，仍是 pi 的 1.43 倍、Codex 的 1.23 倍；模型之外的时间降低 81%。以下 1–4 条是第一天 rc1 的结论。
1. **留出集质量与 pi 持平。** new30 是 30 道从未用于开发的题。v12 独立通过 23/30，与 pi 相同，高于 Codex 和优化前 Aster（均为 21/30）。
2. **相对优化前 Aster 降本 46%**（留出集，去掉 regex-chess）。这部分主要来自 v9–v11 的缓存工作。成本仍是 pi 的 1.8 倍、Codex 的 1.5 倍，差距几乎全部来自请求数。
3. **v12 的收益在时延、可靠性和评测可信度。**
   - old20 上模型调用之外的时间从 3,663 秒降到 1,021 秒（−72%）。
   - checkpoint 从每次 1,078 ms 降到 124 ms。
   - 正常交付且通过达到 14/20，是 Aster 在 old20 上的最好成绩。
4. **v12 没有减少请求数。** 两次 v12 old20 运行的请求数都落在历史运行的波动范围内，偏高约 7%，单次运行无法区分。工具反馈类改动没有可测收益。

v13 的改动见 [docs/harness-v13.md](../../docs/harness-v13.md)。new30 在 v12 中已经跑过两次，从 v13 起与 old20 一样只作开发集使用；留出结论来自第 11 节的 fresh30。

- **计时**：rc1 的两个评测同时以 6 并发运行，所有 harness 计时都偏高约 3 倍。rc2 起主机上总并发保持为 6，计时恢复正常（checkpoint 93–127 ms）。

### 11.3 结论

1. **v13 在留出集上没有提升质量。**
   - 独立通过 −1、正常交付 −2，置信区间都包含 0。
   - 请求数 −8%、成本 −9%，区间的上界刚好越过 0，只能说“可能略省”。
   - v13 的新能力在 fresh30 上几乎用不到：fresh30 的两道终端题都是数据库恢复，不需要常驻服务。只有 4 道 C++ 题会用到按退出码判定的测试。
2. **和 pi、Codex 比较。**
   - 质量：v12 与 pi 持平（0 [−2, +2.5]）。v13 低于 Codex（−2 [−4, −0.5]），差距显著。
   - 请求数：两个 Aster 版本都显著多于 pi 和 Codex，多出 30%–50%。
   - 成本：去掉离群题后，Aster 约为 pi 的 1.6 倍、Codex 的 1.4 倍。
3. **按类别看。**
   - Aider 题四者都是 10/10。
   - 仓库题：v13 为 7、7，v12 为 7、7，pi 为 6，Codex 为 7。
   - 差距集中在 BigCodeBench：v13 为 7、5，v12 为 7、7，pi 和 Codex 都是 8。这一项在 new30 上同样如此，v13 两次是 5、3，v12 两次都是 6。在 BigCodeBench 上，v13 每题的请求数比 v12 少约 25%。从轨迹看，翻转发生在模型第一次写出的实现上，例如图上画了 2 条线、规格要求 1 条；没有找到 harness 层面的原因。可以确认的只是方向一致，但单看任何一个数据集都不显著。

### 11.4 留出轨迹暴露的缺陷与 v13.1

v13b 中有两道题通过了判分，却以 `completion_requirements_failed` 结束：

- **aider-cpp-phone-number**：模型的一条 g++ 测试命令把可执行文件输出到 `/tmp`，沙箱不允许写入，命令失败。这条失败按命令字符串记了下来。之后模型改用 `.tmp/` 输出并通过，但原来那条命令再跑也只会以同样方式失败，这条失败无法消除。new30 上的 aider-cpp-meetup 也是同样的原因。
- **sqlite-db-truncate**：模型自己写的内联测试期望值有误，门禁按规则要求它通过。这是既定行为，没有修改。

v13.1（`68d69d3`，标签 `v13-1`）的改法：按退出码判定的失败只把验证状态置为失败，不再记成必须消除的“失败测试”；之后任何一次通过的项目测试命令都能把验证状态置为通过。逐用例失败的规则不变，仍然必须让同一个用例重新通过。

这个缺陷是看了留出集轨迹才确认修复的，因此：

- fresh30 上的数字仍然是 v13-rc3 的；
- v13.1 只在开发集上验证，不对 fresh30 做任何声明；
- 今后若要再声明留出成绩，需要重新抽一套题。
