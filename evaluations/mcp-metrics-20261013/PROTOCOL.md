# MCP 指标实验（2026-10-13）

用户要求测量 MCP 指标，明确不测备用服务。实验不配置备用服务器，不向 GitHub 写入。模型通过项目 `aster` Conda 环境调用 `.env` 中已有的 `gpt-5.6-luna` Responses 配置；本地写入仅发生在忽略目录 `artifacts/private/mcp-metrics-20261013`。

## 事前固定

- `cases.json`：8 类任务（仓库定位、固定提交的 package.json、指定 Issue、指定提交、本地目录读取、创建汇总文件、条件更新、条件删除），每类每组重复 2 次，合计 32 个 episode。GitHub 答案来自模型运行前的独立 REST API 查询，文件任务由 JSON 内容及最终文件状态判定。
- eager 组在第一次模型请求前发现并加载全部 14 个 MCP 工具；lazy 组使用现有默认流程，由模型自行发现、选择和加载。两组均保留相同内置工具、提示、模型、权限、输出上限及预算；要求所有业务读取/操作走 MCP，并由轨迹检查。eager 启动发现时间计入总耗时。
- 2 对任务并发；每对内部顺序运行，按任务序号及重复次数交错组别顺序。每次使用新 Runtime、会话与工作区，关闭记忆、自动整理和 worker。不设置模型温度。每次最多 12 轮模型、24 次工具、160,000 个已报告 token、240 秒；输出上限 4,096，输入加输出窗口 65,536。
- `queries.json`：14 个意图各配英文自然表达、中文自然表达、原始工具名，合计 42 条；每条事前标注一个目标工具。调用真实 `mcp_list` 关键词逻辑，在冻结目录上记录 Recall@1/3/5 和 MRR。单相关项时 Recall@K 等于 Hit@K。原名查询是单独的正向对照，不与自然语言混算。
- Schema 体积：当前 14 工具及官方只读端点目录扩展至 30、34 工具；新增工具只参与离线 Schema 统计，不发起调用。比较全量加载与仅加载文件读/写两个工具，包含 `tool_load` 候选名称枚举，使用 Aster 的 `cl100k_base` 估算器。这不是模型计费量或大规模任务成功率。
- 幂等：10 个独立的真实 filesystem MCP 写操作，各追加一次同会话重试、一次恢复后重试和一次参数冲突。检查回执标记、文件内容及纳秒修改时间。未知写入不重放的既有回归测试可作为补充，但不把单元测试次数当作真实服务可用率。

## 判定与统计

任务成功要求最终答案、必要 MCP 工具调用、文件产物/删除/保留规则全部通过，不能用 Runtime 的 completed 代替独立判定。工具指标分别报告参数错误率、业务返回成功率，以及符合预先任务工具/参数约束的成功调用率。后者的限定工具集合与参数规则保留在脚本中，不能当作覆盖所有等价解法的通用评测。

记录全部模型请求及诊断、首轮 Schema 估算 token、服务端报告的整任务 input/output/cached/total token、请求次数、端到端耗时、MCP 调用及状态。失败运行保留并计入，不反复重跑挑最好结果；无凭证或全部请求无用量时中止批量并单独诊断。报告缓存和服务端模型名，既不把估算量当计费量，也不把 token 换算为未核实的价格。

`freeze.json` 固定源文件、评测脚本、输入文件哈希和运行设置，运行前检查漂移。公开结果保存判分、用量、调用参数及轨迹摘要哈希；原始会话和请求留在本地忽略目录。检索实验和全量 Schema 统计不调用模型。主备切换成功率、切换延迟和备用熔断恢复均不在本次范围。

## 运行

```bash
conda activate aster
python evaluations/mcp-metrics-20261013/evaluate.py freeze
python evaluations/mcp-metrics-20261013/evaluate.py retrieval
python evaluations/mcp-metrics-20261013/evaluate.py idempotency
python evaluations/mcp-metrics-20261013/evaluate.py run
python evaluations/mcp-metrics-20261013/analyze.py
```

本次小样本围绕当前两个服务，不能外推至数百工具、长程项目调研或生产故障率。模型任务仅在 14 工具配置下运行；30/34 工具只有静态上下文统计。

## 执行中的测量修正

首轮离线 Schema 扩容统计发现配置白名单仍只允许原始 9 个 GitHub 工具，导致 30/34 工具时的 `tool_load` 名称枚举少计。保留原始 `schema-scaling.json`，由 `analyze.py` 显式扩展离线目录白名单并断言全部未加载名称在枚举中，写入 `schema-scaling-corrected.json`；报告只引用修正值。14 工具的值不变，已冻结模型实验的代码、配置、任务、判分均不变。

模型实验出现服务端未返回 usage 的传输超时重试。报告的 token 因此称为“API 已报告 token”，不能据此断言完整计费成本；缺失请求数与失败类别单独列出。主表仍保留全部运行，另外按两组所有 HTTP 请求均成功且都有用量的配对给出观测完整的辅助结果，筛选不取决于哪组更省或是否答对。

第 20 次结果（`files_create--eager--1`）的 3 次 HTTP 尝试均超时，没有返回用量，原运行器按预设条件停止。此时没有未落盘的工作区。一次独立的小请求在 4.24 秒内正常返回，记录为 `healthcheck.json`，不混入 A/B 数据。用 `resume.py` 审计全部已完成轨迹后，仅继续尚未启动的 12 次运行；保留此前全部失败。任务、组别顺序、并发量、预算和冻结的 `run_one` 均不变。恢复入口在发生新的完全无用量失败时，等同批另一个配对落盘后再停止，避免遗失正在执行的结果。

分析器将完全无用量运行计为失败，其 token 仅对已报告部分求和（该运行贡献 0 个已报告 token，真实用量未知）。首轮 input token 的均值仅使用有用量记录，并列出样本数；不把缺失用量当成真实的零消耗。`analyze.py --allow-partial` 可在服务再次不可用时生成明确列出未执行项的部分报告；默认仍要求 32 次结果全部存在。

最终 32 次全部落盘并通过轨迹审计。复核原始错误发现 `mcp_invalid_arguments` 只统计客户端 Schema 校验拒绝；`files_create--lazy--2` 的 `read_file(limit=10000)` 通过 Schema，但被服务端的 1..2000 范围限制拒绝。报告新增服务端参数范围错误一栏，保留原指标含义及原始结果；模型随后改为 2000 并成功。另有 7 次成功调用没有满足冻结的严格相关性规则（6 次额外目录查询、1 次合法 SHA 前缀），单独解释，不能用它们推断选错工具率。分析新增这些诊断字段，不改判分或重跑任务。
