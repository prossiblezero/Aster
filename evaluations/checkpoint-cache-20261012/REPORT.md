# 2026-10-12：检查点持久化与请求缓存优化

**已完成局部重构，本地检查点开销显著下降；本轮仍未证明稳定的整题降本、提速，也未达到扩展二十题的门槛。** 保留实现及全部结果，未追加付费重跑。历史 Aster 15/20、pi/Codex 的成绩及用量不变，简历不新增降本或竞品领先的结论。

## 实际改动

- 检查点 v3 将初始仓库文本与权限保存为一次写入的基线文件，JSON 和 SQLite 快照保存摘要引用。恢复检查引用、摘要及类型；旧 v1/v2 内联格式继续可读。便携迁移复制完整 `.aster/runs`，其中包含基线和观察记录。新任务、分支或新脱敏凭据使用独立基线，历史文件不改写。
- 同一次 checkpoint 的文件指纹使用已经取得的快照，减少一次完整仓库扫描。保持原有保存时机、工具批次保护、工作区漂移检查与隔离。
- Responses 请求用运行 ID 作为 `prompt_cache_key`；恢复沿用，独立运行/Worker 分开，后台记忆用独立 job ID。实际请求、归档与预算使用同一字段；Chat/Anthropic 不发送该字段。参考 pi/Codex 的具体源码依据见[前期诊断](../cost-diagnosis-20261012/REPORT.md)，没有照搬整套存储或引入新依赖。

生产代码修改前冻结 baseline，确认与上一轮 full-candidate 的 56 个源码文件摘要完全一致。[本轮生产补丁](source.patch)、[事先登记协议](PROTOCOL.md)、[基线清单](pilot-baseline/manifest.json)、[新版清单](pilot-candidate/manifest.json)保留。

Sphinx 评分有一个需要单列的限制：新版在 `tests/test_directive_other.py` 添加的测试与官方测试补丁尾部冲突；评分器的 checkout 同时包含尚不存在的新增测试路径，未成功还原该文件，后续官方补丁应用失败，最终收集 0 项。原始报告将 `infra_failure` 记为 false，却给出 `no_tests_collected`；沿用的汇总器因此错误地把它视为无评分错误的已评分题。原始产物和主分数保留，补充审计明确标记未执行测试；不能称新版 Sphinx 已由断言证实功能错误，也不能称所有八次都有效执行了独立测试。此问题只会阻止扩展，不用于提高成绩或替换结果。

## 为什么本地快了，整题仍慢

实跑 Django 的两段本地间隔（上下文构建到首次请求、最后回执到模型回复）合计 **91.034 → 25.027 秒**，checkpoint 大小 **38.22 → 1.06 MB**。Sphinx 对应间隔 **88.239 → 39.877 秒**。这些间隔含其他本地工作，不是专用检查点计时，且新旧轨迹不同；它们与微测共同说明大仓库持久化开销确实下降。

但 Django 的网关请求累计时间由 **82.534 → 738.622 秒**，新版包含一次约 120 秒的读取超时；最终无法按时交付。Scheme 基线有五次无用量的断连，新版没有。Requests 两版都把大部分时间花在请求等待，最后均超时。新旧版本先后运行、样本各一次，供应商路由和负载变化无法被排除，不能宣称缓存键改善了路由，也不能将这些延迟差异全归于本地实现。[基线供应商诊断](pilot-baseline/provider-diagnostics.json)、[新版供应商诊断](pilot-candidate/provider-diagnostics.json)。

此次已修复可复现的本地热点，但**降低真实任务总成本、稳定缩短评测仍未完成**。下一步应先处理已确认的评分补丁冲突，并把失败重试/供应商等待与有效模型工作分开衡量；不能再以四题费用总和下降作为扩大评测的理由。请求缓存键可保留为协议能力，当前证据不足以把它写成性能成果。

本轮共 **8 次任务尝试 + 10 次探针，193 次请求、4,951,819 已报告 tokens、11 次缺失用量**。所有已完成任务、评分容器、网关及专用网络均已退出；未提交或推送代码。
