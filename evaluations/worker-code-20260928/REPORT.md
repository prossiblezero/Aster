# Worker Code v2 真实模型对照（2026-09-28）

**评测完成：20 题、5 来源、40 次真实模型运行，未换题或重采样。当前 Worker 未体现整体优势。** Solo 通过 14/20，Worker 通过 13/20；全队已报告 token 增加 5.9%，总耗时增加 3.4%。配对为 Worker 独有成功 0 题、独有失败 1 题、两组均通过 13 题、均失败 6 题。

## 评分与费用口径

通过率以独立评分器为准。Aster 自己声称完成，与代码通过上游断言是两个指标；预算用尽后留下的代码仍接受同一个独立评分，完成状态单列。不能把候选自行编写的一个通过用例，当作原任务已经通过。

仓库结果的 `required_count` 是原 F2P/P2P 评分项数；`observed_count` 包含解析器收集的其他测试与别名，可能更大，不应直接当成实际测试数。完整性同时核对原评分名称是否全部出现，以及 F2P/P2P 各状态计数；具体原生日志数在逐题诊断中说明。

用量包含父 Agent 和全部子 Agent，并核对 HTTP 已返回 usage、请求账本及持久化运行树。金额没有可信的中转服务价格依据，因此只报告**服务端已报告的 input/output/cache/total tokens**，不编造美元费用。cache 是 input 的子集，不额外加到 total。缺失 usage 的传输尝试单列；已报告 token 不等于完整账单。

最终 838 次 HTTP 尝试中 831 次返回 usage：Solo 385/388，Worker 446/450。其余 7 次均是很短的 transport 重试，累计约 1.03 秒；费用未知，不能当成免费。831 次已返回用量与请求账本、父子运行树全部一致，合计 16,135,529 token。Solo 4 次、Worker 5 次父运行最终标为 `provider_error`，实际全部是 `evaluation_budget`；Worker 另有一个子运行同样因整队预算停止。没有将它们误计为模型服务故障。

耗时从 Agent 执行开始计到父子任务清理结束，包含自身工具、等待和整合；不含材料准备、独立评分和本次工程搭建。它是一次实测，不是稳定延迟估计。早期控制题与可信环境预检曾重叠执行，且请求响应速度存在明显波动，因此不能将全部墙钟差异归因于 Worker。

## 已核实的轨迹观察

多道题重复出现“读满工具预算，但没有最终交付”的模式。[Worker 循环](../../src/aster/core/workers.py) 在达到 12 步时直接结束；若最后一轮读取刚好耗尽额度，模型不会再获得一次生成总结的机会。因此部分子任务只用了 2–4 个模型轮次就停止，不能将“12 步”误解为完成了 12 轮推理。完整轨迹仍有保存，但 `answer` 为空且没有文件交付，与正常交付后父任务未采纳是不同问题。

8 道控制题两组均通过，其中 4 题真的使用 Worker，全部为只读 `explore`。4 份交付都进入父 Agent 后续请求；子任务读取的 12 个“题目—文件路径”组合中，有 11 个父 Agent 也读取过。这是文件级重叠，不等于 91.7% 的行或 token 浪费；独立审阅也可能需要阅读相同文件。本轮这些控制题未观察到通过率增益。

耗时有明显非机制因素：BigCodeBench/25 两组都没有启动 Worker，仍分别耗时约 157 秒与 58 秒；transpose 的父模型请求累计约 282 秒，整次运行约 289 秒，显式等待子任务仅约 5 秒。因此不能把未委派运行的随机提速写成委派收益，也不能将委派组全部额外耗时称为协调等待。

`django-11532` 的 Worker 组通过新增 Message-ID 用例，却遗漏共享 DNS 缓存的 SMTP 消费路径：局部编码后，缓存仍可能保存 Unicode，SMTP 握手随之报错。Solo 同时修复共享缓存，149 个原评分项全通过；Worker 为 1/1 F2P、129/148 P2P。上游新测试留下 Unicode 缓存，starter 也有同一组问题，所以这是**修复不完整**，不是新引入 19 种不同回归。两组测试收集完整、环境一致；Worker 的内部完成判断只对应自己的局部验证。

该题和 `django-13121` 的只读子任务都达到 12 步上限后停止。前者停止时交付摘要为空、没有文件修改。后者最终代码通过原评分，但全团队用量达到 756,286 token 后触发预算停止；运行记录中的 `provider_error` 实际类别是 `evaluation_budget`，不是 GPT 服务故障。

`django-16256` 两组产品补丁完全相同，均漏掉泛型关联管理器的 3 个异步接口，评分同为 F2P 6/9、P2P 53/53。原 62 个评分项全部收集；这不是评分环境故障。两组各发生 5 次 `approval_unavailable`：评测指南中的标准项目命令 `PYTHONPATH=. python tests/runtests.py ...` 被 Aster 的当前策略视为需审批命令，之后的测试入口绕行也未顺利完成。这是**指南与产品执行策略的共同障碍**，会消耗两组预算；本轮没有审批回调，与交互模式下用户可以批准命令的情况不同。不能把由此产生的开销或停止全部归因于 Worker，也不能说所有 Python/原生命令都无法执行。该题的子任务另消耗 64,008 token，在 12 步后停止且未完成报告。

`sphinx-9461` 两组均为 F2P 0/3、P2P 59/59，62 个评分项全部实际执行。Worker 恢复了 classmethod property 的类型与文档，但两组都未完成 autodoc 的 classmethod 标记及 Python domain 对该选项的支持。Worker 四次编辑较大的 `sphinx/ext/autodoc/__init__.py` 均遇到 `OSError: [Errno 7] Argument list too long`，工具记录 `changed_paths=[]`，预期修改没有落盘；其测试命令另被审批策略阻断。Solo 确实执行过两次失败的 pytest，因此共同失败不能主要归因于命令审批。两组最终均达到评测 token 预算，Worker 的一个只读子任务则达到 12 步上限。这条样本同时暴露基础工具限制，不能单独证明委派架构优劣。

`sympy-14248` 两组均为 F2P 0/2；Solo P2P 431/433，Worker 433/433，全部 435 个评分项无缺失。Solo 在通用 LaTeX Add 打印中丢失首项负号，造成两个真实回归；其 MatAdd 修改又依赖不能识别 MatMul 的 helper。Worker 修了 helper 对 MatMul 的识别，却没有修改三种打印器独立的 MatAdd/MatMul 路径，目标问题同样未解决。Worker 启动的两个只读任务分别因 12 步上限和全队预算停止，均无最终交付，共耗 63,826 token。两组的失败与前述 5 个基线兼容异常分开记录；Worker 还遇到验证命令审批和一次大测试文件编辑 E2BIG，不能将这些开销全部解释为协作成本。

`cancel-async-tasks` 两组均通过全部 6 项独立测试，Worker 组没有启动子任务。其约 96 秒/97,021 token 对 Solo 288 秒/267,135 token 的差异不能归为委派收益。Solo 自写测试先访问被沙箱清理的 `.tmp` 文件，随后一次测试运行超时，再修正测试并完成验证；这体现执行路径波动，两组都没有 HTTP 重试。

`cobol-modernization` 是实际协作的正面案例：两组独立评分均为 3/3，Worker 全队 317,713 token 对 Solo 438,067（少 27.5%），240 秒对 535 秒（少 55.2%）。第一个只读子任务仍在 12 步时无报告停止；第二个 `worker` 子任务的复合验证命令被审批阻断，但通过静态审查发现父任务的验证数据自相矛盾：输入指向不存在的商品，预期输出却修改了另一个商品。其报告进入父任务后续请求，父任务采纳该判断并补写自己的测试，最终交付通过。这证明本次审查产生了被采用的有效反馈，**不是子任务成功执行了验证或并行交付了代码**。Worker 组父请求中位耗时约 7.8 秒，Solo 约 13.3 秒，响应波动明显；因此 token 和耗时差只是一次观察，不能把全部差异归因于审查。两组全队模型调用分别为 24 与 25 次。

`kv-store-grpc` 两组均为 7/7，Worker 全队 233,625 token 对 Solo 323,905（少 27.9%），143 秒对 153 秒；两组都调用模型 20 次。唯一子任务只是调查初始工作区，在 12 步时无报告停止，消耗 28,968 token。Solo 多经历了测试收集、沙箱 socket 限制和编辑前重新读取，因此不能把这个用量差解释为有效子任务交付带来的收益。两组最后都通过独立评分器实际启动服务后的 RPC 验证。

`mvcc-lsm-compaction` 两组均自报完成，独立评分却均为 11/15：相同的四项多未来版本/墓碑尾保留检查失败，存储预算等其余检查通过。Worker 消耗 473,091 token/210 秒，Solo 为 342,417 token/180 秒。唯一子任务在 12 步时无报告停止，耗 25,916 token；父任务还因 `.tmp` 验证文件被清理而多次恢复测试入口。该题没有正确性收益，总开销增加，但直接子任务消耗只占总增量的一部分。

`session-window-debug` 两组同为 4/7，全部评分项执行，均遗漏未发射窗口被回收、合并窗口被强制 GC、多源空闲时水位线不推进这三个边界。Worker 的调查任务两轮就耗尽 12 个工具步，未交付报告。Terminal 五题的五个子任务实际都未改文件，其中三个使用 `explore` 模式、两个使用 `worker` 模式；模式标签不能代替实际交付统计。唯一正常完成者是 COBOL 的静态审查反馈。

`flipt-segments` 两组都通过原 3 个评分组；原生日志各有 157 个 RUN、155 个 PASS、0 个 FAIL 标记（另有跳过），不是只执行了三个小测试。两组都修改了六个产品文件，没有修改测试。Worker 为 1,018,130 token/281 秒，Solo 为 1,000,991 token/552 秒，模型调用均 38 次，工具调用 73 对 58。Worker 两个子任务共用 152,972 token，均在 12 步停止，无最终报告或文件修改。两组最后都触发 `evaluation_budget`，独立代码评分仍通过。`run_tests` 不支持 `go test`；带环境前缀或复合操作的命令又需审批，但 Worker 后来确实通过 `run_shell` 执行裸 `go test ./internal/ext`，根据编译错误去掉多余字段。因此不能说 Go 完全无法运行，也不能把这次约 49% 的墙钟下降当成成功协同的证据。

`openlibrary-authors` 两组均自报完成但未通过：Solo F2P 3/4、P2P 4/4；Worker 0/4、2/4，原 8 项全部执行。Solo 漏查“用输入 name 匹配已存作者 alternate_names”的优先级路径；Worker 另有类型对象访问异常及姓氏匹配遗漏。两组实际都跑过公开测试，最终失败不能归为 API 故障或无法验证。Worker 的调查子任务耗 115,626 token，父任务等约 105 秒后收到空报告；全队 token 比 Solo 多 49.9%、耗时多 78.6%。上游允许候选保留 `mock_infobase.py` 修改，Solo 将 mock 的普通等号也改成不区分大小写匹配，而生产查询仍未完整使用对应运算符；因此其 7/8 测试通过也不证明真实服务查询语义全部正确。两组整题均记失败，不扩大部分通过的含义。

这轮最可靠的改进线索是**让子任务在预算内形成可消费的交付**：工具预算耗尽前应能总结已有发现，父任务也需要识别空交付并及时接手。下一轮还应先解决验证命令、Go 测试识别和大文件编辑这些基础障碍，再在同一冻结数据上比较改造后的协作机制。当前结果适合作为失败基线与设计诊断，尚不支持在简历上宣称 Worker 普遍提高通过率或降低成本。本轮没有实施这些生产改动。
